# Veeam Backup & Replication

Veeam B&R — платформа резервного копирования виртуальных машин: снимает образы через гипервизор, хранит цепочки на репозитории и умеет восстанавливать как целую ВМ, так и отдельные файлы. Для L1–L2 важны компоненты, типы заданий, устройство цепочек и разбор упавших джобов.

## Компоненты

| Компонент | Роль |
|---|---|
| Backup Server | Центр управления: БД конфигурации, расписания, задания |
| Proxy | Снимает данные с источника, считает сжатие/дедуп, передаёт на репозиторий |
| Repository | Место хранения бэкапов: Windows/Linux-сервер, NAS (SMB/NFS), dedup appliance, object storage |
| Guest Interaction Proxy | Взаимодействие с гостевой ОС для VSS и file-level restore |
| Mount Server | Монтирует бэкап для восстановления файлов и Instant Recovery |
| Transport mode | Способ чтения данных: Direct SAN, Hot Add, NBD, Backup from Storage Snapshots |

Transport mode выбирают по среде: **Direct SAN** — чтение с LUN по FC/iSCSI, **Hot Add** — proxy как ВМ на том же хосте, **NBD** — через сеть гипервизора (медленнее), **Storage Snapshots** — снимки массива без нагрузки на хост.

## Типы заданий

- **Backup** — ВМ → репозиторий, основная защита.
- **Replication** — ВМ → хост/площадка, готовая к запуску копия (RPO минуты).
- **Backup Copy** — копия бэкапа в другой репозиторий/offsite, с GFS.
- **SureBackup** — автоматическая проверка: поднимает ВМ из бэкапа в изолированной лаборатории.
- **Backup to Tape** — выгрузка на ленту, offline-копия.
- **Agent Backup** — физические серверы и рабочие станции через Veeam Agent.

## Цепочки

| Тип | Как устроено | Плюсы | Минусы |
|---|---|---|---|
| Forward incremental | Full `.vbk` + инкременты `.vib` | Быстрый бэкап, мало места | Восстановление = full + вся цепочка |
| Forward + synthetic full | Периодически собирает новый full из цепочки | Не грузит источник | Нужны CPU/IO репозитория |
| Reverse incremental | `.vbk` всегда полный, изменения «вкручиваются» | Быстрое восстановление | Каждый раз перезапись full |
| Forever forward incremental | Один full + цепочка `.vib`, старые блоки переносятся в full | Компактно, без новых full | Длинная цепочка, чувствительна к целостности |

Файлы: `.vbk` — full, `.vib` — forward incremental, `.vrb` — reverse incremental, `.vbm` — метаданные цепочки. Опция **per-VM backup files** раскладывает цепочки по папкам ВМ — удобнее для восстановления и параллелизма.

## Application-aware processing и VSS

Перед снятием образа Veeam просит гостевую ОС подготовиться: в Windows через **VSS** (requester → coordinator → writer), в Linux — через скрипты/pre-freeze. Это даёт консистентный образ и, где настроено, **усечение логов** SQL/Exchange — иначе логи растут и база восстанавливается только на момент бэкапа.

Если VSS не сработал, джоб может упасть или выдать warning; для критичных БД проверять application-aware отдельно.

## Восстановление

- **Instant Recovery** — ВМ запускается прямо из бэкапа (vPower NFS), потом переносится на хранилище. Быстро, но зависит от репозитория.
- **Entire VM** — полное восстановление в исходное или новое место.
- **VM files / disk restore** — вернуть `.vmx` или отдельный `.vmdk`.
- **Guest files restore** — файлы внутри образа (Windows/Linux).
- **Veeam Explorer** — гранулярно: AD, Exchange, SharePoint, SQL, Oracle из бэкапа.
- **SureBackup** — проверка загрузки, heartbeat, скриптов и антивируса в виртуальной лаборатории.

## Scale-out repository, immutability, GFS

**SOBR** объединяет несколько репозиториев: performance tier (extent'ы), capacity tier (object storage, режимы copy/move), archive tier. Placement policy определяет, где лежат данные.

**Immutability** защищает точки восстановления от изменения/удаления: на уровне задания (block generation period), на hardened Linux-репозитории (XFS + immutable), либо через object lock в S3. Это ответ на шифровальщиков.

**GFS** хранит отдельные weekly/monthly/yearly full по своей политике, независимо от обычного retention.

## Типовые проблемы

| Симптом | Что проверять |
|---|---|
| Job failed | Причину в сессии/логе, а не только статус; сеть, доступ к ВМ, место |
| Snapshot removal issues | Зависший снапшот на ВМ, latency datastore, таймаут VSS, нехватка места |
| Не хватает места | Retention, health check, свободное место extent'а, размер цепочки |
| VM not found | ВМ удалена/переименована/мигрировала, изменился MoRef, права |
| Credentials | Пароль, локальный админ, UAC, права на гостевую ОС и vCenter |

**Логи**: `C:\ProgramData\Veeam\Backup\<Job>\` (`Job.log`, `Task.log`), логи proxy/repository, Event Viewer. В PowerShell:

```powershell
Get-VBRJob | Select-Object Name, LastResult, LastRun
Get-VBRJob -Name 'Daily VM Backup' | Start-VBRJob
Get-VBRBackupSession | Sort-Object EndTime -Descending |
    Select-Object JobName, Result, EndTime -First 5
Get-VBRRestorePoint -Name 'app01'
```

## Бесплатные альтернативы

- **Veeam Agent for Windows/Linux (Free)** — образ или файлы одного сервера, без центрального управления.
- **Windows Server Backup** — встроен в Windows, system state и bare-metal.
- **restic / borg** — CLI, дедуп и шифрование, удобны для Linux и скриптов.
- **rsync + ZFS/Btrfs snapshots** — свои снапшоты и отправка на удалённый хост.
- **Duplicati** — простой агент с шифрованием, для небольших сред.

## Чек-лист диагностики

1. Открыть задание → последняя сессия: на каком шаге и с какой ошибкой упало.
2. Проверить `Job.log`/`Task.log` и Event Viewer за время сбоя.
3. Проверить доступность vCenter/ESXi и самой ВМ (не удалена ли, не переименована).
4. Проверить учётные записи: vCenter, гостевая ОС, доступ к репозиторию.
5. Проверить свободное место на репозитории и сроки retention.
6. Проверить снапшоты на ВМ: нет ли зависших и «Consolidation needed».
7. Проверить VSS в гостевой ОС (`vssadmin list writers`), свободное место, службы.
8. Убедиться, что proxy/repository живы и доступны по сети.
9. После исправления запустить джоб вручную и проверить restore point.

## Вопросы на собеседовании

**Зачем нужен proxy, если есть backup server?**
Proxy снимает данные с источника и обрабатывает их, разгружая backup server. Несколько proxy дают параллелизм и распределение нагрузки по хостам и сетям.

**Чем forward incremental отличается от reverse?**
Forward пишет новые изменения в отдельные `.vib` после full, reverse держит `.vbk` всегда полным, вкручивая изменения в него. Первый быстрее на бэкапе и компактнее, второй — на восстановлении.

**Что даёт application-aware processing?**
Консистентный образ приложения и усечение логов через VSS. Без него БД может восстановиться в несогласованном состоянии, а логи растут бесконечно.

**Чем SureBackup отличается от обычного бэкапа?**
SureBackup автоматически поднимает ВМ из копии в изолированной лаборатории и проверяет загрузку/сервисы. Это проверка восстановления, а не создание копии.

**Зачем нужна immutability?**
Чтобы точки восстановления нельзя было изменить или удалить в течение срока. Защищает от шифровальщика и скомпрометированной учётной записи администратора.

**Почему джоб падает на этапе удаления снапшота?**
Хост не может консолидировать дельту: нет места, высокая latency datastore, зависший VSS или таймаут. Сначала разбирают снапшот и datastore, потом перезапускают джоб.

**Что такое scale-out repository?**
Объединение нескольких репозиториев в один пул с политикой размещения и опциональной capacity tier в object storage. Даёт масштабирование и offsite.

**Можно ли использовать Veeam Agent Free как полноценный бэкап?**
Для одного сервера — да, но без центрального управления, отчётности и продвинутых проверок. Для парка нужен B&R.
