# Active Directory. Основы

## Проблема: одна учётная запись на все компьютеры

В компании 200 компьютеров и 150 сотрудников. Каждый должен уметь войти в любой компьютер — хотя бы в переговорной.

Если учётки локальные, то:

- на каждом компьютере нужно завести 150 пользователей (или хотя бы тех, кто может там оказаться);
- сменил сотрудник пароль — надо поменять его на всех машинах, где он бывал;
- уволился — надо не забыть отключить его на каждом компьютере;
- выдал доступ к папке на сервере — надо завести его ещё и там.

Получается 200 независимых списков пользователей, которые никогда не совпадают.

**Домен** решает это: учётные записи хранятся в одном месте, а компьютеры спрашивают у него «можно этому человеку войти?». Один пароль, одно отключение, один список групп.

Разница коротко:

| | Рабочая группа | Домен |
|---|---|---|
| Где учётки | на каждом ПК своя база | одна общая база |
| Вход | только на свой ПК | на любой ПК домена |
| Пароли | менять везде | менять один раз |
| Права | на каждом ПК отдельно | централизованно |
| Кто управляет | пользователь | администратор |

Active Directory — реализация домена в Windows. Служба называется **AD DS** (Active Directory Domain Services).

## Контроллер домена

Сервер, на котором работает AD DS, называется **контроллером домена (DC)**. Он хранит базу объектов и проверяет вход.

Если контроллер один, то при его падении никто не войдёт в систему, не откроет почту, не получит доступ к файлам. Поэтому контроллеров ставят минимум два.

Два контроллера должны иметь одинаковые данные. Этот процесс называется **репликацией**. Она идёт не мгновенно: изменение, сделанное на одном DC, доедет до другого за секунды или минуты (в разных сайтах — дольше).

Отсюда типичная ситуация на работе: «я создал пользователя, а он не может войти». Его создали на одном контроллере, а проверяет вход другой, до которого изменение ещё не доехало. Лечится ожиданием или принудительной репликацией.

## Что происходит, когда человек входит в систему

Это лучший ответ на собеседовании, потому что показывает понимание всей цепочки.

1. **Компьютер ищет контроллер домена.** Спрашивает DNS: «где серверы домена `corp.local`?». Ответ лежит в специальных SRV-записях.
2. **Проверка подлинности.** Клиент и DC обмениваются через **Kerberos**: DC выдаёт билет (ticket), подтверждающий личность. Пароль по сети не передаётся.
3. **DC собирает список групп** пользователя и кладёт его в билет. Это важно: права проверяются по данным на момент входа.
4. **Применяются групповые политики** (GPO) — настройки компьютера и пользователя.
5. **Подключается профиль** — папка с настройками рабочего стола.
6. Пользователь работает.

Из этого следуют три практических вывода:

- **Без DNS домен не работает.** Не «плохо работает», а не работает вообще: клиент не найдёт DC.
- **Изменение групп не действует сразу** — нужен новый вход, иначе в билете старый список.
- **Сбитые часы ломают вход** — Kerberos не любит расхождение времени больше нескольких минут.

## Лес, дерево, домен, сайт — зачем столько уровней

На собеседовании могут спросить «что такое лес». Отвечать лучше не определением, а задачей.

| Уровень | Зачем нужен |
|---|---|
| **Домен** | одна база учёток и политик; граница административной ответственности |
| **Дерево** | несколько доменов с общим пространством имён (`corp.local`, `sales.corp.local`) |
| **Лес** | несколько деревьев, доверяющих друг другу; общая схема и общий каталог |
| **Сайт (site)** | группа подсетей с хорошей связью; подсказывает, какой DC ближе и когда реплицировать |

В маленькой компании почти всегда один домен и один сайт. Остальное нужно, когда компаний несколько или офисы в разных городах.

**OU (подразделение)** — это не «папка для красоты». Это граница, к которой привязывают GPO и на которую делегируют права. Поэтому структуру OU строят под управление, а не под оргструктуру.

## FSMO: пять ролей, которые нельзя разделить

Некоторые операции нельзя выполнять параллельно на всех контроллерах — иначе получится конфликт (например, два DC одновременно выдали бы один и тот же номер). Для этого есть пять ролей, которые в каждый момент принадлежат ровно одному DC:

| Роль | Что делает простыми словами |
|---|---|
| Schema Master | отвечает за изменения схемы (структуры базы) |
| Domain Naming Master | добавление/удаление доменов в лесу |
| PDC Emulator | главный по паролям и времени; сюда идут срочные проверки |
| RID Master | выдаёт блоки идентификаторов для новых объектов |
| Infrastructure Master | следит за ссылками между доменами |

На L1 достаточно знать: «есть пять ролей, они принадлежат конкретным контроллерам, смотреть — `netdom query fsmo`». Глубже — задача L2/L3.

## Порты: кто за что отвечает

| Порт | Протокол | Зачем |
|---|---|---|
| 53 | DNS | найти контроллер домена |
| 88 | Kerberos | проверка входа |
| 389 | LDAP | чтение каталога |
| 636 | LDAPS | то же с шифрованием |
| 445 | SMB | SYSVOL, общие папки, GPO |
| 135 | RPC | удалённое управление |
| 3268/3269 | Global Catalog | поиск по всему лесу |

Если между офисами закрыт 88 — «не входит в домен». Закрыт 445 — не применяются политики и не открываются шары. Поэтому при проблемах с доменом первым делом проверяют не «AD сломался», а доступность портов.

## SYSVOL и почему политики «не доезжают»

На каждом DC есть папка **SYSVOL**, которая реплицируется между контроллерами. В ней лежат скрипты входа и файлы групповых политик.

Если SYSVOL не реплицируется, политики применяются по-разному на разных машинах. Проверяется через `dfsrmig`/журналы репликации, но на L1 достаточно знать: «политики лежат в SYSVOL, он должен быть одинаковым на всех DC».

## DSRM: режим восстановления

**Directory Services Restore Mode** — специальный режим загрузки DC, в котором AD не запущена. Нужен, чтобы восстановить базу из бэкапа или сбросить пароль администратора восстановления.

Пароль DSRM задаётся при повышении сервера в DC. Если он потерян, восстановление AD усложняется — поэтому его сохраняют.

## Как диагностировать

Три инструмента, которые надо знать по имени:

```text
dcdiag                 :: общая проверка здоровья контроллера
repadmin /replsummary  :: состояние репликации между DC
nltest /dsgetdc:corp.local :: какой DC нашёл клиент
```

Типовой порядок: клиент не входит → `nltest` (нашёл ли DC) → `dcdiag` на DC → `repadmin` (не разъехались ли данные) → журналы.

## Чек-лист диагностики

1. Один пользователь или все? Если все — смотреть DC, DNS, сеть. Если один — учётку.
2. `nltest /dsgetdc:corp.local` — находит ли клиент контроллер.
3. `nslookup -type=SRV _ldap._tcp.dc._msdcs.corp.local` — есть ли записи DC в DNS.
4. `dcdiag` на контроллере — какие проверки падают.
5. `repadmin /replsummary` — нет ли ошибок репликации.
6. Проверить время на клиенте и DC (`w32tm /query /status`) — расхождение ломает Kerberos.
7. Проверить порты 53/88/389/445 между клиентом и DC.
8. Для одной учётки — `Search-ADAccount -LockedOut`, срок пароля, членство в группах.

## Вопросы на собеседовании

**Чем домен отличается от рабочей группы?** В домене учётные записи централизованы на контроллерах, и вход возможен на любой компьютер домена; в рабочей группе у каждого ПК своя база.

**Что происходит при входе пользователя?** DNS находит DC, Kerberos проверяет учётку и выдаёт билет с группами, применяются GPO, подключается профиль.

**Почему AD не работает без DNS?** Клиент не может найти контроллер домена: его адрес хранится в SRV-записях DNS.

**Зачем несколько контроллеров?** Отказоустойчивость и распределение нагрузки; данные между ними реплицируются.

**Что такое OU и зачем оно?** Контейнер, к которому привязывают групповые политики и делегируют права; граница управления, а не просто папка.

**Что такое FSMO?** Пять ролей, которые в каждый момент выполняет один DC, чтобы избежать конфликтов при изменении каталога.

## Что запомнить

1. Домен = одна база учёток вместо 200 локальных.
2. Вход — это DNS → Kerberos → группы → GPO → профиль.
3. Без DNS домена нет; без синхронного времени тоже.
4. OU — граница политик и делегирования.
5. Диагностика: `nltest`, `dcdiag`, `repadmin`.
