# LDAP

## Проблема: одной базы учёток мало

В компании есть Active Directory. Но кроме Windows-машин появляются:

- NAS, которому нужно проверять, кто входит;
- Jira/Confluence — своя система, но логины должны быть те же;
- VPN-шлюз;
- файловый сервер на Linux (Samba);
- корпоративная почта.

Заводить пользователей в каждой системе отдельно — тот же хаос, что и с локальными учётками на ПК: уволился — надо не забыть отключить в пяти местах.

Решение: все системы ходят за проверкой в **один каталог**. Язык, на котором они это делают, называется **LDAP**.

## Что такое LDAP и чем он не является

LDAP (Lightweight Directory Access Protocol) — это **протокол доступа к каталогу**, а не сама база.

- **Active Directory** — каталог, который умеет LDAP (и ещё Kerberos, DNS, GPO).
- **OpenLDAP** — другой каталог, тоже говорящий на LDAP.
- **389 Directory Server**, **ApacheDS** — ещё implementations.

Поэтому фраза «настроить LDAP» обычно значит «настроить интеграцию с каталогом по протоколу LDAP». А «AD vs LDAP» — сравнение каталога с протоколом, что некорректно, но так говорят.

## Каталог — это дерево, а DN — адрес в нём

Записи в каталоге лежат в иерархии, как папки:

```text
dc=corp,dc=local
└── ou=Users
    └── cn=Иван Иванов
        ├── sAMAccountName: ivanov
        ├── mail: ivanov@corp.local
        └── memberOf: cn=GG-Accounting,ou=Groups,...
```

**DN (Distinguished Name)** — полный путь к записи:

```text
cn=Иван Иванов,ou=Users,dc=corp,dc=local
```

Читается **справа налево**: `dc=local` → `dc=corp` → `ou=Users` → `cn=Иван Иванов`. Слева — самая конкретная часть, справа — самая общая. Это как адрес: «квартира 5, дом 3, улица Ленина, город Москва».

Компоненты:

| Префикс | Значение |
|---|---|
| `dc=` | компонент домена (domain component) |
| `ou=` | организационное подразделение |
| `cn=` | общее имя (common name) |
| `uid=` | идентификатор пользователя (чаще в OpenLDAP) |

## objectClass и атрибуты: тип записи и поля

У каждой записи есть **objectClass** — тип объекта: `user`, `group`, `computer`, `organizationalUnit`.

Атрибуты — поля этого объекта: `cn`, `sAMAccountName`, `mail`, `telephoneNumber`, `memberOf`.

Схема — набор правил: какие атрибуты обязательны для какого типа. Поэтому нельзя создать пользователя без обязательных полей, и поэтому у AD и OpenLDAP схемы похожи, но не одинаковы.

Практический вывод: при интеграции сторонней системы нужно узнать, какие атрибуты она ожидает. Чаще всего это `sAMAccountName`/`uid`, `mail`, `displayName`, `memberOf`.

## Что делает клиент: bind и search

Любая интеграция состоит из двух операций:

1. **Bind** — «я такой-то, вот пароль». Так проверяется учётная запись.
2. **Search** — «найди мне записи по условию».

Есть ещё `add`, `modify`, `delete`, но на L1 чаще всего встречаются именно bind и search.

**Анонимный bind** — подключение без пароля. Некоторые каталоги его разрешают для чтения части данных; в AD по умолчанию анонимный доступ ограничен. Если система подключается анонимно и «ничего не видит» — обычно в этом причина.

**Сервисная учётная запись** — отдельный пользователь, под которым система ходит в каталог (например, `svc-jira`). Так делают, чтобы не хранить чей-то личный пароль и чтобы было видно, кто именно читает каталог.

## Фильтры: как формулируется запрос

Фильтр — строка в скобках. Символы:

| Символ | Значение |
|---|---|
| `(атрибут=значение)` | равно |
| `(атрибут=*значение*)` | содержит |
| `(&(...)(...))` | И — все условия |
| Условие «ИЛИ» | `(...)` ИЛИ `(...)` — хотя бы одно |
| `(!(...))` | НЕ — исключить |

Примеры:

```text
(objectClass=user)
(&(objectClass=user)(sAMAccountName=ivanov))
(&(objectClass=user)(department=Бухгалтерия)(!(disabled=TRUE)))
(|(sAMAccountName=ivanov)(sAMAccountName=petrov))
(sAMAccountName=ivan*)
```

Разбор третьего: «пользователь, у которого отдел «Бухгалтерия», и при этом не отключён».

**Scope** — где искать:

| Scope | Значение |
|---|---|
| base | только сама запись |
| one | непосредственные дети |
| sub | всё поддерево (обычно нужен он) |

## Порты и шифрование

| Порт | Что |
|---|---|
| **389** | LDAP, обычно с StartTLS (шифрование после подключения) |
| **636** | LDAPS, TLS с самого начала |

Важно: при simple bind пароль идёт по сети. Без TLS он фактически открыт. Поэтому в интернет и даже внутри сети интеграции настраивают на 636 или 389+StartTLS, а сертификат должен быть доверенным.

## AD и OpenLDAP: в чём разница на практике

| | Active Directory | OpenLDAP |
|---|---|---|
| Аутентификация | Kerberos (LDAP для чтения) | чаще simple bind |
| Схема | фиксированная, расширяется осторожно | гибкая |
| Группы | `memberOf`, `member` | `memberOf`/`memberUid` (зависит от overlay) |
| Управление | ADUC, GPO | конфиги, `ldapadd` |
| Где встречается | Windows-сеть | Linux, NAS, самодельные сервисы |

Для интеграции обычно важны только DN, атрибуты и фильтр — остальное система делает сама.

## Как выглядит запрос руками

```bash
ldapsearch -x -H ldap://dc01.corp.local -D "cn=svc-jira,ou=Service,dc=corp,dc=local" \
  -W -b "ou=Users,dc=corp,dc=local" "(&(objectClass=user)(sAMAccountName=ivanov))" \
  cn mail memberOf
```

По частям:

- `-x` — simple bind (без SASL);
- `-H` — адрес сервера;
- `-D` — DN пользователя, под которым подключаемся;
- `-W` — спросить пароль;
- `-b` — база поиска (откуда начинать);
- строка в кавычках — фильтр;
- `cn mail memberOf` — какие атрибуты вернуть.

Если ответ пустой, а запись существует — почти всегда неверная база (`-b`) или фильтр.

## Где LDAP встречается в работе

- NAS/файловое хранилище: вход доменной учёткой.
- Jira, Confluence, GitLab: синхронизация пользователей и групп.
- VPN: проверка учётки перед выдачей доступа.
- Samba на Linux: вступление в домен и проверка пользователей.
- Принтеры/МФУ: адресная книга из каталога.
- Почтовые системы: поиск получателей.

Во всех случаях настраивают одно и то же: адрес сервера, порт, базу поиска, DN сервисной учётки, пароль, фильтр пользователей и сопоставление атрибутов.

## Типовые ошибки

| Код/симптом | Причина | Что делать |
|---|---|---|
| **49 invalid credentials** | неверный DN или пароль сервисной учётки | проверить DN полностью, не только логин |
| **32 no such object** | неверная база поиска | проверить `-b`, начиная с домена |
| **50 insufficient access** | у учётки нет прав читать атрибут | проверить права в AD |
| **8 strong auth required** | сервер требует TLS | использовать 636/StartTLS |
| Пустой результат | фильтр или scope | упростить фильтр до `(objectClass=user)` |

## Чек-лист диагностики

1. Проверить доступность порта: 389 или 636.
2. Выполнить bind руками (`ldapsearch`/`ldp.exe`) — проходит ли аутентификация.
3. Проверить DN сервисной учётки полностью, включая OU.
4. Упростить фильтр до `(objectClass=*)` и убедиться, что база поиска верна.
5. Проверить, какие атрибуты требует система и есть ли они в каталоге.
6. Проверить TLS: сертификат доверенный, имя совпадает.
7. Посмотреть логи системы-клиента: она обычно пишет точный код LDAP.

## Вопросы на собеседовании

**Что такое LDAP?** Протокол доступа к каталогу: bind для проверки учётки, search для поиска записей.

**Чем LDAP отличается от AD?** LDAP — протокол, AD — каталог, который его использует вместе с Kerberos, DNS и GPO.

**Что такое DN?** Полный путь к записи в дереве каталога, читается справа налево: от общего `dc=` к конкретному `cn=`.

**Зачем нужен bind?** Чтобы подтвердить, кто подключается: приложение проверяет логин и пароль или подключается под сервисной учёткой.

**Почему запрос возвращает пусто?** Неверная база поиска, слишком строгий фильтр или нет прав на чтение.

**Почему LDAP без TLS опасен?** При simple bind пароль передаётся по сети; без шифрования его можно перехватить.

## Что запомнить

1. LDAP — язык, а не база; AD — один из каталогов.
2. DN — адрес записи, справа налево.
3. Две операции: bind (кто я) и search (что найти).
4. 389 — LDAP, 636 — LDAPS; без TLS пароль открыт.
5. Пустой ответ = база, фильтр или права.
