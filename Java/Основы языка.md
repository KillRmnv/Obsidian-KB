# Java SE — Шпаргалка: Основы языка (теория + подводные камни собесов)

***

## 1. JVM, JDK, JRE, Байт-код, ClassLoader

### Что есть что

**JDK (Java Development Kit)** — полный набор инструментов разработчика: компилятор `javac`, отладчик, профилировщик, и внутри него — JRE. Нужен тем, кто пишет код.[1]

**JRE (Java Runtime Environment)** — среда для запуска: стандартные библиотеки + JVM. Нужен тем, кто только запускает приложение, не разрабатывает.[1]

**JVM (Java Virtual Machine)** — виртуальная машина, которая исполняет байт-код. Сама по себе **платформозависима** (под каждую ОС своя реализация), но байт-код, который она исполняет — платформонезависим. Именно в этом суть «Write Once, Run Anywhere».[2]

**Байт-код** — промежуточный формат (.class файлы), который получается после компиляции .java файлов. Это не машинный код и не исходник — это инструкции для JVM.[2]

### Как JVM исполняет байт-код: Interpreter и JIT

JVM начинает с **интерпретации** байт-кода — построчного выполнения. Это медленнее нативного кода. Когда JVM замечает «горячие» методы (часто вызываемые) — включается **JIT-компилятор (Just-In-Time)**, который компилирует их в нативный машинный код прямо во время работы программы.[3][2]

HotSpot JVM имеет два JIT-компилятора:[3][2]
- **C1 (Client)** — быстрая компиляция, меньше оптимизаций. Для приложений с быстрым стартом (GUI).
- **C2 (Server)** — глубокая оптимизация. Для долго работающих серверных приложений.

С Java 7 используется **Tiered Compilation** — сначала C1, потом при необходимости C2.

### ClassLoader — механизм загрузки классов

ClassLoader загружает байт-код класса в память JVM в момент, когда класс впервые используется. Существует три уровня:[4][5]

| ClassLoader | Загружает | Реализован на |
|---|---|---|
| **Bootstrap** | Ядро JDK (`java.lang`, `java.util`) | Нативный код C/C++ |
| **Extension (Platform, Java 9+)** | `javax.*`, расширения JRE | Java |
| **Application (System)** | Классы из CLASSPATH | Java |

**Принцип делегирования (Parent Delegation Model):** когда Application ClassLoader получает запрос, он **не грузит сам**, а делегирует родителю (Extension), тот — Bootstrap. И только если Bootstrap не нашёл класс — загружает Extension, и т.д. вниз по цепочке.[6][7][8]

**Зачем это нужно:** предотвращает подмену системных классов. Нельзя создать свой `java.lang.String` и заставить JVM использовать его — Bootstrap всегда загрузит оригинал первым.

### ⚠️ Подводные камни на собесе

**"JVM платформозависима или нет?"** — JVM **платформозависима** (разная для Windows/Linux/macOS), но байт-код — платформонезависим. Многие путают.[2]

**"Что будет, если один класс загрузить двумя ClassLoader'ами?"** — JVM считает их **разными типами**. `instanceof` вернёт `false`, при касте — `ClassCastException`, даже если байт-код идентичен. Это реальная причина утечек памяти в application servers.[9]

**"Можно ли переопределить `java.lang.String`?"** — Нет. Bootstrap всегда загрузит его первым благодаря делегированию.

**"Где хранятся метаданные классов?"** — В **Metaspace** (с Java 8). До этого — в PermGen, который был причиной `OutOfMemoryError: PermGen space`. Metaspace растёт динамически в нативной памяти.

## 2. Типы данных: Primitive vs Reference, Autoboxing/Unboxing

### Primitive vs Reference — теория

В Java существует жёсткое разделение между **примитивными** типами и **ссылочными** типами (объектами).

**Примитивы** хранят значение напрямую. Локальные примитивы хранятся в **Stack** (в стек-фрейме текущего метода). Примитивы-поля объекта хранятся в **Heap** вместе с объектом.[10][11][12]

**Ссылочные типы** хранят в Stack **ссылку** (адрес), а сам объект находится в **Heap**.[11]

8 примитивных типов: `byte` (1 байт), `short` (2), `int` (4), `long` (8), `float` (4), `double` (8), `char` (2), `boolean` (размер не определён спецификацией JVM, на практике 1 бит логически, но хранится как byte или int).

**Значения по умолчанию полей:** числовые → 0, `boolean` → false, `char` → `'\u0000'`, ссылочные → `null`. Локальные переменные в методах default value **не имеют** — компилятор требует явной инициализации.

### Autoboxing / Unboxing — механизм

**Autoboxing** — автоматическое преобразование примитива в объект-обёртку: `int → Integer`, `double → Double` и т.д. Происходит при добавлении в коллекцию, передаче туда где ожидается Object, присваивании.[13][14]

**Unboxing** — обратное преобразование: `Integer → int`. Происходит при арифметических операциях с обёртками, сравнении с примитивом, передаче в метод с примитивным параметром.[14][13]

Autoboxing — синтаксический сахар компилятора. Фактически `Integer.valueOf(x)` и `intValue()`.

### Integer Cache — самый частый вопрос на собесе[15][16][17][18]

JVM **кэширует** объекты `Integer` в диапазоне **от -128 до 127**. При autoboxing значений в этом диапазоне всегда возвращается один и тот же объект из кэша. Значения за пределами диапазона каждый раз создают **новый объект в Heap**.

Именно поэтому сравнение обёрток через `==` даёт непредсказуемые результаты: в диапазоне кэша `==` вернёт `true`, за его пределами — `false`. Аналогичный кэш есть у `Long`, `Short`, `Byte`, `Character` (0..127).[19][18]

Единственный правильный способ сравнивать обёртки — `.equals()`.

### ⚠️ Подводные камни

**NullPointerException при unboxing.** Если переменная-обёртка равна `null` и происходит unboxing (например, при сравнении `Integer` с `int`, при арифметике) — выбрасывается NPE. Это особенно опасно в неочевидных местах: при передаче `null` из Map, при автогенерированных equals и т.д.[20][21][13]

**Performance при autoboxing в цикле.** Каждый boxing создаёт новый объект в Heap, что нагружает GC. Особенно критично в tight loops с миллионами итераций. Для накопления числовых значений всегда используй примитивные типы.[22]

**Сравнение `Integer` через `==` в условиях с mixed types.** Если один операнд — `int`, другой — `Integer`, происходит unboxing `Integer` в `int`. Если `Integer == null`, NPE неизбежен.[20]

## 3. Операторы, управляющие конструкции

### if — теория

В Java условие `if` обязано быть **булевым выражением** (`boolean`). Нельзя написать `if (x)` где x — int (как в C/C++). Компилятор выдаст ошибку.[23]

Проверка присваивания вместо сравнения в `if` тоже невозможна из-за типизации: `if (x = 5)` не скомпилируется для int.

### switch — теория и правила[24][25][23]

**Допустимые типы выражения в switch:** `byte`, `short`, `int`, `char`, `String` (с Java 7), `enum`, а также их обёртки `Byte`, `Short`, `Integer`, `Character`.

**Недопустимые типы:** `long`, `float`, `double`, `boolean`, объекты произвольных классов.

**Правила case-меток:**
- Значения должны быть **compile-time константами** (литералы, `final` переменные, enum-константы).
- Все case-метки должны быть **уникальными** — дубликаты вызывают ошибку компиляции.
- `default` — необязателен и может находиться в любом месте switch (не только последним).

**Fall-through** — поведение по умолчанию: если `break` отсутствует, выполнение "проваливается" в следующий case. Это не баг языка, а намеренный механизм — позволяет группировать несколько case с одним телом.[26]

**Switch Expression (Java 14+):** новый синтаксис со стрелкой `->` исключает fall-through полностью, switch может возвращать значение, компилятор проверяет полноту вариантов.[27]

### ⚠️ Подводные камни switch

**Октальные литералы в case.** Java поддерживает восьмеричные числа с префиксом `0`. Если случайно написать `case 012` — это `10` в десятичной. Если одновременно есть `case 10` — ошибка компиляции (дубликат).[25]

**switch не работает с диапазонами и условиями.** `switch` проверяет только **точное равенство**. Написать `case x > 5` нельзя — для диапазонов нужен `if-else` или `switch` с pattern matching (Java 21+).[28][24]

**default выполняется не всегда последним.** Если `default` стоит в середине и нет `break` — возможен fall-through из него в следующие case.[23]

### Циклы — теория и подводные камни

**for-each (enhanced for)** работает через `Iterator` для коллекций и по индексу для массивов. Нельзя модифицировать коллекцию в процессе итерации — будет `ConcurrentModificationException`. Нет доступа к индексу.

**Labeled break/continue** — позволяют прерывать или пропускать итерации **внешних** циклов. Редко используются, но часто спрашивают на собесах.

**Бесконечный цикл `while(true)`** — легитимный паттерн для серверных циклов, но без условия выхода — классическая ловушка. В многопоточности `while(true)` с захваченным `synchronized` блоком приводит к starvation других потоков.

**`do-while`** — выполняется **хотя бы один раз**, так как условие проверяется после тела.

## 4. Массивы

### Теория

Массив в Java — это **полноправный объект**, наследующий `Object`. Создаётся через `new`, хранится в **Heap**. У массива есть поле `length` (не метод), неизменяемое после создания.[29]

Элементы массива инициализируются значениями по умолчанию: 0 для числовых, `false` для boolean, `null` для ссылочных.

Многомерные массивы в Java — это **"массив массивов"**: `int[][]` — это массив ссылок на массивы `int[]`. Внутренние массивы могут иметь разную длину (jagged/ragged arrays).

### Ковариантность массивов — главный теоретический подводный камень[30][31][32]

Массивы в Java **ковариантны**: если `B extends A`, то `B[]` является подтипом `A[]`. Это значит, что можно присвоить `String[]` переменной типа `Object[]`. Компилятор это допустит.

Однако если потом через ссылку `Object[]` положить объект несовместимого типа — JVM бросит `ArrayStoreException` **в runtime**, а не на этапе компиляции. Это является известной слабостью системы типов Java.

Generics, в отличие от массивов, **инвариантны**: `List<String>` — НЕ является подтипом `List<Object>`. Это намеренное ограничение, которое обеспечивает type safety на уровне компилятора, а не runtime.[32]

На собесе часто спрашивают: "Почему generics инвариантны, а массивы ковариантны?" — ответ: исторически массивы появились раньше generics; ковариантность массивов — legacy-решение, которое теперь считается design flaw.[32]

### ⚠️ Подводные камни

**`==` у массивов сравнивает ссылки.** `array.equals(other)` тоже сравнивает ссылки (унаследован от Object). Для сравнения содержимого — только `Arrays.equals()`. Для вложенных массивов — `Arrays.deepEquals()`.

**`toString()` массива** выдаёт `

**`clone()` массива** создаёт **shallow copy**: для массива примитивов это полная копия, для массива объектов — копируются ссылки, не сами объекты.

**Передача массива в метод** — передаётся ссылка, метод может изменять элементы массива. Это отличается от передачи примитива.

## 5. Строки: String, StringBuilder, StringBuffer

### Почему String — immutable?[33][34][35][36]

Неизменяемость `String` — архитектурное решение, обусловленное четырьмя причинами:

1. **String Pool.** JVM кэширует строковые литералы в специальной области Heap. Если бы строки были изменяемы, изменение одной ссылки затронуло бы все другие ссылки на тот же объект в пуле — непредсказуемые баги.

2. **Безопасность.** Строки используются как имена классов при загрузке, URL, пароли, параметры соединений с БД. Если бы их можно было изменить после передачи — это стало бы дырой в безопасности.

3. **Thread Safety.** Immutable объект потокобезопасен по определению — без synchronized, без lock, без volatile. Несколько потоков могут читать одну строку одновременно без проблем.

4. **Кэширование hashCode.** `String.hashCode()` вычисляется один раз и кэшируется внутри объекта. Это делает `String` высокоэффективным ключом в `HashMap` / `HashSet`. У mutable объекта хэш пришлось бы пересчитывать при каждом изменении.

### String Pool — механизм[35][37]

String Pool — специальная область в Heap (с Java 7 перенесена из PermGen в основной Heap), где JVM хранит уникальные строковые литералы.

При создании строки через **литерал** (`"hello"`) JVM проверяет пул: если такая строка уже есть — возвращает существующую ссылку, не создаёт новый объект. При создании через **`new String("hello")`** — всегда создаётся новый объект в heap, минуя пул.

Метод **`intern()`** принудительно помещает строку в пул и возвращает ссылку из пула. После `intern()` сравнение через `==` работает корректно (но это антипаттерн — лучше всегда `.equals()`).

### String vs StringBuilder vs StringBuffer[38][39][40]

| Характеристика | String | StringBuilder | StringBuffer |
|---|---|---|---|
| Изменяемость | Immutable | Mutable | Mutable |
| Thread-safety | ✅ (immutable) | ❌ | ✅ (все методы synchronized) |
| Производительность | Медленно при конкатенации | Самый быстрый | Медленнее StringBuilder из-за locks |
| Когда использовать | Строковые константы, ключи Map | Однопоточная конкатенация | Многопоточная среда |
| Появился | Java 1.0 | Java 5 | Java 1.0 |

Компилятор Java **автоматически** оптимизирует простую конкатенацию `+` вне цикла через `StringBuilder`. Однако конкатенацию **внутри цикла** компилятор не оптимизирует — каждая итерация создаёт новый `StringBuilder` и новый `String`.[41]

### ⚠️ Подводные камни

**`==` vs `.equals()` для строк.** Главное правило: **никогда не сравнивай строки через `==`**. `==` проверяет, одинаковые ли ссылки (один ли объект в памяти). `.equals()` проверяет содержимое. Из-за String Pool `==` может случайно работать для литералов, создавая ложное ощущение корректности.[41]

**`null + "строка"` не бросает NPE.** Java конвертирует `null` в строку `"null"` при конкатенации. Результат: `"nulltext"`. Это распространённый источник неожиданных данных в логах и output.[42]

**`String` — `final` класс.** Нельзя наследоваться и переопределить поведение. Попытка создать `class MyString extends String` даст ошибку компиляции.

**`substring()` до Java 7** разделял backing `char[]` массив с оригиналом — одна маленькая подстрока могла удерживать в памяти огромную оригинальную строку (memory leak). С Java 7 `substring()` создаёт копию — проблема устранена.[41]

**`String.format()` vs конкатенация.** `format()` заметно медленнее простой конкатенации из-за парсинга шаблона. В горячих путях кода лучше `StringBuilder`.

**Компиляторная оптимизация константных строк.** `"abc" + "def"` компилируется в `"abcdef"` ещё на этапе компиляции — полностью бесплатно. Но `str1 + str2` где переменные не `final` — не оптимизируется таким образом.
