Для наглядности возьмём иерархию:
```java
abstract class Employee { Long id; String name; }
class Programmer extends Employee { String language; }
class Manager    extends Employee { int teamSize; }
```

Ниже разбор трёх подходов, которые вы указали, с примерами маппинга, генерируемой схемой БД и сравнением по вашим критериям.

---

## 🔹 1. `@MappedSuperclass` (Маппинг на базовый класс)
**Суть:** Чисто Java-наследование для переиспользования кода. Базовый класс **не является сущностью**, таблицы для него нет. Каждый наследник — самостоятельная таблица.

```java
@MappedSuperclass
public abstract class Employee {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Column private String name;
}

@Entity @Table(name = "programmers")
public class Programmer extends Employee {
    @Column private String language;
}

@Entity @Table(name = "managers")
public class Manager extends Employee {
    @Column private int teamSize;
}
```
**Схема БД:**
- `programmers` (`id`, `name`, `language`)
- `managers` (`id`, `name`, `team_size`)
- Таблицы `employees` **нет**.

---

## 🔹 2. `SINGLE_TABLE` (Одна таблица в целом)
**Суть:** Вся иерархия хранится в одной таблице. Различие типов определяется дискриминатором.

```java
@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "emp_type", discriminatorType = DiscriminatorType.STRING)
public abstract class Employee {
    @Id @GeneratedValue private Long id;
    @Column private String name;
}

@Entity @DiscriminatorValue("PROGRAMMER")
public class Programmer extends Employee {
    @Column private String language;
}

@Entity @DiscriminatorValue("MANAGER")
public class Manager extends Employee {
    @Column private int teamSize;
}
```
**Схема БД:**
- `employee` (`id`, `name`, `language`, `team_size`, `emp_type`)

---

## 🔹 3. `TABLE_PER_CLASS` (Одна таблица на класс)
**Суть:** Каждая конкретная сущность получает свою таблицу, но **дублирует все поля базового класса**. Полиморфные запросы выполняются через `UNION`.

```java
@Entity
@Inheritance(strategy = InheritanceType.TABLE_PER_CLASS)
public abstract class Employee {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) // IDENTITY НЕ РАБОТАЕТ
    private Long id;
    @Column private String name;
}

@Entity @Table(name = "programmers")
public class Programmer extends Employee {
    @Column private String language;
}

@Entity @Table(name = "managers")
public class Manager extends Employee {
    @Column private int teamSize;
}
```
**Схема БД:**
- `programmers` (`id`, `name`, `language`)
- `managers` (`id`, `name`, `team_size`)
*(Структура столбцов `id`, `name` дублируется)*

> ⚠️ **Важно:** `TABLE_PER_CLASS` часто путают с `@Inheritance(JOINED)`. При `JOINED` базовые поля хранятся в отдельной таблице `employee`, а подклассы — в отдельных таблицах только со своими полями (`programmers` имеет только `id`, `language`). `JOINED` используется чаще, так как `TABLE_PER_CLASS` имеет ограничения в Hibernate.

## 📊 Сравнительная таблица

| Критерий | `@MappedSuperclass` | `SINGLE_TABLE` | `TABLE_PER_CLASS` |
|----------|---------------------|----------------|-------------------|
| **Производительность** | ✅ Быстрое точечное чтение. ❌ Нет полиморфных запросов в JPA | ✅ Быстрое чтение без `JOIN`. ⚠️ Сканирование широкой таблицы при росте подклассов | ❌ Медленные полиморфные запросы (`UNION ALL`). ✅ Быстрые точечные запросы |
| **Расширяемость** | ✅ Новый тип = новая таблица. ❌ Добавление общего поля = `ALTER` всех таблиц | ✅ Новый тип = только `@DiscriminatorValue`. ⚠️ Новое общее поле = `ALTER TABLE` (блокировка) | ❌ Новое общее поле = `ALTER` всех таблиц-наследников. Дублирование схемы |
| **Удобство работы (JPA)** | ⚠️ Теряется полиморфизм: `em.find(Employee.class, id)` не работает. Запросы только к конкретным таблицам | ✅ Максимальное удобство. Полная поддержка полиморфизма, `instanceof` в JPQL, каскады | ⚠️ Ограничения Hibernate: не поддерживает `IDENTITY`, проблемы с `JOIN` и пагинацией в полиморфных запросах |
| **Нормальные формы** | ✅ **3НФ**. Каждая таблица автономна, нет NULL-полей, нет дублирования структуры | ❌ **Нарушает 1НФ/3НФ**. Много `NULL`, денормализация, повторяющиеся группы по смыслу | ⚠️ **Нарушает принцип единственного источника схемы**. Структурное дублирование столбцов базового класса |

## 🔍 Детальный разбор критериев

### 1. Производительность
- `@MappedSuperclass`: Идеально для CRUD по конкретным типам. Если нужно выбрать "всех сотрудников", придётся писать 2 отдельных запроса и объединять в Java.
- `SINGLE_TABLE`: Самый быстрый для полиморфного чтения (один `SELECT`). Но при 50+ полях подклассов таблица становится "раздутой", индексы деградируют, растёт размер страниц БД.
- `TABLE_PER_CLASS`: Полиморфный запрос `SELECT e FROM Employee e` превращается в `UNION ALL`, что убивает производительность на больших объёмах. Пагинация (`setFirstResult/setMaxResults`) работает некорректно без оконных функций.

### 2. Расширяемость
- `@MappedSuperclass`: Гибко для добавления новых типов. Но если через год понадобится поле `departmentId` для всех, миграция затронет все таблицы.
- `SINGLE_TABLE`: Легко добавлять типы. Но добавление общего поля требует изменения одной, но часто используемой таблицы (риск блокировок в PROD).
- `TABLE_PER_CLASS`: Наихудший вариант для эволюции схемы. Каждое общее поле = синхронное изменение N таблиц.

### 3. Удобство работы
- `@MappedSuperclass`: Прост в начале, но ломает архитектуру, если позже потребуется полиморфная логика (аудит, общие репозитории, Spring Data `JpaSpecificationExecutor<Employee>`).
- `SINGLE_TABLE`: Золотой стандарт JPA. Работает "из коробки" с каскадами, `orphanRemoval`, `@EntityGraph`, спецификациями.
- `TABLE_PER_CLASS`: Требует ручной настройки генераторов ID (`SEQUENCE` или `TABLE`), обходных путей для пагинации и `JOIN`. В Hibernate 6+ поддержка улучшена, но ограничения остаются.

### 4. Соответствие нормальным формам
- `@MappedSuperclass`: Полностью нормализовано. Каждая таблица описывает один конкретный тип сущности.
- `SINGLE_TABLE`: Явная денормализация. Нарушает 1НФ (смысловая повторяемость групп атрибутов) и 3НФ (много nullable-полей, функциональные зависимости не зависят от PK полностью).
- `TABLE_PER_CLASS`: Формально данные нормализованы, но схема нарушает принцип DRY на уровне DDL. При изменении базового класса схема расходится.

## ✅ Практические рекомендации

| Сценарий | Рекомендуемый подход |
|----------|----------------------|
| Аудит-поля (`createdAt`, `id`, `version`), которые не участвуют в полиморфных запросах | `@MappedSuperclass` |
| Иерархия с 2-5 подклассами, частые полиморфные запросы, приоритет скорости разработки | `SINGLE_TABLE` |
| Строгая изоляция данных подклассов, редкие полиморфные запросы, требование к нормализации | `@Inheritance(JOINED)` *(вместо TABLE_PER_CLASS)* |
| Legacy-БД с готовыми таблицами, дублирующими структуру | `TABLE_PER_CLASS` |

> 💡 **Реальная практика:** В 90% корпоративных проектов используют комбинацию:
> - `@MappedSuperclass` для технических полей (`BaseEntity`)
> - `SINGLE_TABLE` или `JOINED` для бизнес-иерархий
> - `TABLE_PER_CLASS` избегают из-за ограничений Hibernate и стоимости `UNION`

Если уточните, какие операции преобладают в вашем случае (чтение полиморфных списков, точечные обновления, частое добавление новых ролей, строгие требования к НФ), помогу выбрать конкретную стратегию и дам готовый шаблон с миграцией Flyway/Liquibase.
