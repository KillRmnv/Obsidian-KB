А, понял! Вы имеете в виду классическую ловушку: **двусторонняя связь → взаимный вызов `equals()/hashCode()` → `StackOverflowError`**. Разберём механику и покажем, как её гарантированно избежать.

---

###  Почему возникает рекурсия?
```java
@Entity class Order {
    @OneToMany(mappedBy = "order") List<OrderItem> items;
    // equals() вызывает items.equals() или items.hashCode()
}

@Entity class OrderItem {
    @ManyToOne Order order;
    // equals() вызывает order.equals() или order.hashCode()
}
```
Цепочка вызовов:
`order.equals()` → `items.hashCode()` → `item1.hashCode()` → `order.hashCode()` → `items.hashCode()` →  **StackOverflowError**

Даже если явно не вызывать методы, коллекции (`HashSet`, `HashMap`, `contains()`) вызывают их автоматически.

---

###  Единственное рабочее правило
**Никогда не включайте двусторонние связи в `equals()` и `hashCode()`**.  
Эти методы должны идентифицировать **сущность**, а не весь граф объектов. Связи навигационны, а не идентификационны.

---

###  Корректная реализация для обеих сторон

#### Сторона `One` (родитель)
```java
@Entity
public class Order {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(unique = true, nullable = false)
    private String orderNumber; // бизнес-ключ

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Order)) return false;
        Order order = (Order) o;
        return orderNumber != null && orderNumber.equals(order.orderNumber);
    }

    @Override
    public int hashCode() {
        return orderNumber != null ? orderNumber.hashCode() : System.identityHashCode(this);
    }
}
```

#### Сторона `Many` (дочерняя)
```java
@Entity
public class OrderItem {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id")
    private Order order; //  НАМЕРЕННО ИГНОРИРУЕМ в equals/hashCode

    private String sku;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof OrderItem)) return false;
        OrderItem item = (OrderItem) o;
        return id != null && id.equals(item.id);
    }

    @Override
    public int hashCode() {
        return getClass().hashCode(); // стабилен, не зависит от id и order
    }
}
```
>  **Почему так безопасно?**  
> - `Order` сравнивается по бизнес-ключу (стабилен до и после `persist`)  
> - `OrderItem` сравнивается по `id` только если он уже присвоен, иначе объекты не равны  
> - Связи `order` и `items` **физически не участвуют** в вычислениях → рекурсия невозможна

###  Lombok: как не выстрелить себе в ногу
`@EqualsAndHashCode` по умолчанию включает **все поля**, включая связи → гарантированный `StackOverflow`.

**Вариант 1: Явное исключение**
```java
@EqualsAndHashCode(exclude = {"order", "items"})
@Entity
public class OrderItem { ... }
```

**Вариант 2: Только явные включения (рекомендуется)**
```java
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
@Entity
public class Order {
    @EqualsAndHashCode.Include
    private String orderNumber;
    // items автоматически игнорируется
}
```

###  Почему нельзя "аккуратно" сравнивать связи?
Некоторые пытаются сделать так:
```java
//  ОПАСНО
@Override public int hashCode() {
    return Objects.hash(id, order != null ? order.getId() : null);
}
```
Проблемы:
1. **Нарушает контракт `Set`/`Map`**: при изменении `order` объект "исчезает" из коллекции.
2. **Lazy-инициализация**: `order.getId()` может триггерить прокси, что ломает производительность.
3. **Семантика**: `equals()` должен отвечать на вопрос "это тот же логический объект?", а не "совпадает ли весь граф?".

---

###  А если реально нужно сравнивать полные графы?
Используйте **отдельные методы**, а не `equals()`/`hashCode()`:
```java
public boolean hasSameStructure(Order other) {
    if (!this.orderNumber.equals(other.orderNumber)) return false;
    if (this.items.size() != other.items.size()) return false;
    return new HashSet<>(this.items).equals(new HashSet<>(other.items));
}
```
Или используйте библиотеки типа `ObjectDiffer` / `Javers` для аудита и сравнения сущностей.

---

###  Итоговый чеклист для двусторонних связей
| Что делать | Почему |
|------------|--------|
|  Исключить `@ManyToOne`/`@OneToMany` из `equals/hashCode` | Предотвращает рекурсию и `LazyInitializationException` |
|  Использовать бизнес-ключ или стабильный подход с `id` | Гарантирует корректную работу в `Set`/`Map` до и после сохранения |
|  `hashCode()` для transient-объектов → `System.identityHashCode(this)` или `getClass().hashCode()` | Хэш не меняется после `persist()` |
|  Не сравнивать коллекции связей в `equals()` | Ломает контракт `Set`, вызывает N+1, рекурсию |
|  Не использовать Lombok `@EqualsAndHashCode` без `exclude`/`onlyExplicitlyIncluded` | Автоматически добавит связи → StackOverflow |

Если у вас конкретная связка (например, `@ManyToMany` с промежуточной сущностью или наследование) — киньте код, покажу, как правильно разорвать цикл рекурсии без потери логики.
