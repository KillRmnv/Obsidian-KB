## Что такое Servlet, чем отличается от CGI, зачем нужен

**Servlet** — это Java‑класс на стороне сервера, который обрабатывает HTTP‑запросы и формирует HTTP‑ответы, живя внутри сервлет‑контейнера (Tomcat, Jetty и т.д.).qna.habr+1

Главные отличия от CGI:github+3

- CGI: на каждый запрос веб‑сервер стартует **отдельный процесс/программу**, что дорого по ресурсам и не позволяет легко хранить состояние между запросами.
    
- Servlet: контейнер поднимает JVM и **создаёт один объект сервлета**, а каждый запрос обрабатывается **новым потоком в том же процессе** → намного лучше по производительности и памяти.github+2
    
- Сервлеты портируемы (стандартный API Java EE/Jakarta), работают в любом контейнере, реализующем спецификацию.github+2
    

Формулировка для собеса:

> Servlet — это серверный Java‑компонент, который обрабатывает HTTP‑запросы внутри сервлет‑контейнера. В отличие от CGI, сервлеты работают в одном процессе JVM, используют многопоточность и дают более высокую производительность и удобное управление состоянием.github+3

## Роль Servlet Container (Tomcat/Jetty)

Сервлет не живёт сам по себе, он всегда внутри **контейнера сервлетов** (Tomcat, Jetty, GlassFish, WildFly…). Контейнер:blog.skillfactory+3

- **Управляет жизненным циклом сервлетов**: загружает класс, создаёт экземпляр, вызывает `init()` один раз, затем `service()`/`doGet()`/`doPost()` на каждый запрос и `destroy()` при остановке.bsac+2
    
- **Создаёт потоки под запросы**: на каждый HTTP‑запрос создаётся отдельный поток, которому контейнер передаёт `HttpServletRequest` и `HttpServletResponse`.textjavascript+1
    
- **Делает маппинг URL → сервлет**: по конфигурации (`web.xml` или аннотации `@WebServlet`) решает, какой сервлет вызвать для конкретного URL‑паттерна.javastudy+1
    
- **Обеспечивает безопасность и конфигурацию**:
    
    - аутентификация/авторизация (декларативная security, роли, защищённые URL),
        
    - управление сессиями (создание `HttpSession`, хранение `JSESSIONID`),
        
    - работа с метаданными запросов/ответов, логирование, ресурсы контекста.javarush+2
        

Ещё можно добавить: контейнер создаёт «среду выполнения» для сервлетов — HTTP‑памятки, кодировки, доступ к ресурсам приложения, listener’ы и фильтры.java-online+3

Кратко для ответа:

> Servlet‑container (Tomcat/Jetty) управляет жизненным циклом сервлетов, создаёт потоки под запросы, маппит URL на сервлеты, организует сессии, безопасность и обмен данными между клиентом и сервлетом. Он фактически предоставляет среду выполнения для сервлетов.blog.skillfactory+4

## Структура веб‑приложения: WEB‑INF, web.xml, META‑INF

Типичная структура war‑приложения:javarush+2

text

`myapp.war   index.jsp / static files ...  META-INF/     (манифест и доп. метаданные приложения)  WEB-INF/      web.xml          (дескриптор развёртывания)      classes/         (скомпилированные .class файлы)      lib/             (зависимости .jar)`

Основные элементы:

- **WEB-INF/**
    
    - Содержит **конфигурацию и классы**, недоступные напрямую по HTTP: сервер не имеет права отдавать файлы из `WEB-INF` клиенту как статику.studfile+1
        
    - Здесь лежит `web.xml`, каталог `classes` с скомпилированными классами и `lib` с jar‑зависимостями.javarush+2
        
- **web.xml**
    
    - Дескриптор развёртывания: конфигурация сервлетов, фильтров, слушателей, маппингов, параметров (init‑params, context‑params), настроек безопасности.studfile+2
        
    - При старте контейнер читает `WEB-INF/web.xml` и настраивает приложение согласно его содержимому.javastudy+1
        
- **META-INF/**
    
    - Для war/ear — метаданные приложения, манифест и доп. инфа, тоже не должна отдаваться напрямую пользователю.[studfile](https://studfile.net/preview/13455632/page:14/)
        

Фраза для собеса:

> В корне war лежат публичные ресурсы (JSP, HTML, статика). Папка `WEB-INF` содержит недоступные напрямую классы, библиотеки и файл `web.xml` — дескриптор развёртывания с настройками сервлетов, фильтров, security и т.д. Папка `META-INF` хранит дополнительные метаданные приложения.javarush+2

Если хочешь, дальше можем таким же форматом закрыть следующий блок — «Жизненный цикл сервлета» или «Request/Response и forward vs redirect», чтобы у тебя была связная шпора.
