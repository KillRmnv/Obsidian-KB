## Транзакции в Spring — полный разбор для собеседования

Транзакции — это одна из самых частых тем на собеседованиях уровня Middle/Senior. Вопросы обычно идут по нарастающей: от определений ACID до подводных камней AOP-прокси. Ниже — структурированный ответ, который покажет глубину понимания.

---

### 1. Что такое транзакция и ACID

**Транзакция** — это логическая единица работы, которая выполняется как единое целое. Она либо завершается успешно (коммит), либо полностью откатывается (роллбэк) в случае ошибки.

**ACID** — четыре свойства, которым должна удовлетворять транзакция:

- **Atomicity (Атомарность)** — всё или ничего. Если одна операция в транзакции упала, все предыдущие изменения откатываются.
- **Consistency (Согласованность)** — транзакция переводит базу данных из одного корректного состояния в другое (сохраняются все ограничения, внешние ключи, уникальность).
- **Isolation (Изоляция)** — параллельно выполняющиеся транзакции не должны мешать друг другу (регулируется уровнями изоляции).
- **Durability (Долговечность)** — после коммита данные сохраняются даже при сбое системы (запись на диск).

**Зачем транзакционность в бизнес-логике?** 
Бизнес-операции почти всегда состоят из нескольких шагов. Классический пример — **перевод денег**: списать сумму со счета А и зачислить на счет Б. Если на втором шаге произойдет сбой (падение БД, сеть), деньги должны вернуться на счет А. Без транзакций данные становятся несогласованными, что в банковской сфере недопустимо.

### 2. Аннотация `@Transactional` — полный гайд

#### Где вешать?
- **На сервисный слой (`@Service`)** — это стандарт и лучшая практика.
- Почему не на контроллеры? Контроллер — это представление, а транзакции — это бизнес-логика. Кроме того, контроллер может вызывать несколько сервисов, и управлять транзакцией на уровне контроллера — значит смешивать ответственности.
- Почему не на репозитории? Методы репозитория — это атомарные CRUD-операции. Если повесить транзакцию туда, она закроется сразу после сохранения, и вы не сможете объединить несколько операций в одну бизнес-единицу.

#### Propagation (Распространение транзакций) — как ведут себя вложенные вызовы

| Тип | Описание | Пример из жизни |
| :--- | :--- | :--- |
| **REQUIRED** (по умолчанию) | Присоединяется к существующей транзакции или создаёт новую, если её нет. | Обычный метод сохранения заказа, который вызывает метод сохранения клиента. Всё должно быть в одной транзакции. |
| **REQUIRES_NEW** | Всегда создаёт **новую** транзакцию, приостанавливая текущую, если она есть. | Логирование ошибок. Если основная транзакция упала, логи должны сохраниться отдельно. Важно помнить, что разные транзакции не видят изменений друг друга до коммита. |
| **MANDATORY** | Требует существующей транзакции. Если её нет — кидает исключение. | Метод, который должен выполняться строго внутри другой транзакции (например, проверка безопасности, которая должна быть частью родительской операции). |
| **SUPPORTS** | Если транзакция есть — присоединяется, если нет — работает без транзакции. | Метод-читалка, который может работать как сам по себе, так и внутри транзакции для согласованности данных. |
| **NOT_SUPPORTED** | ВСЕГДА выполняется без транзакции. Если есть активная — приостанавливает её. | Методы, которые не должны блокировать ресурсы (например, простая проверка кэша). |
| **NEVER** | Запрещает выполнение внутри транзакции. Если есть активная — кидает исключение. | Операции, которые точно не должны быть в транзакции (например, аналитика, которая может читать незакоммиченные данные, если ей это не важно). |
| **NESTED** | Создаёт вложенную транзакцию. Откат внутренней не откатывает внешнюю (если внешняя не упала). Используется с Savepoint. | Отдельная логика внутри заказа, отказ которой не должен ломать весь заказ. |

#### Rollback для исключений (критично для собеса)
**По умолчанию** Spring откатывает транзакцию только на **`RuntimeException`** (unchecked) и **`Error`**. 
**`Checked` исключения (например, `IOException`, `SQLException` без обертки) НЕ вызывают откат** по умолчанию.

```java
@Transactional(rollbackFor = Exception.class) // теперь откатывает ВСЁ
public void transferMoney() throws MyBusinessException { ... }

@Transactional(noRollbackFor = NullPointerException.class) // специально не откатываем на NPE
public void riskyLogic() { ... }
```

### 3. Прокси-модель и Self-Invocation (главная ловушка!)

Spring реализует `@Transactional` через **AOP (Аспектно-ориентированное программирование)**. При старте приложения Spring создаёт **прокси-объект** вашего сервиса (динамический JDK-прокси или CGLIB-прокси).

#### Как это работает:
1. Когда вы инжектите сервис через `@Autowired`, вы получаете не сам объект, а **прокси**.
2. Когда вызываете метод на этом прокси, прокси проверяет, есть ли аннотация `@Transactional`. Если есть — перед вызовом открывает транзакцию, вызывает реальный метод, затем коммитит или откатывает.
3. После вызова прокси возвращает управление.

#### Почему self-invocation (внутренний вызов) НЕ работает?
Рассмотрим пример:

```java
@Service
public class UserService {
    public void methodA() {
        // ВЫЗОВ ИЗНУТРИ (self-invocation)
        methodB(); // БЕЗ ТРАНЗАКЦИИ! Прокси игнорируется.
    }

    @Transactional
    public void methodB() {
        // логика...
    }
}
```

Здесь `methodA` вызывает `methodB` через `this.methodB()`. Поскольку вызов происходит внутри реального объекта (а не через прокси), Spring **не перехватывает** вызов, и транзакция для `methodB` не открывается.

#### Как исправить?
1. **Внедрить сам бин (Self-Injection)** — лучший способ:
```java
@Service
public class UserService {
    @Autowired
    private UserService self; // инжектим прокси самого себя

    public void methodA() {
        self.methodB(); // теперь работает через прокси!
    }
}
```
2. **Использовать `AopContext.currentProxy()`** (не очень удобно, требует настройки экспозиции прокси):
```java
((UserService) AopContext.currentProxy()).methodB();
```
3. **Разделить логику на отдельные сервисы** (перенести `methodB` в другой `@Service`) — наиболее чистый архитектурный подход.

### 4. Бонусный блок (для "звёздного" ответа)

#### Уровни изоляции (`isolation`)
Уровень изоляции определяет, как изменения одной транзакции видны другой.

- `READ_UNCOMMITTED` — грязное чтение (видны незакоммиченные данные).
- `READ_COMMITTED` — неповторяемое чтение (данные могут меняться за время транзакции).
- `REPEATABLE_READ` — фантомное чтение (другие транзакции могут вставить строки, влияющие на условия запроса).
- `SERIALIZABLE` — полная изоляция (блокировки на уровне таблицы, медленно, но безопасно).

*Важно*: Изоляция настраивается на уровне БД, и не все СУБД поддерживают все уровни (например, MySQL использует `REPEATABLE_READ` по умолчанию, а PostgreSQL — `READ_COMMITTED`).

#### `readOnly = true` — зачем это?
- **Оптимизация**: Hibernate не отслеживает изменения (не делает dirty checking), что снижает нагрузку на память.
- Некоторые БД используют этот флаг для оптимизации плана выполнения запроса.
- Применяется к методам, которые только читают данные (`find`, `get`).

#### Transaction Manager — кто управляет?
`@Transactional` требует наличия `PlatformTransactionManager`. В Spring Boot для JPA автоматически создаётся `JpaTransactionManager`. Если используется несколько источников данных — потребуется явно указывать менеджер транзакций (`transactionManagerRef`).

#### Программное управление транзакциями (альтернатива)
Иногда нужен гибкий контроль внутри метода. Тогда используют `TransactionTemplate`:

```java
@Autowired
private TransactionTemplate transactionTemplate;

public void handle() {
    transactionTemplate.execute(status -> {
        // код, обернутый в транзакцию
        return result;
    });
}
```

> *"Транзакции в Spring реализованы через AOP. В бизнес-логике мы вешаем `@Transactional` на сервисный слой. По умолчанию используется propagation REQUIRED и откат только на RuntimeException. Важно помнить про self-invocation: вызов метода внутри того же класса не проходит через прокси, поэтому транзакция не открывается — решаю через self-injection или вынос в отдельный бин. Управляю уровнями изоляции через параметр `isolation`, а для чтения ставлю `readOnly = true` для оптимизации. При сложных сценариях использую `REQUIRES_NEW`, когда вложенная транзакция не должна зависеть от родительской (например, логирование ошибок)."*

Если собеседование углубится в Hibernate, добавьте, что `readOnly` отключает механизм dirty checking (автоматическое отслеживание изменений), что повышает производительность. Удачи! Если готовы — можно переходить к следующей теме (например, **Spring Security** или **Микросервисы / Spring Cloud**).
