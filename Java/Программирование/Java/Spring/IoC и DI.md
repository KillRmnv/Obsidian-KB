## Что такое IoC и DI в Spring

- **Inversion of Control (IoC)** — принцип, при котором объект **не сам управляет своим жизненным циклом и зависимостями**, а передаёт этот контроль внешнему контейнеру.javarush+4
    
- **Dependency Injection (DI)** — конкретный способ реализации IoC: вместо того чтобы объект сам создавал зависимости (`new`), контейнер **создаёт их и «вкалывает» (inject) в объект** через конструктор, сеттер или поле.javarush+3
    

Фраза для собеса:

> IoC — это когда управление созданием и связями объектов отдаётся контейнеру. DI — это способ реализовать IoC: контейнер сам создаёт бины и внедряет их в другие бины через конструктор, сеттеры или поля.habr+5

## Типы Dependency Injection в Spring

Spring поддерживает три основных способа внедрения зависимостей:otus+4

1. **Конструкторная (constructor injection)**
    
    - Зависимости передаются через параметры конструктора.
        
    - Рекомендуемый способ для обязательных зависимостей: объект нельзя создать без них, проще писать тесты, удобно с `final` полями.
        
    - В Spring Boot чаще всего используешь именно это (через автогенерируемый конструктор и `@Autowired` опционально).
        
2. **Сеттерная (setter injection)**
    
    - Зависимости передаются через публичные сеттеры.
        
    - Хороша для **опциональных** зависимостей или когда нужно менять зависимости после создания бина.sysout+2
        
    - Минус: объект можно создать в «полусобранном» состоянии.
        
3. **Через поле (field injection)**
    
    - `@Autowired` прямо на поле.
        
    - Удобно и коротко, но считается **антипаттерном** в прод‑коде:
        
        - сложнее тестировать (нужно лезть в reflection),
            
        - нарушает принцип явности зависимостей,
            
        - затрудняет иммутабельность.javarush+2
            

Фраза:

> В Spring есть конструкторная, сеттерная и полевая инъекция. Конструкторная — предпочтительна для обязательных зависимостей, сеттерная — для опциональных, field injection удобна, но считается антипаттерном из‑за проблем с тестируемостью и явностью зависимостей.arenda-server+3

## Жизненный цикл бина в Spring и @PostConstruct/@PreDestroy

Типичный жизненный цикл бина в Spring IoC‑контейнере:javarush+3

1. **Создание экземпляра (instantiation)** — контейнер создаёт объект (через конструктор/фабричный метод).
    
2. **Внедрение зависимостей (population)** — контейнер внедряет все зависимости в поля/сеттеры/конструктор.proselyte+1
    
3. **Hooks и инициализация**:
    
    - вызов методов `*Aware` интерфейсов (`BeanNameAware`, `ApplicationContextAware` и т.д.), если реализованы;
        
    - `BeanPostProcessor` (before‑init);
        
    - метод, помеченный **`@PostConstruct`**;
        
    - `afterPropertiesSet()` из `InitializingBean`, если реализован;
        
    - `BeanPostProcessor` (after‑init).habr+1
        
4. **Использование бина** — бин живёт в контексте и используется другими бинами.
    
5. **Уничтожение (destroy)** при закрытии контекста:
    
    - вызов метода, помеченного **`@PreDestroy`**;
        
    - `destroy()` из `DisposableBean` или метода, заданного в `@Bean(destroyMethod="...")`.arenda-server+2
        

Роль аннотаций:

- `@PostConstruct` — метод будет вызван **после создания бина и внедрения всех зависимостей, но до использования**.profit247+2  
    Используется для инициализации ресурсов, стартовых проверок, кэшей.
    
- `@PreDestroy` — метод будет вызван **перед уничтожением бина**, при закрытии контекста; тут закрывают соединения, чистят ресурсы.habr+2
    

Фраза:

> Spring сам создаёт бины, внедряет в них зависимости, затем вызывает `@PostConstruct` для финальной инициализации, после чего бин используется в приложении. При остановке контекста вызывается `@PreDestroy` для корректного освобождения ресурсов.javarush+4

## Ключевые аннотации: компоненты и конфигурация

Основные stereotype‑аннотации (все — вариации `@Component`):habr+5

- **`@Component`**
    
    - Базовая аннотация для любого Spring‑компонента.
        
    - Говорит контейнеру: «создай бин этого класса и положи в контекст».
        
- **`@Service`**
    
    - Специализация `@Component` для сервисного слоя (бизнес‑логика).
        
    - Семантическая маркировка, иногда используется AOP для логгинга/транзакций.sibinfo+2
        
- **`@Repository`**
    
    - Специализация `@Component` для DAO/репозиториев.
        
    - Дополнительно включает перевод исключений в `DataAccessException` в Spring Data.habr+2
        
- **`@Controller`**
    
    - Специализация `@Component` для MVC‑контроллеров (обрабатывают web‑запросы, возвращают view).github+1
        
- **`@RestController`** (хотя ты его не просил, его часто спрашивают)
    
    - `@Controller + @ResponseBody` по умолчанию, возвращает данные (JSON/XML), а не view.
        
- **`@Configuration`**
    
    - Класс конфигурации Spring (аналог XML‑конфига), внутри которого объявляются `@Bean`‑методы.proselyte+1
        
    - Сами такие классы тоже бины, их обрабатывает контейнер.
        
- **`@Bean`**
    
    - Ставится на метод в `@Configuration`‑классе.
        
    - Говорит: возвращаемый объект — это бин, зарегистрируй его в контексте.javarush+1
        
    - Удобно для интеграции сторонних библиотек и тонкой конфигурации.
        
- **`@Autowired`**
    
    - Помечает место, куда нужно внедрить зависимость: конструктор, сеттер, поле.javarush+2
        
    - Включает авто‑поиск бина по типу (и, при необходимости, по имени).
        
- **`@Qualifier`**
    
    - Используется вместе с `@Autowired`, когда в контексте несколько бинов одного типа.
        
    - Позволяет указать конкретный бин по имени/квалификатору: `@Qualifier("emailService")`.sibinfo+2
        

Фраза:

> Классы помечаются `@Component` и его специализациями (`@Service`, `@Repository`, `@Controller`) для автоматической регистрации в контексте. Конфигурация — через `@Configuration` и методы `@Bean`. Зависимости внедряются `@Autowired`, а при нескольких реализациях одного интерфейса выбор делается через `@Qualifier`.habr+6
