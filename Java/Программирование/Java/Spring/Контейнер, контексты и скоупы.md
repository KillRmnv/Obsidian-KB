## ApplicationContext vs BeanFactory

Оба — **контейнеры Spring**, управляющие бинами и их зависимостями, но `ApplicationContext` — «продвинутый» контейнер поверх базового `BeanFactory`.baeldung+4

Кратко:

- **BeanFactory**
    
    - Базовый контейнер, минимальный функционал DI.geeksforgeeks+1
        
    - Ленивая инициализация: бины создаются при первом `getBean()`.stackoverflow+3
        
    - Почти не используется напрямую в обычных приложениях.
        
- **ApplicationContext**
    
    - Расширяет `BeanFactory`, предоставляет **enterprise‑фичи**:smartprogramming+3
        
        - eager‑инициализация бинов по умолчанию,
            
        - поддержка AOP,
            
        - события (event‑publishing / event‑listening),
            
        - i18n (сообщения, `MessageSource`),
            
        - автосканирование компонентов, аннотации (`@Component`, `@Autowired`),
            
        - поддержка всех web‑скоупов (`request`, `session`, `application`).
            
    - Это то, что фактически используется в Spring / Spring Boot.
        

Фраза:

> BeanFactory — базовый DI‑контейнер с ленивой инициализацией и минимальными возможностями. ApplicationContext расширяет BeanFactory и добавляет AOP, события, i18n, автосканирование и web‑скоупы, поэтому в реальных проектах почти всегда используют именно ApplicationContext.javarush+4

## Скоупы бинов: singleton, prototype, request, session, application

Скоуп — это **правило, сколько экземпляров бина создаёт контейнер и как долго они живут**.spring+3

Основные:

- **`singleton` (по умолчанию)**
    
    - Один экземпляр бина на контейнер (`ApplicationContext`).geeksforgeeks+2
        
    - Все `getBean("id")` возвращают **один и тот же объект**.
        
    - Типичный выбор для сервисов, репозиториев, конфигураций.
        
- **`prototype`**
    
    - Каждый `getBean("id")` создаёт **новый экземпляр**.dev+2
        
    - Контейнер только создаёт и «отдаёт», дальнейший жизненный цикл на совести клиента.
        
    - Используется, когда нужна новая сущность на каждый запрос к контейнеру (stateful‑объекты и т.п.).
        
- **`request`** (только в web‑контексте)
    
    - Один экземпляр бина на **HTTP‑запрос**.marcnuri+1
        
    - Для каждого запроса создаётся новый объект, в пределах запроса — один и тот же.
        
    - Удобен для хранения данных, связанных с конкретным запросом (формы, DTO, контекст).
        
- **`session`** (web)
    
    - Один экземпляр бина на **HTTP‑сессию**.spring+1
        
    - Каждый пользователь получает свою копию бина, живущую столько, сколько сессия.
        
    - Подходит для пользовательского состояния (корзина, preferences), но осторожно с памятью и потоками.
        
- **`application`** (web, иногда называют `singleton` на уровне `ServletContext`)
    
    - Один экземпляр бина на весь **ServletContext** (всё веб‑приложение).marcnuri+1
        
    - Практически совпадает с дефолтным singleton, но привязан к web‑контексту.
        

Фраза:

> По умолчанию бины singleton — один экземпляр на контейнер. Prototype создаёт новый экземпляр на каждый запрос к `getBean`. В web‑контексте есть ещё request/session/application: один бин на HTTP‑запрос, на HTTP‑сессию и на всё приложение соответственно.geeksforgeeks+3

(Можно помнить: `@Scope("singleton")`, `@Scope("prototype")`, `@Scope("request")`, `@Scope("session")`, `@Scope("application")`.)

## Как создаётся контекст: standalone, Boot, web

## 1. Standalone / обычный Spring

- **Java‑config**:
    

java

`AnnotationConfigApplicationContext ctx =         new AnnotationConfigApplicationContext(AppConfig.class);`

- `AppConfig` помечен `@Configuration` и может использовать `@ComponentScan`, `@Bean` и т.д..javarush+1
    
- Такой контекст подходит для консольных приложений, тестов, утилит.
    

## 2. Spring Boot (auto‑config)

- Точка входа:
    

java

`@SpringBootApplication public class App {     public static void main(String[] args) {        SpringApplication.run(App.class, args);    } }`

- `@SpringBootApplication` = `@Configuration + @EnableAutoConfiguration + @ComponentScan`.
    
- Boot сам поднимает `ApplicationContext`, выполняет автоконфигурацию, сканирует компоненты, поднимает встроенный сервер (Tomcat/Jetty/Undertow).javarush+1
    

Фраза:

> В Spring Boot контекст создаётся вызовом `SpringApplication.run(...)`. Аннотация `@SpringBootApplication` включает автоконфигурацию и сканирование, так что почти всегда ты получаешь готовый `ApplicationContext` без явного создания.itflashcards+1

## 3. В веб‑приложении: DispatcherServlet + WebApplicationContext

В классическом Spring MVC:

- На уровне сервлет‑контейнера регистрируется `DispatcherServlet` (через `web.xml` или `WebApplicationInitializer`).proselyte+1
    
- Для `DispatcherServlet` поднимается **отдельный `WebApplicationContext`**, обычно дочерний по отношению к `root ApplicationContext`.spring+2
    
    - `root`‑контекст — сервисы, репозитории, инфраструктура.
        
    - `WebApplicationContext` — web‑слой: контроллеры, view‑резолверы, handler mapping и т.п.
        

Фраза:

> В вебе Spring создаёт `WebApplicationContext`, связанный с `DispatcherServlet`. Обычно есть корневой контекст с сервисами/DAO и дочерний web‑контекст с контроллерами и MVC‑инфраструктурой. `DispatcherServlet` использует этот контекст как IoC‑контейнер для web‑слоя.docs.spring+3

Если хочешь, можем перейти к Spring MVC: `DispatcherServlet`, `HandlerMapping`, `Controller`, `ViewResolver`, и заодно провести параллель с тем, что ты уже разобрал по сервлетам.
