Циклическая зависимость (circular dependency) возникает, когда бин A зависит от бина B, а бин B в свою очередь зависит от бина A. Spring при создании контекста пытается разрешить зависимости и может упереться в бесконечную рекурсию.

**Главное правило:**  
- **Constructor injection** + circular dependency → `BeanCurrentlyInCreationException` **всегда**.  
- **Setter/field injection** с singleton-бинами Spring *может* разрешить автоматически (через кеширование ранних ссылок), но это **плохая практика**, которая часто ломается при добавлении прокси, `@Async`, `@Transactional` и т.п., а для prototype-бинов всё равно приводит к ошибке.

---

## 🧩 Способы решения

### 1. Рефакторинг (лучший путь)
Избавиться от цикла, введя третий класс или выделив общий интерфейс.

```java
// Вместо A -> B -> A
// делаем
@Component
public class A {
    private final SharedService shared;
    // ...
}
@Component
public class B {
    private final SharedService shared;
    // ...
}
@Service
public class SharedService {
    // общая логика
}
```

### 2. `@Lazy` – ленивая инициализация одного из бинов
Помечаем точку внедрения аннотацией `@Lazy`. Spring внедрит прокси, который отложит реальное получение бина до первого вызова метода.  
Работает и с конструктором, и с полем/сеттером.

```java
@Component
public class A {
    private final B b;
    public A(@Lazy B b) {   // <--- отложенная зависимость
        this.b = b;
    }
}
@Component
public class B {
    private final A a;
    public B(A a) {
        this.a = a;
    }
}
```

Можно также пометить сам бин `@Lazy` на уровне класса – тогда он не будет создаваться до первого запроса.

### 3. Переход на внедрение через сеттер / поле
Для простых singleton-бинов Spring кеширует незавершённые экземпляры и может разрулить цикл. Но это ненадёжно – при добавлении аспектов (транзакции, асинхронность) или скопов отличных от singleton всё ломается.

```java
@Component
public class A {
    private B b;
    @Autowired
    public void setB(B b) { this.b = b; }
}
@Component
public class B {
    private A a;
    @Autowired
    public void setA(A a) { this.a = a; }
}
```

### 4. Использование `ObjectProvider` / `Provider`
Позволяет получать зависимость вручную, когда она реально понадобится (например, внутри метода).

```java
@Component
public class A {
    private final ObjectProvider<B> bProvider;
    public A(ObjectProvider<B> bProvider) {
        this.bProvider = bProvider;
    }
    public void doSomething() {
        B b = bProvider.getIfAvailable(); // реальное получение
        // ...
    }
}
```

### 5. Разруливание через `@PostConstruct`
Логика, требующая обеих бинов, выносится из конструктора в метод, помеченный `@PostConstruct`. К этому моменту оба бина уже созданы.

```java
@Component
public class A {
    @Autowired
    private B b;

    @PostConstruct
    public void init() {
        b.register(this);
    }
}
```

### 6. Слияние классов
Если A и B настолько тесно связаны, что постоянно вызывают друг друга, возможно, их стоит объединить в один класс.

## 🛠 Что работает в XML-конфигурации
Аналогичные подходы. Например, атрибут `lazy-init="true"` или внедрение через `<property>` вместо `<constructor-arg>`:

```xml
<bean id="a" class="com.example.A">
    <property name="b" ref="b"/>
</bean>
<bean id="b" class="com.example.B">
    <property name="a" ref="a"/>
</bean>
```
Использование `lazy-init`:
```xml
<bean id="a" class="com.example.A" lazy-init="true">
    <constructor-arg ref="b"/>
</bean>
```

## 📌 Итоговая рекомендация
1. **Первое – пересмотрите дизайн.** Циклическая зависимость почти всегда симптом неудачной архитектуры.  
2. Если цикл неизбежен, **используйте `@Lazy`** на одном из конструкторных параметров – это самый безопасный способ сохранить конструкторное внедрение и избежать исключений.  
3. Избегайте полагаться на автоматическое разрешение через сеттеры – это бомба замедленного действия.
