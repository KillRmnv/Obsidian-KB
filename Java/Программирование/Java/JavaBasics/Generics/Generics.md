# Java SE — Шпаргалка: Generics (теория + подводные камни собесов)

***

## 1. Синтаксис дженериков

### Зачем нужны generics

Generics появились в Java 5 для обеспечения **type safety на этапе компиляции**. До generics коллекции работали с `Object`, и ошибки типов обнаруживались только в runtime через `ClassCastException`. Generics переносят эти ошибки на этап компиляции — компилятор проверяет совместимость типов и автоматически вставляет касты.[1][2]

### Виды параметризации

**Generic класс** — тип параметризуется на уровне класса. Параметр типа (`T`, `E`, `K`, `V` — конвенция именования) используется как тип полей, параметров методов и возвращаемых значений. Параметр действует внутри всего класса.

**Generic метод** — параметр типа объявляется на уровне метода (перед возвращаемым типом: `<T> T method(...)`). Может существовать в обычных, нестатических и статических методах. Тип выводится компилятором автоматически из аргументов (type inference) или указывается явно.

**Bounded type parameter** — ограничение параметра: `<T extends Number>` означает "T — это Number или его подкласс". Можно задать несколько границ: `<T extends Comparable<T> & Serializable>` (сначала класс, потом интерфейсы).[2]

### Инвариантность generics[3][4][5][6]

Generics в Java **инвариантны**: `List<String>` НЕ является подтипом `List<Object>`, даже если `String extends Object`. Это фундаментальное отличие от массивов (которые ковариантны). Инвариантность — намеренное решение для type safety: если бы `List<String>` был подтипом `List<Object>`, можно было бы добавить `Integer` в список строк, нарушив типобезопасность.

Три вида отношений:
- **Инвариантность** — `List<String>` и `List<Object>` несовместимы
- **Ковариантность** — `List<? extends T>`: можно только читать, тип — "T или подтип T"
- **Контравариантность** — `List<? super T>`: можно только писать, тип — "T или надтип T"

## 2. Wildcards: `?`, `? extends`, `? super`

### Unbounded Wildcard `<?>`[7][6][8][9]

`List<?>` означает "список неизвестного типа". Это **не то же самое**, что `List<Object>`:
- В `List<Object>` можно добавлять объекты любого типа
- В `List<?>` нельзя добавить **вообще ничего** (кроме `null`) — тип неизвестен, компилятор не может гарантировать совместимость
- `List<?>` принимает любой `List<T>`, тогда как `List<Object>` принимает только `List<Object>`

Используется, когда нужно обработать коллекцию независимо от её типа и добавление не требуется (например, метод `printAll(List<?> list)`).[9]

### Upper Bounded Wildcard `<? extends T>` — ковариантность[10][11][12][13][14]

`List<? extends Number>` — "список Number или любого его подкласса" (`Integer`, `Double`, `Long`...). Из такого списка можно **читать** элементы как `Number`. **Нельзя добавлять** ничего (кроме `null`), потому что компилятор не знает точный тип — `List<Integer>` или `List<Double>`? Добавление `Double` в `List<Integer>` недопустимо.

### Lower Bounded Wildcard `<? super T>` — контравариантность[11][12][13][14][10]

`List<? super Integer>` — "список Integer или любого его суперкласса" (`Number`, `Object`). В такой список можно **добавлять** `Integer` (и его подклассы) — они гарантированно совместимы с любым суперклассом. **Читать** можно только как `Object` — конкретный тип неизвестен.

### Принцип PECS (Producer Extends, Consumer Super)[12][15][13][11]

Правило Джошуа Блоха из "Effective Java" — мнемоника для выбора wildcard:

- **Producer Extends** — если коллекция **производит** (предоставляет) значения для чтения → `<? extends T>`
- **Consumer Super** — если коллекция **потребляет** (принимает) значения для записи → `<? super T>`

Практический смысл: используй максимально гибкую сигнатуру. Метод копирования элементов из `src` в `dst`: `src` — producer (читаем из него) → `<? extends T>`, `dst` — consumer (пишем в него) → `<? super T>`.

Если коллекция одновременно читается и пишется — используй точный тип `<T>` без wildcard.[13][11]

###  Подводные камни wildcards

**`List<?>` — нельзя добавлять элементы.** Единственное допустимое значение для добавления — `null`. Попытка добавить элемент вызовет ошибку компиляции.[7][9]

**`List<Object>` не принимает `List<String>`.** Это главный источник путаницы. Метод с параметром `List<Object>` не примет `List<String>` — нужен `List<?>` или `List<? extends Object>`.[6][9]

**`<?>` и `<? extends Object>` — почти одно и то же, но есть разница.** `List<?>` — reifiable type (можно использовать в `instanceof`), а `List<? extends Object>` — не reifiable.[8]

## 3. Type Erasure — стирание типов

### Что такое type erasure[16][17][1][2]

**Type erasure** — механизм, при котором компилятор **удаляет всю информацию о generic-типах** и заменяет параметры типов конкретными типами перед генерацией байт-кода. JVM не знает ничего о дженериках — в байт-коде `List<String>` и `List<Integer>` выглядят одинаково как просто `List`.

Generics существуют **только во время компиляции** — это чисто компиляторная конструкция.

### Правила erasure[17][1][2]

Компилятор выполняет три действия:
1. **Заменяет параметры типов** на их верхнюю границу (или `Object`, если граница не задана): `T` → `Object`, `T extends Number` → `Number`
2. **Вставляет явные касты** в местах, где результат используется как конкретный тип
3. **Генерирует bridge-методы** для сохранения полиморфизма

Поэтому `new T()` невозможен — в runtime JVM не знает, что такое `T`. `new ArrayList<String>()` — возможен, но информация о `String` стирается; в runtime это просто `new ArrayList()`.

### Bridge-методы[18][19][17][1]

Рассмотрим ситуацию: generic-класс `Node<T>` с методом `setData(T data)`. После erasure метод становится `setData(Object data)`. Дочерний класс `MyNode extends Node<Integer>` объявляет `setData(Integer data)`.

Проблема: с точки зрения JVM после erasure в родителе `setData(Object)`, а в потомке `setData(Integer)` — это **перегрузка**, а не переопределение. Полиморфизм сломан.

Решение: компилятор **автоматически генерирует bridge-метод** в `MyNode`:
`setData(Object data) { setData((Integer) data); }` — этот метод виден только в байт-коде, не в исходнике. Он восстанавливает цепочку переопределения. При передаче несовместимого типа через raw-ссылку bridge-метод бросает `ClassCastException`.[19][1]

### Heap Pollution[20][21][22][23]

**Heap pollution** — ситуация когда переменная параметризованного типа указывает на объект несовместимого типа. Возникает при смешивании raw types и generics, а также при использовании generic varargs. Компилятор предупреждает `unchecked warning`, но не блокирует. В runtime проявляется как `ClassCastException` в неожиданном месте — не там, где реальная ошибка.[23]

Аннотация `@SafeVarargs` подавляет предупреждение heap pollution для varargs-методов — используется, когда разработчик гарантирует, что тело метода не выполняет опасных операций с массивом varargs.[20]

###  Подводные камни type erasure

**Нельзя создать экземпляр через `new T()`.** В runtime `T` не существует. Обходной путь: передать `Class<T>` как параметр и создать через рефлексию.[24][25]

**Нельзя использовать `instanceof` с параметризованным типом.** `obj instanceof List<String>` не скомпилируется. Можно только `obj instanceof List<?>` или `obj instanceof List`.[24][16]

**Нельзя создать generic-массив.** `new T[10]` запрещён. Причина: массивы ковариантны и reifiable, generics — нет. Совместить их безопасно невозможно. Обходной путь: `(T[]) new Object[10]` с подавленным предупреждением или использовать `ArrayList<T>`.[25][24]

**Overloading по generic-параметру невозможен.** Методы `void process(List<String> list)` и `void process(List<Integer> list)` — ошибка компиляции, потому что после erasure обе сигнатуры превращаются в `void process(List list)`.[17][24]

**Raw types обходят type safety.** Использование `List` вместо `List<T>` отключает все проверки компилятора. Unchecked предупреждения — серьёзный сигнал, не стоит их игнорировать. Raw types — legacy, нужны только для совместимости с кодом до Java 5.[21][7]

**`getClass()` возвращает `Class<? extends T>`, не `Class<T>`.** Реальный объект может быть подклассом.[15]
