## 1. Lambda-выражения

### Что такое лямбда[1][2]

Lambda — **анонимная функция**: блок кода без имени, который можно передать как аргумент, сохранить в переменной или вернуть из метода. Лямбда — синтаксический сахар над **анонимным классом**, реализующим функциональный интерфейс. Компилятор не создаёт отдельный `.class` файл; лямбды реализованы через `invokedynamic` — механизм JVM, добавленный в Java 7.

Синтаксис: `(параметры) -> тело`. Скобки можно опустить при одном параметре, фигурные скобки — при однострочном теле с implicit return.

### Захват переменных (Variable Capture)[3][4][1]

Лямбда может захватывать переменные внешнего скоупа трёх видов:
- **Статические поля** — свободно, без ограничений
- **Instance-поля** — свободно через неявный `this`
- **Локальные переменные** — **только effectively final**

**Effectively final** — переменная, значение которой никогда не меняется после инициализации (компилятор не жаловался бы, если добавить `final`). Явного ключевого слова `final` не нужно.

**Почему это ограничение?** Локальные переменные хранятся на стеке, а лямбда может жить дольше (например, передана в другой поток). JVM не может дать лямбде ссылку на стековый фрейм — она **копирует** значение. Если бы лямбда могла изменять локальную переменную, а поток-источник мог бы это видеть — возникла бы гонка данных.[4][1]

###  Подводные камни

**`this` в лямбде ≠ `this` в анонимном классе.** В анонимном классе `this` — сам анонимный класс. В лямбде `this` — **внешний класс**, в котором написана лямбда. Лямбда не создаёт новый скоуп для `this`.

**Лямбда не может изменять захваченную локальную переменную** — даже через обёртку. Обход через массив `int[] counter = {0}; () -> counter[0]++` — технически работает, но это антипаттерн: нарушает принцип чистоты функции и небезопасно в параллельной среде.[3]

## 2. Функциональные интерфейсы

### Определение[5][6][7]

**Функциональный интерфейс** — интерфейс ровно с **одним абстрактным методом** (SAM — Single Abstract Method). Может содержать любое количество `default` и `static` методов. Аннотация `@FunctionalInterface` — необязательна, но помогает компилятору выдать ошибку при случайном добавлении второго абстрактного метода.

Любой SAM-интерфейс является функциональным — даже без аннотации (`Runnable`, `Comparator`, `Callable`).

### Четыре ключевых интерфейса `java.util.function`[6][8][9][7][5]

| Интерфейс | Метод | Принимает | Возвращает | Использование |
|---|---|---|---|---|
| `Predicate<T>` | `test(T t)` | T | `boolean` | Условие / фильтрация |
| `Function<T, R>` | `apply(T t)` | T | R | Преобразование типа |
| `Consumer<T>` | `accept(T t)` | T | `void` | Действие с побочным эффектом |
| `Supplier<T>` | `get()` | — | T | Фабрика / ленивое создание |

**Predicate** — тест условия. Методы композиции: `and()`, `or()`, `negate()`. `Predicate.not()` (Java 11) — отрицание через метод-ссылку.

**Function** — преобразование T → R. Методы: `andThen(after)` (выполнить после), `compose(before)` (выполнить до). `UnaryOperator<T>` — частный случай, когда T = R. `BiFunction<T, U, R>` — два входных параметра.

**Consumer** — потребление без возврата. Методы: `andThen()` для цепочки. `BiConsumer<T, U>` — два параметра. `forEach()` в коллекциях принимает `Consumer`.

**Supplier** — поставка без входного параметра. Ключевое применение: **ленивая инициализация** — передаём Supplier туда, где значение может не понадобиться, и вычисляем только по запросу. `Optional.orElseGet(Supplier)` vs `orElse(value)`.

### Специализированные примитивные интерфейсы[8][6]

`IntPredicate`, `LongFunction`, `DoubleConsumer`, `IntSupplier` и т.д. Существуют, чтобы избежать autoboxing — boxing/unboxing влияет на производительность в интенсивных вычислениях.

###  Подводные камни

**`Function.compose()` vs `Function.andThen()` — порядок обратный.** `f.andThen(g)` → `g(f(x))`. `f.compose(g)` → `f(g(x))`. Легко перепутать.

**Функциональные интерфейсы не обязаны быть `@FunctionalInterface`** — любой SAM-интерфейс работает с лямбдами. Например, `Runnable` не помечен `@FunctionalInterface`, но лямбда `() -> {}` допустима.

## 3. Stream API

### Что такое Stream[10][11][12][13]

Stream — **последовательность элементов для декларативной обработки данных**. Stream **не хранит данные** — он их обрабатывает из источника (коллекция, массив, I/O, генератор). Stream **не модифицирует источник** — каждая операция создаёт новый поток.

Stream **нельзя переиспользовать**: после вызова терминальной операции поток закрыт. Повторное использование — `IllegalStateException`.

### Lazy Evaluation — главный принцип работы[14][11][15][16][10]

**Промежуточные операции (Intermediate)** — ленивые. Вызов `filter()`, `map()`, `sorted()` сам по себе **ничего не делает** — создаёт новый Stream с описанием операции. Реальная обработка начинается только при вызове терминальной операции. Это позволяет JVM оптимизировать pipeline: объединять операции, не создавать промежуточные коллекции.

**Терминальные операции (Terminal)** — запускают выполнение pipeline. Возвращают не Stream, а результат или побочный эффект. После вызова поток "потреблён".

### Intermediate vs Terminal операции[15][12]

| Тип | Примеры | Lazy? | Возвращает |
|---|---|---|---|
| **Промежуточные (stateless)** | `filter`, `map`, `flatMap`, `peek` |  Да | Stream |
| **Промежуточные (stateful)** | `sorted`, `distinct`, `limit`, `skip` |  Да, но требуют весь input | Stream |
| **Short-circuit** | `limit`, `findFirst`, `anyMatch`, `takeWhile` |  Да | Зависит |
| **Терминальные** | `collect`, `forEach`, `reduce`, `count`, `findFirst` |  Eager | Результат |

**Stateful vs Stateless операции:**
- **Stateless** (`filter`, `map`) — обрабатывают каждый элемент независимо, не хранят состояние. Идеально для параллельных потоков.
- **Stateful** (`sorted`, `distinct`) — требуют обработать **весь** входной поток перед выдачей результата. `sorted()` не может вернуть первый элемент, не увидев все остальные.[16][13]

**Short-circuit операции** завершают обработку досрочно, не просматривая весь поток. `anyMatch` останавливается на первом совпадении, `limit(n)` — после n элементов.[17][12]

### flatMap vs map

`map()` — преобразует каждый элемент в один другой:  Stream\<T> → Stream\<R>.
`flatMap()` — преобразует каждый элемент в Stream, затем "плющит" все стримы в один: Stream <List\<T>> → Stream\<T>.  Ключевое применение: работа с вложенными коллекциями.


### Parallel Streams[11][12]

`parallelStream()` / `.parallel()` — разбивает поток на части и обрабатывает через `ForkJoinPool.commonPool()` параллельно. Не всегда быстрее: накладные расходы на разбиение и объединение результатов оправданы только для больших объёмов данных. Stateful операции (`sorted`, `distinct`) плохо параллелизуются — требуют синхронизации. Лямбды в parallel stream должны быть **stateless и non-interfering**.[12]

###  Подводные камни Stream API

**Stream не переиспользуется.** После терминальной операции — закрыт. `IllegalStateException: stream has already been operated upon or closed`.

**`peek()` — только для отладки.** Семантически — промежуточная операция с побочным эффектом. При оптимизации компилятор может не вызвать `peek()` (например, после short-circuit). Нельзя полагаться на `peek()` для реальной логики.

**`forEach` не гарантирует порядок для parallel stream.** Используй `forEachOrdered()` если порядок важен.

**`collect(Collectors.toList())` vs `.toList()` (Java 16+).** `.toList()` возвращает **неизменяемый** список, `Collectors.toList()` — изменяемый `ArrayList`. Важное различие!

**Бесконечные потоки** (`Stream.iterate()`, `Stream.generate()`) — требуют терминатора (`limit()`, `takeWhile()`), иначе бесконечный цикл.

## 4. Method References — ссылки на методы

### Четыре типа[18][19][20][21][22]

| Тип | Синтаксис | Lambda-эквивалент |
|---|---|---|
| Статический метод | `ClassName::staticMethod` | `(args) -> ClassName.staticMethod(args)` |
| Метод конкретного экземпляра | `instance::instanceMethod` | `(args) -> instance.instanceMethod(args)` |
| Метод произвольного экземпляра данного типа | `ClassName::instanceMethod` | `(obj, args) -> obj.instanceMethod(args)` |
| Конструктор | `ClassName::new` | `(args) -> new ClassName(args)` |

**Тип 3 — самый неочевидный.** `String::toLowerCase` — первый аргумент становится получателем метода: `(s) -> s.toLowerCase()`. JVM сама поймёт, что `s` — это `String`. Используется в `sorted(String::compareTo)`, `map(String::toUpperCase)`.

###  Подводные камни

**Method reference может скрывать NPE.** `list.stream().map(obj::method)` — если `obj` равен `null`, получишь NPE только при запуске стрима, а не при создании ссылки.

**Тип 3 vs тип 2 легко перепутать.** `instance::method` захватывает конкретный объект. `Class::method` принимает объект первым параметром. Разная семантика при использовании в параллельных стримах.

## 5. Optional

### Что такое Optional и зачем[23][24][25][26][27]

`Optional<T>` — контейнер, который может содержать значение или быть пустым. Предназначен **только для возвращаемых типов методов** — как явный сигнал вызывающему коду, что результат может отсутствовать. Цель: заставить разработчика явно обработать случай "нет значения", вместо тихого NPE.

По словам Brian Goetz (автора): Optional — это **не аналог Haskell Maybe/Scala Option** для всеобщего применения. Это узкоспециализированный инструмент для возвращаемых значений.[24]

### Ключевые методы[26][23]

- `Optional.of(value)` — создать с non-null значением; NPE если null
- `Optional.ofNullable(value)` — создать с возможным null
- `Optional.empty()` — пустой Optional
- `isPresent()` / `isEmpty()` (Java 11) — проверка
- `get()` — получить значение; `NoSuchElementException` если пусто
- `orElse(default)` — значение или дефолт
- `orElseGet(Supplier)` — значение или результат Supplier (ленивый)
- `orElseThrow(Supplier)` — значение или бросить исключение
- `map(Function)` — преобразовать если есть значение
- `flatMap(Function)` — преобразовать, если Function тоже возвращает Optional
- `filter(Predicate)` — обнулить если не прошло условие
- `ifPresent(Consumer)` — выполнить если есть значение

###  Антипаттерны Optional[25][27][23][24][26]

**Optional как поле класса** — антипаттерн. `Optional` не реализует `Serializable`. JPA, Jackson без доп. конфигурации не работают с Optional-полями. Каждый Optional — лишний объект для GC. Правильно: поле `null`, getter возвращает `Optional.ofNullable(field)`.[27][23]

**Optional как параметр метода** — антипаттерн. Вынуждает вызывающий код оборачивать значения в Optional. Правильно: два метода с/без параметра, или явная проверка на null внутри.

**`optional.get()` без `isPresent()`** — равноценно `null.field` по риску. Нивелирует смысл Optional.

**`orElse()` vs `orElseGet()`** — критическое различие. `orElse(createExpensiveObject())` вычислит `createExpensiveObject()` **всегда**, даже если Optional непуст. `orElseGet(() -> createExpensiveObject())` вычислит только если Optional пуст. При дорогих операциях (запросы в БД, сетевые вызовы) всегда `orElseGet`.[26]

**`Optional<List<T>>`** — всегда лишнее. Пустой список уже выражает "нет элементов". `Optional` поверх коллекции — двойная "необязательность".[23]

**`isPresent()` + `get()` вместо `map()`/`ifPresent()`** — нарушает функциональный стиль. Если нужна трансформация — используй `map()`. Если нужно действие — `ifPresent()`. Длинная цепочка `if(opt.isPresent()) { T val = opt.get(); ... }` — именно то, от чего Optional должен избавлять.

### Итоговая таблица: где Optional применять

| Сценарий | Рекомендация |
|---|---|
| Возвращаемый тип метода |  Да |
| Поле класса |  Нет |
| Параметр метода |  Нет |
| Тип в коллекции (`List<Optional<T>>`) |  Нет |
| `Optional<Collection<T>>` |  Нет — верни пустую коллекцию |
