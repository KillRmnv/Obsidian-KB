# Java SE — Шпаргалка: Многопоточность (Concurrency)

***

## 1. Thread, Runnable, Callable

### Thread

Класс `Thread` — прямое представление потока ОС в JVM. Жизненный цикл потока: `NEW → RUNNABLE → BLOCKED/WAITING/TIMED_WAITING → TERMINATED`.[1]

Создать поток можно двумя путями: расширить `Thread` и переопределить `run()`, либо передать `Runnable` в конструктор `Thread`. Второй вариант предпочтительнее — разделяет задачу и механизм выполнения.[2]

Важные методы: `start()` — запускает поток (нельзя вызвать дважды, иначе `IllegalThreadStateException`). `run()` — тело задачи (вызов напрямую выполнит код в текущем потоке, без нового). `join()` — ждать завершения потока. `sleep()` — статический, усыпляет **текущий** поток. `interrupt()` — устанавливает флаг прерывания, не убивает поток принудительно.[1]

### Runnable vs Callable[3][4][5][6][2]

| | `Runnable` | `Callable<V>` |
|---|---|---|
| Пакет | `java.lang` | `java.util.concurrent` |
| Метод | `run()` | `call()` |
| Возвращает | `void` | `V` (generic тип) |
| Бросает checked exception | ❌ | ✅ |
| Запуск через `Thread` | ✅ | ❌ (только через `ExecutorService`) |
| Результат через | — | `Future<V>` |

**Runnable** — "fire and forget": запустить и забыть, результат не нужен. **Callable** — когда нужен результат или важна обработка исключений.[5]

### ⚠️ Подводные камни

**`thread.run()` вместо `thread.start()`** — код выполнится в **текущем** потоке синхронно. Новый поток не создаётся. Классическая ошибка новичка.

**`start()` дважды** — `IllegalThreadStateException`. Поток нельзя "перезапустить".

## 2. Java Memory Model: synchronized и volatile

### Java Memory Model (JMM)[7][8][9]

JMM определяет, **когда изменения, сделанные одним потоком, становятся видны другим**. Без синхронизации JVM может кешировать значения в регистрах или CPU-кэше — другие потоки видят устаревшие данные. JMM вводит понятие **happens-before**: если операция A happens-before операции B, то все изменения памяти от A видны B.

Два ключевых понятия проблем многопоточности:
- **Visibility (видимость)** — поток не видит изменений, сделанных другим потоком
- **Atomicity (атомарность)** — операция может быть прервана между своими шагами (например, `count++` — это три шага: read, increment, write)

### volatile[10][8][9][11][7]

`volatile` решает **только visibility**. Чтение/запись volatile-переменной всегда идёт напрямую в основную память (Main Memory), минуя CPU-кэш. Все записи до volatile-записи видны потоку, читающему это volatile-поле (happens-before гарантия).

**`volatile` НЕ гарантирует atomicity.** `volatile int count; count++` — по-прежнему три нeатомарных шага. Volatile подходит для **флагов** и **однократно публикуемых ссылок** (double-checked locking паттерн).

### synchronized[8][9][11][10]

`synchronized` гарантирует одновременно **visibility + atomicity + ordering**. Только один поток может выполнять synchronized-блок/метод, владея монитором объекта. При входе — сброс кэша из памяти. При выходе — сброс кэша в память.

Каждый объект в Java имеет встроенный монитор (intrinsic lock, mutex). `synchronized(obj)` — захват монитора `obj`. `synchronized` на instance-методе — монитор `this`. `synchronized` на static-методе — монитор `Class`-объекта.

**Реентерабельность:** поток, уже владеющий монитором, может повторно войти в synchronized-блок на том же объекте без дедлока.[12]

| | `volatile` | `synchronized` |
|---|---|---|
| Visibility | ✅ | ✅ |
| Atomicity | ❌ (только одиночные read/write) | ✅ |
| Blocking | Никогда | Может блокировать |
| Использование | Флаги, опубликованные ссылки | Сложные операции со state |

### ⚠️ Подводные камни

**Двойная проверка блокировки (Double-Checked Locking) без volatile — сломана.** В JMM без `volatile` JIT может переупорядочить инициализацию объекта и публикацию ссылки. Другой поток может увидеть ненулевую ссылку на не полностью инициализированный объект. Решение: `private volatile static Singleton instance`.[8]

**synchronized не наследуется.** Если переопределить synchronized-метод в дочернем классе без `synchronized` — метод больше не синхронизирован.

## 3. wait() / notify() / notifyAll()

### Механизм[13][14][15][16][17]

Методы класса `Object` для **межпоточной коммуникации**. Используются в паттерне Producer-Consumer.

- `wait()` — поток **освобождает монитор** и переходит в состояние WAITING. Пробуждается по `notify()`/`notifyAll()` или по таймауту.
- `notify()` — будит **один случайный** поток из waiting-очереди данного объекта.
- `notifyAll()` — будит **все** ожидающие потоки; из них один получит монитор, остальные снова встанут в очередь.

**Все три метода можно вызывать ТОЛЬКО внутри synchronized-блока** на том же объекте. Иначе — `IllegalMonitorStateException`. Причина: `wait()` освобождает монитор — нельзя освободить то, чем не владеешь.[14][17]

### ⚠️ Подводные камни

**Spurious wakeup (ложное пробуждение).** Поток может проснуться из `wait()` без вызова `notify()` — это допустимо по спецификации JVM. Поэтому `wait()` **всегда** оборачивается в `while` (не `if`) с проверкой условия.[16][13]

**`notify()` vs `notifyAll()`:** `notify()` безопасен только если все ожидающие потоки взаимозаменяемы (ожидают одно и то же условие). Если есть разные условия ожидания — `notify()` может разбудить "не тот" поток, и все потоки зависнут. `notifyAll()` безопаснее, но дороже.[13][16]

## 4. java.util.concurrent: ExecutorService, Future, Locks

### ExecutorService[18][19][20]

Абстракция над пулом потоков. Скрывает создание/управление потоками. Основные реализации через фабрику `Executors`:
- `newFixedThreadPool(n)` — фиксированный пул из n потоков
- `newCachedThreadPool()` — неограниченный пул, потоки живут 60с без задач
- `newSingleThreadExecutor()` — один поток, задачи в очереди
- `newScheduledThreadPool(n)` — с возможностью планирования по таймеру

Методы: `execute(Runnable)` — без результата. `submit(Callable)` / `submit(Runnable)` — возвращает `Future`. `shutdown()` — мягкое завершение (дождаться текущих задач). `shutdownNow()` — попытка немедленной остановки. `awaitTermination()` — заблокировать до завершения.[20]

### Future[19][18][20]

Placeholder для результата асинхронной задачи. `get()` — **блокирующий** вызов до получения результата. `get(timeout, unit)` — с таймаутом. `isDone()` — завершена ли задача. `cancel(mayInterruptIfRunning)` — отмена.

**`Future.get()` блокирует вызывающий поток** — это ключевое ограничение. Для неблокирующей работы — `CompletableFuture`.[20]

### CompletableFuture (Java 8+)[21][18][19][20]

Расширяет `Future`. Поддерживает **неблокирующие цепочки операций**. `thenApply()` — преобразовать результат. `thenAccept()` — потребить. `thenCombine()` — объединить два будущих результата. `exceptionally()` — обработать исключение. По умолчанию использует `ForkJoinPool.commonPool()`.

`ExecutorService` управляет пулом потоков. `CompletableFuture` управляет **async-пайплайном** (что делать после завершения). В реальных приложениях их часто комбинируют.[18][20]

### ReentrantLock vs synchronized[22][23][24][12]

| Характеристика | `synchronized` | `ReentrantLock` |
|---|---|---|
| Автоматическое освобождение | ✅ (даже при exception) | ❌ (нужен `try-finally`) |
| `tryLock()` (без блокировки) | ❌ | ✅ |
| Прерываемое ожидание | ❌ | ✅ (`lockInterruptibly()`) |
| Политика справедливости | ❌ | ✅ (`new ReentrantLock(true)`) |
| Несколько условий | ❌ (одно) | ✅ (`Condition`) |
| Память | 8 байт (object header) | ~48 байт (AQS) |

**`ReentrantLock` всегда нужен `try-finally`** — иначе при исключении лок не освободится и всё зависнет.[22][12]

## 5. Атомарные классы

### CAS — Compare-And-Swap[25][26][27][28][29]

**CAS** — атомарная CPU-инструкция: "если текущее значение равно ожидаемому — замени на новое, иначе — не трогай, верни false". Выполняется **за один неделимый шаг** на уровне железа — без блокировок (lock-free).

Алгоритм: `CAS(location, expected, new)` → если `*location == expected` → `*location = new` и вернуть `true`, иначе `false`. При неудаче — повторить (spin loop).

### Atomic-классы (`java.util.concurrent.atomic`)[26][29][25]

`AtomicInteger`, `AtomicLong`, `AtomicBoolean`, `AtomicReference<V>` — обёртки над volatile-переменными с CAS-операциями. Реализованы через `Unsafe` (прямой доступ к памяти) или VarHandles (Java 9+).

Ключевые методы `AtomicInteger`: `get()`, `set()`, `getAndIncrement()`, `incrementAndGet()`, `compareAndSet(expected, newValue)`, `getAndAdd(delta)`.

**AtomicInteger внутри:** хранит `volatile int value`. `incrementAndGet()` делает CAS-петлю: читает текущее, вычисляет новое, пробует CAS — если неудача (кто-то изменил между чтением и CAS) — повторяет. Намного легче `synchronized` при низком и среднем contention.[29][25]

### ⚠️ Подводные камни

**ABA-проблема:** поток читает значение A, другой меняет A→B→A, первый поток делает CAS, видит A и "успешно" заменяет — но промежуточное изменение потеряно. Решение: `AtomicStampedReference` — добавляет счётчик версий.[27]

**AtomicReference не защищает поля объекта** — только саму ссылку. Если поля объекта изменяемы, AtomicReference не поможет.

## 6. ThreadLocal[30][31][32][33][34][35][36][37]

### Механизм

`ThreadLocal<T>` предоставляет каждому потоку **свою копию переменной**. Внутри каждый объект `Thread` содержит `ThreadLocalMap` — хэш-карту, где ключ — `ThreadLocal`-объект (weak reference), значение — данные потока (strong reference).

`set(value)` — записывает в карту текущего потока. `get()` — читает из карты текущего потока. `remove()` — удаляет из карты. `withInitial(Supplier)` — фабричный метод с инициализатором.

**Применение:** хранение текущего пользователя/транзакции/соединения в request-scoped контексте без передачи через параметры. Spring's `SecurityContextHolder`, Hibernate's `Session`, MDC в логировании — всё построено на `ThreadLocal`.[32]

### ⚠️ Утечка памяти — главная ловушка[31][33][34][35][36][37][30][32]

**Проблема:** ключ в `ThreadLocalMap` — **weak reference** на `ThreadLocal`-объект. Значение — **strong reference**. При GC: если `ThreadLocal`-объект собран (ключ обнулился), значение остаётся в карте как "ghost entry" — ключ null, значение живёт.

В **thread pool** (Tomcat, Spring, любой ExecutorService) потоки не умирают — они переиспользуются. `ThreadLocalMap` живёт всё время жизни потока. Если не вызвать `remove()` — объекты накапливаются бесконечно → медленный `OutOfMemoryError`, крайне сложный для диагностики.

**Правило:** всегда вызывать `threadLocal.remove()` в `finally`-блоке по завершении работы с потоком. В Spring это делают автоматически Filter'ы и Interceptor'ы.[35][31][32]

## 7. Проблемы многопоточности

### Race Condition[38][39][1]

Несколько потоков обращаются к разделяемому ресурсу без синхронизации, результат зависит от порядка выполнения (нарушение atomicity). Пример: два потока инкрементируют счётчик — итог непредсказуем. Решение: `synchronized`, `AtomicInteger`, `Lock`.

### Deadlock[39][40][38]

Два или более потоков бесконечно ждут ресурсы, удерживаемые друг другом. **4 условия Коффмана** (все должны быть выполнены одновременно):
1. **Mutual exclusion** — ресурс используется одним потоком
2. **Hold and wait** — поток держит ресурс и ждёт другой
3. **No preemption** — ресурс нельзя принудительно отобрать
4. **Circular wait** — цикл ожидания между потоками

**Методы предотвращения:** всегда захватывать блокировки в **одном и том же порядке**. Использовать `tryLock()` с таймаутом. Алгоритм банкира.[40][38]

### Livelock[41][39][40]

Потоки не заблокированы (в отличие от deadlock), но постоянно реагируют на действия друг друга, не продвигаясь вперёд. Аналог: два человека в коридоре уступают дорогу друг другу бесконечно. Потоки "живые" с точки зрения CPU, но полезной работы не делают.[41]

### Starvation (голодание)[38][39]

Поток постоянно не получает доступа к ресурсу из-за приоритетов или несправедливого планировщика. Высокоприоритетные потоки монополизируют процессор, низкоприоритетные ждут бесконечно. Решение: fair lock `new ReentrantLock(true)`.[38]

### Memory Consistency Error[7][39]

Поток видит устаревшее значение разделяемой переменной из-за кэширования CPU. Решение: `volatile` для видимости, `synchronized`/`Lock` для полной согласованности.[7]

### Итоговая таблица инструментов синхронизации

| Проблема | Инструмент |
|---|---|
| Visibility (видимость флага) | `volatile` |
| Atomicity простых операций | `AtomicInteger`, `AtomicReference` |
| Атомарность сложных операций | `synchronized`, `ReentrantLock` |
| Межпоточная коммуникация | `wait()`/`notify()`, `BlockingQueue` |
| Управление пулом потоков | `ExecutorService` |
| Async-цепочки без блокировок | `CompletableFuture` |
| Thread-local состояние | `ThreadLocal` (+ `remove()` в finally!) |
| Deadlock prevention | Единый порядок лок, `tryLock()` |
| Starvation prevention | `ReentrantLock(true)` (fair) |
