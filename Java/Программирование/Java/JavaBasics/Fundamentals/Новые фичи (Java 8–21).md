## `var` (Java 10)

Локальная **type inference**: компилятор сам выводит тип по правой части.

- Работает только для:
    
    - локальных переменных в методах/блоках;
        
    - переменных цикла `for`;
        
    - локальных переменных в `try-with-resources`.
        
- Не работает для:
    
    - полей класса;
        
    - параметров методов/конструкторов;
        
    - возвращаемых типов методов;
        
    - лямбда-параметров (кроме специальных случаев в более новых версиях).
        

Идея:

- `var` **не** динамический тип. Тип фиксируется при компиляции и ничем не отличается от явного объявления.
    
- Это инструмент улучшения читаемости, а не "магия".
    

Подводные моменты для собеса:

- `var x = null;` — нельзя: тип не выводится. Нужно явное приведение.
    
- Правило читаемости: если правая часть слишком сложная, `var` делает код _хуже_. Особенно, когда тип важен для понимания (например, `Map<String, List<Order>>` лучше явно).
    
- `var` + diamond (`var list = new ArrayList<String>();`) — тип всё равно конкретный, не raw.

## Records (Java 16)

Records — это **сжатый синтаксис для неизменяемых "data carriers"**. Концептуально:

- Класс автоматически получает:
    
    - `private final` поля для компонентов;
        
    - конструктор со всеми полями;
        
    - `equals`/`hashCode`/`toString`;
        
    - accessors с именами компонентов (не `getX`, а `x()`).
        

Смысл: выразить **значение** (value type), а не сущность с идентичностью.

Ограничения:

- Record **не может**:
    
    - `extends` другой класс (кроме `java.lang.Record`);
        
    - быть `abstract`.
        
- Может:
    
    - реализовывать интерфейсы;
        
    - иметь static поля/методы;
        
    - иметь дополнительные instance-методы;
        
    - иметь _compact constructor_ с валидацией.
        

Типичный use-case:

- DTO, value objects, ключи в картах (иммутабельность + корректный equals/hashCode).
    
- Параметры конфигурации, где важно сравнение по содержимому.
    

Подводные камни:

- **Shallow immutability**: если компонента — `List`, то сам список можно менять; иммутабельность только на уровне ссылок.
    
- Records плохо ложатся на JPA/Hibernate:
    
    - нужен no-arg конструктор;
        
    - mutable поля;
        
    - проксирование. Это противоречит сути record.
        
- Accessor-методы называются `x()`, а не `getX()` → не всегда совпадает с JavaBeans- и библиотечными ожиданиями.

## Sealed classes (Java 17)

Sealed-классы/интерфейсы — способ _ограничить_ иерархию наследования.

Идея:

- Объявляешь:
    
    - `sealed interface Shape permits Circle, Rectangle, Square`.
        
- Каждый наследник **обязан** сам быть либо:
    
    - `final` (ветвь закрыта),
        
    - `sealed` (продолжает ограниченную иерархию),
        
    - `non-sealed` (снимает ограничение дальше).
        

Цели:

- **Закрытый набор вариантов** → удобно для pattern matching и исчерпывающих switch'ей.
    
- Более строгая модель домена: нельзя "втихаря" добавить новый подтип в другом модуле.
    

Практическое применение:

- Реализация "sum types" (как enum, но с разной структурой данных для вариантов).
    
- Доменная модель: тип сообщений, состояний, команд.
    

Собес-аспект:

- Разница с `final`: `final` запрещает _любое_ наследование, `sealed` ограничивает _конкретным списком_.
    
- Хорошо сочетается с pattern matching `switch`: можно получить компилятор проверяет исчерпываемость вариантов (как с enum'ами).

## Pattern matching для `instanceof`

Расширенный `instanceof`:

До: нужно было:

- проверить тип через `instanceof`;
    
- сделать явный cast;
    
- использовать переменную.
    

Теперь:

- pattern matching позволяет одновременно:
    
    - проверить тип;
        
    - _привязать_ переменную нужного типа.
        

Поведение:

- Компилятор гарантирует, что внутри branch переменная уже **узкого типа** — меньше кастов, меньше NPE.
    
- Работает с объединением условий (`if (obj instanceof String s && !s.isEmpty())`).
    

Главная ценность в сочетании с:

- sealed-классами;
    
- `switch` выражениями (pattern matching в `switch` развивается дальше в новых Java).

## Text blocks

Text blocks — это многострочные строковые литералы с тройными кавычками, предназначенные для:

- JSON, XML, SQL;
    
- многострочных сообщений/шаблонов.
    

Особенности:

- Обрабатывают отступы: ведущие отступы можно выровнять по внешнему коду, а реальная строка будет "подчищена".
    
- Не нужно экранировать кавычки и большинство спецсимволов.
    
- Результат всё равно `String`.
    

Подводные вещи:

- Поведение по пробелам и переносам: Java определяет "минимальный общий отступ" всех строк и убирает его — нужно понимать, как это влияет на реальные данные.
    
- Хорошо смотрится с SQL/JSON, особенно вместе с `String::formatted` или `MessageFormat`.

## Virtual threads (Java 21)

Самое "горячее" для собесов сейчас — виртуальные потоки (Project Loom).

Суть:

- Виртуальный поток — это **легковесный** поток, управляемый JVM, а не напрямую ОС.
    
- Их можно создавать **десятки тысяч**, даже миллионы, без огромных затрат (в отличие от платформенных потоков).
    

Модель:

- Виртуальные потоки мультиплексируются поверх малого количества **платформенных** потоков.
    
- Блокирующие операции (I/O, работа с сокетами), если корректно интегрированы, не "блокируют" платформенный поток: JVM "паркует" виртуальный поток и освобождает носитель.
    

Цели:

- Вернуться к **простому блокирующему стилю** программирования (как обычный `Thread.sleep`, `socket.read`), но при этом масштабироваться как реактивные/async решения.
    
- Упростить отладку и стек-трейсы: обычные стек-трейсы, без "адских" цепочек callbacks и futures.
    

Собес-углы:

- Отличие от потоков платформы:
    
    - платформенные (carrier threads) ограничены десятками/сотнями;
        
    - виртуальных можно много, они дешевле по памяти и переключениям.
        
- Конкурентные примитивы:
    
    - традиционные блокирующие API (synchronized, locks) в целом работают, но нужно понимать, как они взаимодействуют с паркингом/распаркингом виртуальных потоков;
        
    - некоторые старые или нативные блокирующие части могут "отменять" преимущества (если JVM не умеет распарковать).
        
- В ECOSYSTEM:
    
    - Aim — убрать давление "обязательно переходить на реактивщину" ради масштабируемости.
        
    - Но не всё из библиотек ещё идеально подружено с Loom, надо понимать зрелость.
