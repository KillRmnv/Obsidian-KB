### 1. Сегменты памяти и структура процесса

Память скомпилированной C++ программы разделена на несколько четких логических сегментов:

  

```
+-----------------------------------+ High Addresses
| Stack (Стек)                      |  | Растет вниз
|   ...                             |  v
|   v                               |
|                                   |
|   ^                               |
|   |                               |  ^
| Heap (Куча)                       |  | Растет вверх
+-----------------------------------+
| BSS (Uninitialized Data)          | Global/static = 0 по умолчанию
+-----------------------------------+
| Data (Initialized Data)           | Global/static с начальными значениями
+-----------------------------------+
| Text / Code (ROData)              | Машинные инструкции + строковые литералы (Read-Only)
+-----------------------------------+ Low Addresses
```

- **Stack (Стек):**
    
      
    - Очень быстрая память (управление сводится к сдвигу указателя стека `RSP`).
        
          
        
    - Фиксированный размер (обычно 1–8 МБ в зависимости от ОС). Превышение вызывает **Stack Overflow**.
        
          
        
    - Хранит локальные переменные, фреймы функций, адреса возврата. Память освобождается автоматически при выходе из области видимости (`LIFO`).
        
          
        
- **Heap (Куча):**
    
      
    - Динамическая память огромного объема, ограниченная лишь RAM и виртуальной памятью ОС.
        
          
        
    - Медленное выделение/освобождение (поиск свободного блока аллокатором ОС).
        
          
        
    - Выделяется вручную через `malloc`/`new`, освобождается через `free`/`delete`. Риск фрагментации памяти и утечек.
        
          
        
- **BSS & Data:** Хранят глобальные и статические переменные (`static`). BSS обнуляется до старта `main()`.
    
      
    
- **Text / ROData:** Инструкции программы и константы (включая строковые литералы). Защищен от записи на уровне страниц памяти ОС.
    
      
    

### 2. Неопределенное поведение (UB) и категории поведения

C++ строго разграничивает виды некорректного или специфичного кода:

  

- **Undefined Behavior (UB, Неопределенное поведение):**
    
      
    - Стандарт **ничего** не гарантирует. Компилятор имеет право считать, что UB никогда не произойдет, и в процессе оптимизации просто «вырезать» проверки или деформировать логику.
        
          
        
    - _Примеры:_ Разыменование `nullptr` или «висячего» указателя (dangling pointer), выход за границы массива, `Data Race`, переполнение **знакового** целого (`signed overflow`), чтение неинициализированной памяти, повторное освобождение (`double free`).
        
          
        
- **Unspecified Behavior (Непредусмотренное поведение):**
    
      
    - Компилятор выбирает один из нескольких допустимых вариантов реализации, но не обязан его документировать.
        
          
        
    - _Пример:_ Порядок вычисления аргументов функции (`foo(a(), b())`).
        
          
        
- **Implementation-defined Behavior:**
    
      
    - Поведение зависит от конкретной реализации компилятора и целевой платформы, но **обязано быть задокументировано**.
        
          
        
    - _Пример:_ Размер типа `int` (4 байта на x64, 2 байта на 16-битных MC), знаковость обычного `char` (`signed` или `unsigned`).
        
          
        

### 3. Невладеющие представления: `std::string_view` и `std::span`

Эти типы из Modern C++ предоставляют дешевый, невладеющий доступ к непрерывным блокам данных без копирования и выделения памяти в куче.

  

#### `std::string_view` (C++17)

- **Суть:** Обертка над строкой, хранящая указатель (`const char*`) и длину (`size_t`).
    
      
    
- **Размер:** 16 байт (2 указателя на x64).
    
      
    
- **Применение:** Идеальная передача строк в функции по значению без копирования из `std::string`, `const char*` или строковых литералов.
    
      
    
- **Ловушка (Dangling Reference):** `string_view` **не владеет** памятью! Если исходный объект строки уничтожится, `string_view` станет указывать на «мусор».
    
      
    

#### `std::span<T>` (C++20)

- **Суть:** Невладеющее представление для **любого** непрерывного массива данных (`std::vector`, `std::array`, C-array, `C-style pointer + size`).
    
      
    
- **Преимущества:** Предоставляет безопасный доступ с проверкой границ (`.at()`), поддержку `ranges` и slices без выделения динамической памяти.
    
      
    

C++

```
#include <string_view>
#include <span>
#include <vector>

void print_first_three(std::span<const int> data) {
    if (data.size() >= 3) {
        // Доступ без копирования вектора или C-массива
        std::cout << data[0] << ", " << data[1] << ", " << data[2] << '\n';
    }
}

int main() {
    std::vector<int> vec = {10, 20, 30, 40};
    int arr[] = {1, 2, 3, 4, 5};

    print_first_three(vec); // Работает с vector
    print_first_three(arr); // Работает с C-array без лишних копирований!
}
```

### 4. Аллокаторы (`std::allocator`) и кастомное управление памятью

**`std::allocator<T>`** — это низкоуровневый компонент, разделяющий выделение памяти и конструирование объектов.

  

- **Разделение ответственности:**
    
      
    1. `allocate(n)` — выделяет сырую неинициализированную память под `n` объектов $T$ (через `::operator new`).
        
          
        
    2. `construct(ptr, args...)` — вызывает конструктор объекта на этой памяти (placement new).
        
          
        
    3. `destroy(ptr)` — явно вызывает деструктор объекта.
        
          
        
    4. `deallocate(ptr, n)` — освобождает сырую память.
        
          
        

#### ПоCustom Allocators (Зачем и где нужны)

Стандартные контейнеры STL запрашивают память у системного аллокатора (`malloc`), что может быть медленно в приложениях реального времени (GameDev, HFT, Embedded).

  

Пользовательские аллокаторы решают эту проблему за счет использования специальных стратегий:

  

- **Arena / Bump Allocator:** Очень быстро выделяет память, продвигая один указатель вперед по заранее выделенному массиву. Память освобождается только вся целиком.
    
      
    
- **Pool Allocator:** Выделяет блоки памяти одинакового фиксированного размера. Предотвращает фрагментацию при частой вставке/удалении мелких элементов (`std::list`, `std::map`).
    
      
    
- **PMR (Polymorphic Memory Resources, C++17):** Позволяет менять аллокаторы контейнеров в runtime **без изменения типа самого контейнера** (`std::pmr::vector<T>`).
