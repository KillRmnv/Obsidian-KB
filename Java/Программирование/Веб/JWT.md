**JWT (JSON Web Token)** состоит из трёх частей, разделённых точками:  
`HEADER.PAYLOAD.SIGNATURE`

Каждая часть кодируется в формат **Base64Url** (безопасный для URL и HTTP-заголовков), поэтому в итоговом токене вы видите только строки из букв, цифр, `_` и `-`.

---

###  1. Header (Заголовок)
Содержит метаданные о токене. Обычно это JSON с двумя полями:
```json
{
  "alg": "HS256",    // алгоритм подписи (HMAC SHA-256, RS256, ES256 и др.)
  "typ": "JWT"       // тип токена
}
```
После кодирования: `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9`

---

###  2. Payload (Полезная нагрузка)
Содержит **claims** (утверждения) — информацию о субъекте (обычно пользователе) и дополнительные метаданные. Делится на три типа:

| Тип | Примеры | Описание |
|-----|---------|----------|
| **Registered** | `iss`, `sub`, `aud`, `exp`, `nbf`, `iat`, `jti` | Стандартные поля из RFC 7519 |
| **Public** | `role`, `department` | Публичные ключи, согласованные в IANA |
| **Private** | `user_id`, `is_admin` | Пользовательские данные по договорённости сторон |

Пример payload:
```json
{
  "sub": "1234567890",
  "name": "Иван Петров",
  "role": "admin",
  "iat": 1680000000,
  "exp": 1680003600
}
```
После кодирования: `eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6Ikl2YW4gUGV0cm92Iiwicm9sZSI6ImFkbWluIiwiaWF0IjoxNjgwMDAwMDAwLCJleHAiOjE2ODAwMDM2MDB9`

 **Важно:** Payload **не шифруется**, а только кодируется. Любой, кто перехватит токен, может декодировать эту часть. Не размещайте в ней пароли, секреты или чувствительные персональные данные. Для шифрования используется расширение **JWE**.

---

###  3. Signature (Подпись)
Гарантирует **целостность** и **аутентичность** токена. Формируется сервером по формуле:
```
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret_or_private_key
)
```
Пример результата: `SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c`

Сервер проверяет подпись при каждом запросе: если кто-то изменит header или payload, подпись не совпадёт, и токен будет отклонён.

---

###  Как выглядит полный JWT
```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.
eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6Ikl2YW4gUGV0cm92Iiwicm9sZSI6ImFkbWluIiwiaWF0IjoxNjgwMDAwMDAwLCJleHAiOjE2ODAwMDM2MDB9.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```
*(в реальности всё в одну строку)*

---

###  Как используется и проверяется
1. Клиент получает токен после успешной аутентификации.
2. Отправляет его в заголовке: `Authorization: Bearer <jwt>`
3. Сервер:
   - Декодирует header → узнаёт алгоритм
   - Вычисляет подпись, сравнивает с третьей частью
   - Если подпись верна → декодирует payload
   - Проверяет claims (`exp`, `iss`, `aud` и т.д.)
   - Принимает или отклоняет запрос

---

###  Ключевые нюансы
 JWT **самодостаточен**: серверу не нужно обращаться к БД или Redis для проверки (если не используется blacklist/revocation).  
 **Stateless**: идеально для микросервисов и горизонтального масштабирования.  
 **Не отзывается мгновенно**: чтобы "выкинуть" пользователя до `exp`, нужны дополнительные механизмы (чёрный список, короткое время жизни + refresh token).  
 **Размер**: payload растёт с количеством данных → увеличивает нагрузку на сеть. Оптимизируйте claims.
