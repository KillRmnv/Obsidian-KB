# Гайд: запуск MoE-моделей с чтением весов с SSD

Справочник по запуску больших MoE-моделей, когда веса не помещаются в RAM.
Проверено на Ryzen 5 5600 (6 ядер / 12 потоков, AVX2 без AVX-512), 15 ГиБ RAM,
встроенная AMD Lucienne, WDC SN530 (DRAM-less NVMe).

---

## 0. Быстрый ответ

Три флага, без которых не заработает или будет тормозить:

```
-dev none      # не трогать GPU вообще (см. раздел 2 — самое важное)
-ngl 0         # считать на CPU
-nr            # без repack, иначе вторая копия весов в RAM
```

Полная команда для CPU-only:

```bash
llama cli -m /путь/к/модели.gguf -dev none -ngl 0 -nr -t 6 -c 8192 --temp 0.6
```

`-t 6`, а не 12: SMT не масштабирует векторные операции, см. раздел 6.
Без `-st` — иначе выход после одной реплики.

## 1. Как веса вообще живут на диске

Ключевая идея, без которой всё остальное не понять.

При `-lm mmap` (дефолт) файл модели **не копируется в память**. Он
отображается в адресное пространство, и ядро подгружает страницы **по мере
обращения**. Это даёт три следствия:

1. **RSS процесса не показывает размер модели.** У процесса 21 ГиБ весов на
   диске `anon-rss` может быть 88 кБ. Это нормально, веса не в анонимной памяти.

2. **Page cache — это «оперативка» весов.** Ядро держит в кэше столько
   весов, сколько влезает, остальное выбрасывает и читает заново с SSD.
   Проверить: `free -h` → `buff/cache`. Если там 10–12 ГиБ при модели 21 ГиБ,
   механизм работает правильно.

3. **Модель не должна целиком влезать в RAM.** Иначе никакой «выгрузки на
   SSD» не происходит — всё в кэше.

Модели MoE-A3B (3B активных из 35B) идеально подходят: на токен нужна
крошечная доля весов, горячий набор мал, промахи дешёвые.

**Проверка, что механизм работает:**

```bash
PID=$(pgrep -x llama | head -1)
awk '/^read_bytes/{printf "%.1f GiB с SSD\n", $2/1073741824}' /proc/$PID/io
```

Читаемый объём должен заметно превышать размер модели — значит веса
перечитываются многократно, то есть живут на диске.

## 2. ГЛАВНОЕ: GPU крадёт память, даже если ты его не используешь

Это причина большинства OOM-падений при запуске больших моделей на CPU.

### Что происходит

Сборка llama.cpp с бэкендом Vulkan **при каждом запуске инициализирует
устройство**, даже если выгружать слои не нужно. Драйвер забирает из системной
RAM большой кусок под GTT-апертуру.

Проверка:

```bash
llama --list-devices
```

```
Available devices:
  Vulkan0: AMD Radeon Graphics (RADV RENOIR) (8168 MiB, 7673 MiB free)
```

**8 ГиБ — из твоей оперативки.** При 15 ГиБ RAM это больше половины.

### Как обнаружить

При OOM ядро печатает дамп с памятью. Смотреть `Mem-Info`:

```
shmem:      5995048kB   <- 6,0 ГиБ: не принадлежит ни одному процессу
gpu_active: 7269372kB   <- 7,3 ГиБ: память GPU
mapped:       239324kB   <- mmap модели, всего 239 МБ
free:           32537kB
```

Сравни суммой RSS всех процессов. Если сумма маленькая, а `shmem` большой —
память забрал GPU.

Проверка снаружи:

```bash
awk '/^Shmem:/{printf "%d MiB\n", $2/1024}' /proc/meminfo
```

Норма — 190–200 MiB. Если число растёт при запуске модели, это оно.

### Решение

```
-dev none      # не открывать /dev/dri вообще
```

`-ngl 0` **не помогает**: он запрещает выгружать слои, но бэкенд всё равно
инициализируется. Нужен именно `-dev none`.

### Доказательство

| | без `-dev none` | с `-dev none` |
|---|---|---|
| shmem | 6,0 ГиБ | **188 МиБ** |
| wall | 15 с (убит) | **70 с (успех)** |
| прочитано с SSD | 68 МиБ | **45,2 ГиБ** |
| пик RSS | 0,1 ГиБ | 10,0 ГиБ |
| генерация | не началась | 1,9 t/s |
| OOM-событий | 4 | **0** |

### Ловушка llvmpipe

В системе часто есть второй Vulkan-ICD — **llvmpipe**, программный
реализатор на CPU. Он выглядит как устройство, но считает на CPU, то есть
даёт худшую производительность, чем просто `-ngl 0`. Проверь вывод
`--list-devices`: если там llvmpipe, он не должен попадать в выбор.

## 3. Диагностика перед запуском

```bash
# 1. Какие устройства видит движок
llama --list-devices

# 2. Сколько памяти сейчас забронировал GPU
awk '/^Shmem:/{printf "shmem: %d MiB\n", $2/1024}' /proc/meminfo
cat /sys/class/drm/card*/device/mem_info_gtt_used 2>/dev/null   # GTT, байты
cat /sys/class/drm/card*/device/mem_info_vram_used 2>/dev/null # VRAM, байты

# 3. Сколько реально доступно под page cache
free -h

# 4. Нет ли софтверного растеризатора в списке устройств
vulkaninfo --summary 2>/dev/null | grep -E 'deviceName|driverName'

# 5. Какой backend собран
strings $(which llama) | grep -o 'ggml_[a-z0-9_]*backend' | sort -u
```

Для чистой проверки: запусти модель, затем сразу `awk '/^Shmem:/...' /proc/meminfo`.
Если shmem вырос с 190 МБ до гигабайтов — GPU инициализирован, нужен `-dev none`.

## 4. Выбор модели: единственная метрика, которая важна

**Скорость определяется числом активных параметров, а не общим размером.**

```
байт на токен   ≈ активные_параметры × бит_на_вес / 8
время на токен  ≈ max(вычисления, чтение с SSD)
```

Обе величины растут линейно от активных параметров, поэтому увеличение
активных параметров ухудшает скорость по обоим фронтам сразу.

| Модель | Всего | Активно | Скорость на 6 ядрах |
|---|---|---|---|
| Ling 3.0 (`bailingmoe3`, 4,5 ГБ) | ~3B? | 8/128 | самый быстрый |
| OLMoE | 7B | 1B | втрое быстрее 3B |
| **Qwen3.6-35B-A3B** | 35B | **3B** | **3,0 t/s** |
| Ornith-1.5-35B-A3B | 35B | **3B** | **3,0 t/s** |
| Ornith-1.5-9B | 9B dense | **9B** | **~1,0 t/s** |
| Qwen3.8-Flash-Next | 125B | 6B | ~1,5 t/s |
| DeepSeek-V4-Flash | 284B | 13B | ~0,7 t/s |

Правило: **плотная (dense) модель всегда медленнее MoE с меньшим числом
активных параметров**, даже если её общий размер меньше.

### Как узнать активные параметры любой GGUF

Без запуска модели, мгновенно:

```bash
python3 - <<'EOF'
import struct
f=open('МОДЕЛЬ.gguf','rb'); assert f.read(4)==b'GGUF'
struct.unpack('<I',f.read(4)); nt,nkv=struct.unpack('<QQ',f.read(16))
def rs():
    n,=struct.unpack('<Q',f.read(8)); return f.read(n).decode('utf-8','replace')
def rv(t):
    if t==8: return rs()
    if t==9:
        et,=struct.unpack('<I',f.read(4)); ln,=struct.unpack('<Q',f.read(8))
        return [rv(et) for _ in range(ln)]
    fmt={0:'B',1:'b',2:'H',3:'h',4:'I',5:'i',6:'f',7:'?',10:'Q',11:'q',12:'d'}
    sz={0:1,1:1,2:2,3:2,4:4,5:4,6:4,7:1,10:8,11:8,12:8}
    return struct.unpack('<'+fmt[t],f.read(sz[t]))[0]
kv={}
for _ in range(nkv):
    k=rs(); t,=struct.unpack('<I',f.read(4)); kv[k]=rv(t)
a=kv['general.architecture']
ne=kv.get(f'{a}.expert_count'); nu=kv.get(f'{a}.expert_used_count')
print('архитектура:',a,'| слоёв:',kv.get(f'{a}.block_count'))
print('MoE',nu,'из',ne,'экспертов') if ne else print('DENSE — все параметры активны')
EOF
```

## 5. Полный справочник флагов

### Про память и размещение

| Флаг | Значение | Рекомендация |
|---|---|---|
| `-dev none` | не использовать GPU | **обязательно для CPU** |
| `-ngl 0` | слоёв на GPU, 0 = CPU | обязательно |
| `-ngl 99` | все слои на GPU | для дискретной карты с достаточной VRAM |
| `-lm mmap` | memory-map (дефолт) | оставить; веса живут на диске |
| `-lm mlock` | **запретить** вытеснение | **никогда** при нехватке RAM: OOM |
| `-lm none` | читать в анонимную память | не использовать: уйдёт в swap |
| `-lm dio` | DirectIO, минуя page cache | экспериментально, см. раздел 9 |
| `-nr` | без repack | **обязательно** |
| `-lzm on` | ленивое чтение тензоров | бесполезно: срабатывает только >4 ГиБ |
| `-ncmoe N` | N слоёв MoE оставить на CPU | **бессмысленно** при `-ngl 0` (no-op) |
| `-nkvo` | KV-кэш в RAM | не трогать |

### Про `-nr` подробнее

Repack включён **по умолчанию**. Он переупаковывает все веса в
линейно-упорядоченный вид для ускорения CPU-инференса, и для этого нужна
**полная дополнительная копия всех весов**.

По свидетельству пользователей: без `-nr` на модели 167 ГБ llama.cpp
пытается построить repack-буфер на 147 ГБ и умирает. На твоей модели 21 ГБ
это ещё ~21 ГиБ сверху — при 15 ГиБ RAM смертельно.

Флаг не документирован в `docs/`, но есть в парсере аргументов. И **не
принимается `llama-bench` вообще** — поэтому замеры делаются вручную.

### Про `-lzm` — почему он бесполезен

Справка: «on-demand reading of certain tensors», дефолт `auto` = «только для
тензоров крупнее 4 ГиБ».

Реальные размеры тензоров в Qwen3.6-35B-A3B:

| Тензор | Размер |
|---|---|
| `output.weight` | 394 МиБ |
| `token_embd.weight` | 273 МиБ |
| `blk.N.ffn_*_exps.weight` (320 шт.) | 176–208 МиБ |
| **максимум** | **208 МиБ** |

Ни один тензор не достигает 4 ГиБ → `-lzm` не делает **ничего**. Проверено
разбором GGUF.

Менять число активных экспертов нельзя: это свойство обученных весов роутера,
а не настройка. Поднять top-8 до 32 — значит запустить другой роутер и
испортить качество.

### Про `-ncmoe` — почему он бесполезен

Это ручка распределения весов **между CPU и GPU** (`--n-cpu-moe`: первые N
слоёв MoE держать на CPU). При `-ngl 0` GPU не существует, всё и так в CPU,
поэтому флаг — no-op. Он не различает «в RAM» и «на SSD».

### Про `-c` (контекст)

KV-кэш линейный по контексту. Для Qwen3.6-35B-A3B при 8192 это ~640 МиБ,
при 262144 — ~20 ГиБ, что съест всю память и вытеснит веса.

Контекст конкурирует с весами за RAM. Правило:
`размер_контекста × 80 КиБ` должно быть меньше ~10% свободной памяти.

## 6. Потоки CPU: физические ядра, а не логические

**`-t 6`, а не `-t 12`** на 6 ядрах / 12 потоков.

Почему SMT не помогает для ggml:

- векторные юниты AVX2 **один на ядро**; два SMT-потока делят одни и те же
  регистры, второй не получает ни ALU, ни ширину вектора
- добавляются накладные расходы: переключение контекстов, больше барьеров
  OpenMP между чанками слоя
- два потока на ядро вытесняют друг друга из L1/L2 (у тебя L2 всего 3 МиБ на
  6 инстансов)

Измеренный результат:

| | скорость |
|---|---|
| `-t 12` | 1,5 t/s |
| `-t 6` | **~3,0 t/s** |

 Эти замеры **не чистые**: сначала гоняли 12, потом 6, а page cache за это
время прогрелся. Нужен обратный порядок, чтобы отделить эффект кэша.

Определить физические ядра:

```bash
lscpu | grep -E '^CPU\(s\)|Thread\(s\) per core'
grep -E '^(physical id|core id)' /proc/cpuinfo | paste - - | sort -u | wc -l
```

## 7. Изоляция: cgroup вместо надежды

Запуск в transient-службе systemd даёт лимит памяти и не даёт убить всё
остальное.

```bash
systemd-run --user -p MemoryMax=11G -p MemoryHigh=10G -p CPUWeight=50 \
  --collect --wait --pipe \
  llama cli -m /путь/к/модели.gguf -dev none -ngl 0 -nr -t 6 -c 8192 --temp 0.6 \
    -p "вопрос" --no-display-prompt
```

| Параметр | Зачем |
|---|---|
| `MemoryMax` | жёсткий потолок RAM для всей службы, включая page cache |
| `MemoryHigh` | мягкий порог: ядро начинает вытеснять кэш на SSD заранее |
| `CPUWeight=50` | отдать приоритет остальным процессам |
| `--collect` | cgroup удалится после завершения |
| `--pipe` | **обязательно** для stdin и вывода |

### Что делать с лимитом

 **`MemoryMax` не защищает систему от OOM, если память берёт GPU.** GPU
забирает её вне cgroup, и глобальный OOM-киллер выбирает жертву по всей
системе. Лимит лишь сдвигает точку отказа.

Отсюда парадокс, который наблюдался: `MemoryMax=5G` провалился **хуже**, чем
`11G` — при 5 ГиБ давление нарастало раньше, и жертвами стали `dms`, `kitty`,
`opencode`.

Лимит подбирают так:

```
свободная память = MemAvailable (free -h)
MemoryMax        = ~MemAvailable - 1 ГиБ   (запас десктопу)
MemoryHigh       = MemoryMax - 1 ГиБ        (мягче, вытеснение заранее)
```

### `--pipe` и stdin

Без `--pipe` systemd-run **не пробрасывает stdin**. `llama cli` загрузит
модель, прочитает `/dev/null`, напечатает `>` и будет крутить цикл на 127% CPU
бесконечно. Выглядит как «модель зависла», но она готова — просто ввод не
приходит.

С `--pipe` systemd печатает служебные строки (`Running as unit: ...`) в тот же
терминал. Для чистого интерактива запускай `llama` напрямую без
systemd-обвязки — тогда терминал полностью твой, но лимитов не будет.

Остановить зависшую службу:

```bash
systemctl --user stop run-pXXXX-iYYYY.service
systemctl --user stop 'run-p*.service'   # все разом
pkill -x llama                          # хуже: cgroup останется в failed
```

## 8. Как честно проверить, что было OOM

 **Не считай OOM по временному окну.** Окно `-6min` может не задевать момент
события — тогда счётчик пишет «0 OOM», когда OOM был. Это ломало выводы
дважды за сессию.

Правильно — по курсору журнала, он даёт точную позицию в потоке:

```bash
CUR=$(journalctl -b 0 -k --show-cursor | tail -1 \
      | grep -ao 'cursor: s=.*' | sed 's/cursor: //')

# ... запуск модели ...

journalctl -b 0 -k --after-cursor="$CUR" \
  | grep -ac 'Out of memory: Killed process'
```

Посмотреть, кто именно погиб:

```bash
journalctl -b 0 -k --since '-10min' \
  | grep -a 'Out of memory: Killed process' \
  | sed 's/.*Killed process /  /;s/ total-vm.*adj=/ adj=/'
```

### Что должно выжить

Проверять **до и после**, и список должен включать композитор:

```bash
for p in niri kitty pipewire wireplumber dms blueman-applet obexd; do
  pgrep -x "$p" >/dev/null || echo "ПОГИБ: $p"
done
for s in NetworkManager avahi-daemon systemd-userdbd; do
  systemctl --user is-active --quiet "$s" || echo "ПОГИБ: $s"
done
```

`dms` (композитор эффектов Wayland) обязателен — на прошлых прогонах именно он
выпадал из списка, и падение проходило незамеченным.

## 9. Настройки системы

### vm.swappiness — обязательно 30, не 150

 **Дистрибутивы (CachyOS в частности) ставят 150 через udev-правило.** Проверить:

```bash
grep -rl swappiness /usr/lib/udev/rules.d/ /etc/udev/rules.d/
```

CachyOS: `/usr/lib/udev/rules.d/30-zram.rules` содержит
`SYSCTL{vm.swappiness}="150"` и срабатывает при **каждом** создании zram0.

При 150 ядро агрессивно вытесняет страницы в swap. Если swap — zram
(сжатая память в RAM), получается петля: вытеснили в zram → zram занял RAM →
RAM кончился → OOM.

Перекрыть своим правилом в `/etc/udev/rules.d/` (тот же номер файла, udev
берёт приоритет из `/etc`):

```bash
printf 'ACTION=="change", KERNEL=="zram0", ATTR{initstate}=="1", SYSCTL{vm.swappiness}="30", \\\n    RUN+="/bin/sh -c '"'"'echo N > /sys/module/zswap/parameters/enabled'"'"'"\n' \
  | sudo tee /etc/udev/rules.d/30-zram.rules

printf 'vm.swappiness=30\n' | sudo tee /etc/sysctl.d/99-swappiness.conf
sudo sysctl --system
```

 **Комментарии `#` в `zram-generator.conf` ломают парсер:**

```
Error: UnparsedTokensRemaining("# вместо ram: 4 ГиБ вместо 15")
```

Никаких комментариев в значении параметра.

### zram: держать не больше половины RAM

`zram-size = ram` (дефолт CachyOS) означает zram размером с RAM — то есть
сжатая память в памяти. При нехватке это ускоряет OOM.

```bash
printf '[zram0]\ncompression-algorithm = zstd\nzram-size = 4G\nswap-priority = 100\nfs-type = swap\n' \
  | sudo tee /etc/systemd/zram-generator.conf
```

Дефолт самого zram-generator — `min(ram/2, 4096)` МБ, то есть 4 ГиБ при
16 ГиБ RAM. Именно 4 ГиБ безопасны.

Если zram не поднимается (`ENOMEM`, `EBUSY`, `start-limit-hit`) — **это
нормально и не нужно чинить**. При `swappiness=30` чистые файловые страницы
модели ядро выбрасывает мгновенно и без потерь, а не сжимает в zram. Пустой
swap безопаснее.

Диагностика:

```bash
systemctl status systemd-zram-setup@zram0.service
journalctl -u systemd-zram-setup@zram0.service --no-pager | tail -20
sudo systemctl reset-failed systemd-zram-setup@zram0.service
```

### vm.page-cluster — бесплатный рычаг для SSD

```bash
cat /proc/sys/vm/page-cluster    # обычно 0
```

`0` означает: при промахе кэша ядро читает с SSD **ровно одну страницу**
(4 КиБ). Веса экспертов читаются последовательно, поэтому постранично —
крайне неэффективно.

```bash
sudo sysctl -w vm.page-cluster=8
```

На память не влияет, только на скорость чтения. Особенно актуально для
**DRAM-less** накопителей (WDC SN530, SN550 и подобные) — у них нет собственной
кэш-памяти, весь буфер в системной RAM.

Проверить, DRAM-less ли диск:

```bash
lsblk -d -o NAME,MODEL,SIZE /dev/nvme0n1
```

### Не принуждать вытеснение кэша

`MemoryHigh` ниже пикового RSS **замедляет** модель вдвое:

| MemoryHigh | wall | generation |
|---|---|---|
| 10G | 110 с | 0,8–0,9 t/s |
| 6G | 157 с | **0,4 t/s** |

Меньше RAM → больше промахов → больше чтений с SSD. Ядру лучше дать держать
кэш, сколько влезет.

### /tmp в tmpfs — не писать туда логи

`/tmp` смонтирован как tmpfs на 7,5 ГиБ **в RAM**. Логи и сэмплы оттуда
конкурируют с page cache модели.

```bash
mount | grep tmpfs
mkdir -p ~/models/logs
```

## 10. Дискретные GPU и бэкенды

### Vulkan (универсальный, работает с AMD/Intel/NVIDIA)

Единственный бэкенд в проверенной сборке. Плюсы: не требует проприетарных
SDK, работает с AMD через RADV.

```bash
# выгрузить часть слоёв на дискретную карту
llama cli -m модель.gguf -ngl 30 -c 8192      # 30 слоёв в VRAM

# выгрузить всё
llama cli -m модель.gguf -ngl 99
```

 **Дискретная карта тоже берёт память из системы**, если VRAM не хватает.
Проверять так же, как встроенную:

```bash
cat /sys/class/drm/card*/device/mem_info_vram_used
cat /sys/class/drm/card*/device/mem_info_gtt_used
awk '/^Shmem:/{print $2/1024" MiB"}' /proc/meminfo
```

`-ncmoe N` становится осмысленным именно здесь: первые N слоёв MoE оставить на
CPU, остальные выгрузить на GPU.

### CUDA (NVIDIA)

В собранном llama бэкенда нет. Требуется сборка с CUDA и драйвер.
Идентично Vulkan по поведению памяти: VRAM выделенная, но при нехватке
NN-памяти уходит в системную через unified memory — тогда `-dev none` не
поможет, нужно уменьшать `-ngl`.

### OpenGL / OpenCL

 **Этих бэкендов в современном llama.cpp больше нет.** OpenGL-бэкенд был
удалён в пользу Vulkan; OpenCL-бэкенда нет уже давно. Проверено: в бинаре
отсутствуют строки `ggml_gl`, `opencl`. Искать их в справке бессмысленно —
современные варианты: **Vulkan, CUDA, HIP, SYCL, Metal, CPU**.

Для AMD остаётся два пути: Vulkan (RADV, рекомендуется) или HIP/ROCm
(собранные бэкенды AMD, только RDNA-подобные, требуют ROCm).

### Мета-флаг для скрытия GPU

Если бэкенд инициализируется, несмотря на флаги, можно скрыть устройство
на уровне драйвера:

```bash
VK_ICD_FILENAMES=/dev/null llama-cli ...    # Vulkan не найдёт ICD
```

Аналогично `GGML_VK_VISIBLE_DEVICES`. Но `-dev none` проще и надёжнее.

### Не смешивать GPU и CPU для весов MoE

Для MoE-моделей на 21+ ГБ частичная выгрузка обычно проигрывает: перенос
данных через PCIe не окупает экономию RAM. Либо всё в VRAM (`-ngl 99`), либо
всё на CPU (`-dev none`).

## 11. Методика замеров

###  Сначала прочитай раздел 12: тема вопроса определяет результат

Частая ловушка: чтобы проверить прогрев кэша, задают **разные** вопросы в
каждом ходе. Это даёт противоположный (неверный) вывод — см. раздел 12.

### Порядок имеет значение

 **Page cache прогревается постепенно.** Первый запуск читает вещи с SSD,
второй берёт их из кэша. Тест «холодный против тёплого» даёт разницу, которую
легко принять за эффект от настройки.

Правильная методика:

```bash
# сбросить кэш (нужен sudo)
echo 3 | sudo tee /proc/sys/vm/drop_caches

# прогрев: один запуск
# затем замер — несколько прогонов подряд
```

Без `drop_caches` — гонять **обратный порядок**: сначала вариант Б, потом
вариант А, и сравнивать вторые замеры.

### Что мерить

```bash
# чтение с SSD (главный признак, что веса на диске)
awk '/^read_bytes/{printf "%.1f GiB\n", $2/1073741824}' /proc/$PID/io

# RSS (не показывает размер модели при mmap!)
awk '/^VmRSS/{printf "%.1f GiB\n", $2/1048576}' /proc/$PID/status

# скорость — из вывода llama: [ Prompt: 1,1 t/s | Generation: 1,9 t/s ]
```

### Скрипт

Готовые рабочие скрипты в `~/models/scripts/`:
`run-devnone.sh` (проверенный замер с честной проверкой OOM по курсору),
`run-11g.sh`, `final-check.sh`, `warmup-test.py` (прогрев кэша, раздел 12).

## 12. Прогрев кэша по ходу диалога

Разбирает, растёт ли скорость по мере разговора. Ответ: **да, примерно вдвое,
если держать одну тему.**

### Как измеряется

```bash
MEM_MAX=12G MEM_HIGH=12G TURNS=4 MAX_TOK=100 python3 scripts/warmup-test.py
```

Скрипт поднимает `llama serve`, шлёт последовательные запросы с растущей
историей и на каждом ходе снимает скорость, page cache и чтение с SSD.
Ключевое условие: все вопросы по **одной теме**.

### Результат: одна тема

| ход | время | токенов | t/s | промпт | кэш | чтение между ходами |
|---|---|---|---|---|---|---|
| 1 | 101,9 с | 100 | 0,98 | 36 | 11500 МиБ | загрузка 21 ГиБ |
| 2 | 45,0 с | 100 | **2,22** | 76 | 11243 | **+5,0 ГиБ** |
| 3 | 59,5 с | 100 | 1,68 | 215 | 10855 | **+6,7 ГиБ** |

### Контрольный тест: темы НЕ связаны

| | разные темы | одна тема |
|---|---|---|
| чтение с SSD на ход | +50…80 ГиБ | **+5…7 ГиБ** |
| скорость | 0,47–1,00 t/s | **до 2,22 t/s** |

Разница в чтении — **в десять раз**. Роутер возвращается к тем же экспертам,
горячие страницы остаются в page cache, и вместо ~1,4 ГиБ на токен модель
тянет ~50 МБ.

 Тест с несвязанными темами даёт **ложный вывод**, что прогрева нет. Если
измерять прогрев, вопросы должны продолжать одну тему.

### Практический вывод

Веди диалог по одной теме — со второго хода скорость вырастает примерно вдвое.
При перескакивании между несвязанными задачами разгона не будет.

### Оговорки

- **Первый ход всегда медленный** (0,98 против 2,22): включает ~40 с загрузки
  модели и холодный кэш.
- **Рост контекста съедает разгон.** На третьем ходу промпт вырос с 76 до 215
  токенов, скорость упала до 1,68. Дальше будет падать — стоимость префилла
  растущей истории линейна. Это естественный обратный эффект.
- **Page cache не растёт, а сжимается** (11500 → 10855 МиБ). Раннее
  предположение «кэш будет расти» неверно: он не растёт, а **переиспользуется** —
  вместо чтения с SSD идёт попадание в кэш. Давление `MemoryHigh` вытесняет
  часть весов, но оставшиеся горячие страницы всё равно экономят чтение.

### Что НЕ помогло

| | чтение с SSD за прогон | вывод |
|---|---|---|
| базовые настройки | 212 ГиБ | — |
| `--cache-reuse 64` + `MemoryHigh=12G` | **359 ГиБ** | хуже на 70%, не использовать |

`--cache-reuse N` переиспользует префикс через сдвиг KV. На коротком контексте
сдвиг — чистые накладные расходы: чтение выросло, разгона не появилось.

`--cache-prompt` **уже включён по умолчанию** (`default: enabled`), задавать
не нужно.

### Скорость в зависимости от условий

| | условия |
|---|---|
| ~2,2 t/s | тёплый кэш, короткий контекст, одна тема |
| ~1,7 t/s | тёплый кэш, контекст вырос до 200+ токенов |
| ~1,0 t/s | первый ход, холодный кэш + загрузка модели |
| ~0,5 t/s | каждый раз новая тема, кэш не прогревается |

## 13. Диагностика ошибок

| Симптом | Причина | Что делать |
|---|---|---|
| OOM через 15 с, `mapped` 239 МБ | GPU забрал RAM через Vulkan | `-dev none` |
| `free` показывает 6 ГиБ занятых, а сумма RSS 1 ГиБ | память GPU (`shmem`) | `-dev none` |
| `Loading model...` вечно, CPU 127%, вывод `>` | stdin не подключён | добавь `--pipe` |
| Модель выходит после одной реплики | флаг `-st` (single-turn) | убери `-st` |
| `zram: Failed to start` / `start-limit-hit` | zram не поднялся | не чинить, это безопасно |
| `UnparsedTokensRemaining` в zram-конфиге | комментарий `#` в значении | убрать комментарий |
| `Error: zram-size` | то же | убрать комментарий |
| `Device or resource busy` при рестарте zram | устройство занято swap | `swapoff`, затем reset |
| OOM при `MemoryMax=5G`, но не при `11G` | GPU ест вне cgroup, лимит лишь сдвигает точку | `-dev none`, затем поднять лимит |
| Медленно, `buff/cache` пуст | кэш вытесняется, контекст больш | уменьшить `-c` |
| Вдвое медленнее, чем было | принудительное вытеснение кэша | поднять `MemoryHigh` |
| `Cannot allocate memory` при загрузке модели | слишком высокий `-c` или лимит RAM | снизить `-c` |
| `error: invalid argument: -no-display-prompt` | опечатка | два тире: `--no-display-prompt` |
| `failed to open GGUF file './...'` | `systemd-run` меняет рабочую директорию | абсолютный путь или `-p WorkingDirectory=` |
| `-dev none` не помогает | бэкенд инициализируется иначе | `VK_ICD_FILENAMES=/dev/null` |

## 14. Чек-лист перед запуском

```bash
# 1. нет ли софтверного Vulkan и что вообще видно
llama --list-devices

# 2. сколько памяти занимает GPU (должно быть ~190 MiB)
awk '/^Shmem:/{printf "%d MiB\n", $2/1024}' /proc/meminfo

# 3. сколько доступно под веса
free -h          # MemAvailable

# 4. swappiness
cat /proc/sys/vm/swappiness      # должно быть 30, не 150

# 5. активные параметры модели
#    (скрипт из раздела 4)

# 6. сколько физических ядер
lscpu | grep -E '^CPU\(s\)|Thread\(s\) per core'
```

Финальная команда:

```bash
systemd-run --user -p MemoryMax=<MemAvailable-1G> -p MemoryHigh=<на 1G меньше> \
  -p CPUWeight=50 --collect --wait --pipe \
  llama cli -m /абсолютный/путь/модели.gguf \
    -dev none -ngl 0 -nr -t <физические ядра> -c 8192 --temp 0.6 \
    -p "вопрос" --no-display-prompt
```

## 15. Что менять, если нужно быстрее

| Приём | Прирост | Заметка |
|---|---|---|
| `-dev none` | с падения до работы | обязательно |
| `-nr` | без него OOM | обязательно |
| `-t` = физические ядра | ×2 против SMT | бесплатно |
| Больше RAM (32 ГиБ) | модель целиком в кэше, промахи исчезают | апгрейд |
| Больше физических ядер | линейно, это главный рычаг CPU | апгрейд |
| Модель с меньшим числом активных | линейно | качество просядет |
| Q3 вместо Q4 | ~30% меньше вычислений | качество просядет |
| `vm.page-cluster=8` | возможен, замерить | бесплатно, на память не влияет |
| SSD с DRAM или второй диск | заметно при промахах | апгрейд |
| `-lm dio` | минуя page cache, бывает +34% | зависит от накопителя |

Чего **не делать**: увеличивать число активных экспертов (свойство весов),
принудительно вытеснять кэш на SSD (вдвое медленнее), `mlock` при нехватке
RAM (гарантированный OOM).
