# Транзакции и блокировки

## Зачем это нужно

MVCC убирает блокировки чтения, но запись всё равно конфликтует. Не понимая локов, невозможно объяснить «сайт повис», «миграция заблокировала таблицу на 10 минут» или «deadlock detected». Здесь же — как читать `pg_locks` и находить виновника.

## Как устроено

### Уровни изоляции именно в PostgreSQL

| Уровень | Что видит транзакция | Аномалии |
|---|---|---|
| `READ UNCOMMITTED` | То же, что `READ COMMITTED` (в PG не реализован отдельно) | — |
| `READ COMMITTED` (default) | Новый снапшот **на каждый оператор** | non-repeatable read, phantom read |
| `REPEATABLE READ` | Снапшот на первом операторе, до конца транзакции | нет (кроме write skew) |
| `SERIALIZABLE` | SSI: отслеживает конфликты чтения/записи, откатывает одну из транзакций | нет (при retry) |

Особенности PG:

- `REPEATABLE READ` при конкурентном `UPDATE` той же строки выдаёт **`could not serialize access due to concurrent update`** — транзакцию нужно повторить.
- `SERIALIZABLE` — это **SSI** (Serializable Snapshot Isolation) на предикатных блокировках, а не блокировки чтения. Ошибка `could not serialize access due to read/write dependencies` — норма, нужен retry-loop.
- `READ ONLY DEFERRABLE` — ждёт «безопасный» снапшот, полезно для длинных отчётов на реплике.

Подробнее про аномалии — [[изоляция транзакций]], про свойства — [[ACID]].

### Табличные блокировки: 8 режимов

| Режим | Кто берёт | Конфликтует с |
|---|---|---|
| `ACCESS SHARE` | `SELECT` | `ACCESS EXCLUSIVE` |
| `ROW SHARE` | `SELECT FOR UPDATE/SHARE` | `EXCLUSIVE`, `ACCESS EXCLUSIVE` |
| `ROW EXCLUSIVE` | `INSERT/UPDATE/DELETE` | `SHARE`, `SHARE ROW EXCLUSIVE`, `EXCLUSIVE`, `ACCESS EXCLUSIVE` |
| `SHARE UPDATE EXCLUSIVE` | `VACUUM`, `ANALYZE`, `CREATE INDEX CONCURRENTLY`, `ALTER TABLE … VALIDATE` | себя, `SHARE`, `SHARE ROW EXCLUSIVE`, `EXCLUSIVE`, `ACCESS EXCLUSIVE` |
| `SHARE` | `CREATE INDEX` (без CONCURRENTLY) | `ROW EXCLUSIVE` и выше |
| `SHARE ROW EXCLUSIVE` | `CREATE TRIGGER`, некоторые `ALTER` | всё, кроме `ACCESS SHARE` |
| `EXCLUSIVE` | `REFRESH MATERIALIZED VIEW CONCURRENTLY` (не всегда) | всё, кроме `ACCESS SHARE` |
| `ACCESS EXCLUSIVE` | `DROP`, `TRUNCATE`, `ALTER TABLE`, `REINDEX`, `VACUUM FULL` | **всё** |

Важно: **блокировки ставятся в очередь**. Если `ACCESS EXCLUSIVE` ждёт длинный `SELECT`, то все следующие `SELECT` встанут за ним — хотя формально с ним не конфликтуют. Отсюда правило: DDL в миграциях — с `lock_timeout`.

### Строчные блокировки

| Синтаксис | Что блокирует |
|---|---|
| `FOR UPDATE` | Полная блокировка строки (не даёт менять и блокировать) |
| `FOR NO KEY UPDATE` | Не блокирует `FOR KEY SHARE` (обычный `UPDATE` берёт именно её) |
| `FOR SHARE` | Разрешает другим `FOR SHARE`, запрещает изменение |
| `FOR KEY SHARE` | Защищает только ключ (используется при проверке FK) |

Строчная блокировка хранится в заголовке кортежа (`xmax`), при нескольких блокирующих — в `pg_multixact`. **Эскалации блокировок нет** (в отличие от SQL Server): 1 млн заблокированных строк = 1 млн записей в lock table (`max_locks_per_transaction`).

### Deadlock

Взаимное ожидание:

```
tx A: UPDATE t SET … WHERE id=1;   -- держит строку 1
tx B: UPDATE t SET … WHERE id=2;   -- держит строку 2
tx A: UPDATE t SET … WHERE id=2;   -- ждёт B
tx B: UPDATE t SET … WHERE id=1;   -- ждёт A  → deadlock
```

Через `deadlock_timeout` (default `1s`) сервер проверяет граф ожиданий и убивает одну транзакцию (`deadlock detected`). Лучше предотвращать: обновлять строки в одинаковом порядке, сокращать транзакции.

### Advisory locks

Пользовательские блокировки, не привязанные к строкам:

```sql
SELECT pg_advisory_lock(42);            -- сессионная, снимать вручную
SELECT pg_try_advisory_lock(42);        -- не блокируется, вернёт false
SELECT pg_advisory_xact_lock(42);       -- снимется при COMMIT/ROLLBACK
```

Применение: «только один воркер делает job», rate limiting, координация миграций.

### Таймауты — обязательный минимум

```sql
SET lock_timeout = '3s';                     -- не ждать лок дольше
SET statement_timeout = '30s';               -- убить долгий запрос
SET idle_in_transaction_session_timeout = '60s'; -- убить «зависшую» транзакцию
SET deadlock_timeout = '1s';
```

## Что видно в psql

```sql
-- Кто чего ждёт
SELECT pid,
       wait_event_type,
       wait_event,
       state,
       now() - xact_start AS xact_age,
       left(query, 80) AS query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY xact_start;

-- Блокировки
SELECT locktype, relation::regclass, mode, granted, pid
FROM pg_locks
WHERE NOT granted OR relation IS NOT NULL
ORDER BY relation, pid;

-- Кто кого блокирует (самый удобный запрос)
SELECT pid, pg_blocking_pids(pid) AS blocked_by, wait_event_type, left(query, 60)
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- Дерево ожиданий
WITH RECURSIVE waits AS (
  SELECT pid, pg_blocking_pids(pid) AS blockers, 1 AS depth
  FROM pg_stat_activity
  WHERE cardinality(pg_blocking_pids(pid)) > 0
)
SELECT * FROM waits;
```

Убить мешающий бэкенд: `SELECT pg_terminate_backend(<pid>);` (осторожно — это разрыв соединения).

## Грабли и мифы

1. **«MVCC значит блокировок нет»** — есть, и они копятся в очереди. DDL-лок может заблокировать всю таблицу, даже если сам по себе мгновенный.
2. **`ALTER TABLE` берёт `ACCESS EXCLUSIVE`** — на большую таблицу это «стоп-кран». Всегда `SET lock_timeout` + повтор, или `ALTER TABLE … ADD COLUMN … DEFAULT` (в PG11+ это быстро, но лок всё равно берётся).
3. **`CREATE INDEX` блокирует запись** (`SHARE`), `CREATE INDEX CONCURRENTLY` — нет (`SHARE UPDATE EXCLUSIVE`), но работает дольше и может оставить `INVALID` индекс.
4. **Долгая транзакция не только про локи** — она ещё и держит `xmin`, мешая vacuum ([[Внутрянка/MVCC и версии строк]]).
5. **`idle in transaction` — это активная угроза**: держит снапшот и локи, но ничего не делает.
6. **`SELECT … FOR UPDATE` на реплике** не работает (только на primary).

## Эксперимент

```sql
-- Подготовка
CREATE TABLE accounts (id int primary key, balance int);
INSERT INTO accounts VALUES (1, 100), (2, 100);
```

Сессия A:

```sql
BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
SELECT pg_sleep(30);   -- держим транзакцию
```

Сессия B:

```sql
UPDATE accounts SET balance = balance + 10 WHERE id = 1;  -- повиснет
-- смотрим в третьей сессии:
--   pg_stat_activity → wait_event_type = 'Lock'
--   pg_blocking_pids(pid) → PID сессии A
```

Сессия C (deadlock):

```sql
-- A: UPDATE accounts SET balance=1 WHERE id=1;  затем id=2
-- B: UPDATE accounts SET balance=2 WHERE id=2;  затем id=1
-- через ~1s одна из сессий получит: deadlock detected
```
