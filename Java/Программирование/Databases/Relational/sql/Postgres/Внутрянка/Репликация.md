# Репликация

## Зачем это нужно

Репликация — это не только HA, но и **источник задержек и рассинхронизации чтения**: приложение читает с реплики и не видит только что записанное. Плюс реплики влияют на primary: слоты держат WAL, `hot_standby_feedback` держит vacuum, синхронная репликация влияет на latency коммитов.

## Как устроено

### Физическая (streaming) репликация

Standby получает **байты WAL** и применяет их к своей копии данных. Это побайтовая копия кластера.

```
primary:  WAL → walsender ──TCP──► walreceiver → WAL → startup process (replay)
```

Настройка (кратко):

```conf
# primary
wal_level = replica
max_wal_senders = 10
wal_keep_size = '1GB'          # или replication slot
# standby
primary_conninfo = 'host=... port=5432 user=replicator'
hot_standby = on
```

- `pg_basebackup` — начальная копия;
- `pg_ctl promote` / `SELECT pg_promote()` — повышение standby;
- `pg_rewind` — «догнать» старый primary после failover.

### Синхронная vs асинхронная

| | Async (default) | Sync |
|---|---|---|
| Коммит подтверждён | после локального fsync | после подтверждения реплики |
| Потеря при падении primary | последние транзакции | нет (при sync-реплике) |
| Latency коммита | низкая | зависит от сети/реплики |

```conf
synchronous_standby_names = 'ANY 1 (replica1, replica2)'
synchronous_commit = on                 # ждать записи WAL на реплике
# synchronous_commit = remote_apply    # ждать применения (read-your-writes)
```

`ANY 1 (...)` — кворум: достаточно одной из реплик. `FIRST 1 (...)` — приоритет по списку.

Важно: `synchronous_commit=remote_apply` даёт «прочитал с sync-реплики — увидел свой коммит», но сильно увеличивает latency. Обычно читают с primary.

### Логическая репликация

Передаёт **изменения строк** (INSERT/UPDATE/DELETE) по таблицам, а не байты WAL.

```sql
-- На публикующей стороне: wal_level = logical
CREATE PUBLICATION pub_orders FOR TABLE orders;

-- На подписчике
CREATE SUBSCRIPTION sub_orders
CONNECTION 'host=primary dbname=app user=repl'
PUBLICATION pub_orders;
```

Возможности:

- выборочные таблицы (`FOR TABLE`), схемы (`FOR ALL TABLES`);
- row filter (`WHERE`) и список колонок (PG15+);
- репликация между разными версиями и разными СУБД (через output plugins);
- CDC в Kafka/DWH (Debezium).

Ограничения:

- **DDL не реплицируется** — схему менять на обеих сторонах;
- последовательности/`serial` не синхронизируются автоматически;
- нет глобальной транзакционности между таблицами;
- конфликты (unique violation) останавливают подписку — смотреть `pg_stat_subscription_stats` (PG15+);
- `TRUNCATE` реплицируется, но не всё (например, `ALTER`).

### Слоты репликации

Слот гарантирует, что primary не удалит WAL, нужный потребителю:

```sql
SELECT slot_name, slot_type, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;
```

**Опасность:** неактивный слот с `restart_lsn` в прошлом копит WAL, пока не кончится диск. Защита — `max_slot_wal_keep_size` (PG13+): слот инвалидируется, когда WAL превышает лимит. Настрой и мониторь.

### Лаг и его измерение

```sql
SELECT application_name, state, sync_state,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS lag_bytes,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;

-- На реплике
SELECT pg_last_wal_replay_lsn(),
       pg_last_xact_replay_timestamp(),
       now() - pg_last_xact_replay_timestamp() AS replay_delay;
```

`replay_lag` — время от коммита на primary до применения на реплике. Именно оно интересно приложению.

### Проблемы чтения с реплики

1. **Stale reads**: async-реплика отстаёт → пользователь не видит свой заказ.
2. **Read-your-writes**: решается `synchronous_commit=remote_apply` для критичных транзакций, sticky-сессией на primary или ожиданием LSN:

```sql
-- на клиенте запомнили LSN после записи, на реплике ждём его применения
SELECT pg_last_wal_replay_lsn() >= '0/1A2B3C4'::pg_lsn;
```

3. **Конфликты на hot standby**: vacuum на primary удаляет версии, нужные долгому запросу на реплике. `hot_standby_feedback=on` передаёт `xmin` на primary (но это мешает vacuum), `max_standby_streaming_delay` ограничивает ожидание (запрос на реплике будет убит).

### Failover

- **Автоматический**: Patroni, repmgr, cloud-платформы (RDS/Aurora/Cloud SQL).
- **Ручной**: `pg_ctl promote`, затем перенастроить клиентов.
- **Split-brain**: два primary — самая опасная ситуация; нужен quorum/менеджер.
- **pg_rewind** — вернуть старый primary в строй без полной перебазировки.

### Каскадная и отложенная репликация

```conf
# каскад: standby → standby
primary_conninfo = 'host=standby1 ...'
# отложенная: применять WAL с задержкой (защита от человеческой ошибки)
recovery_min_apply_delay = '1h'
```

Отложенная реплика — не бэкап, но спасает от `DROP TABLE`, если заметить вовремя.

## Что видно в psql

```sql
-- 1. Состояние реплик на primary
SELECT pid, application_name, client_addr, state, sync_state,
       sent_lsn, write_lsn, flush_lsn, replay_lsn,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;

-- 2. Слоты и удерживаемый WAL
SELECT slot_name, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn))
FROM pg_replication_slots;

-- 3. На реплике: где мы и насколько отстали
SELECT pg_is_in_recovery(),
       pg_last_wal_replay_lsn(),
       pg_last_xact_replay_timestamp(),
       now() - pg_last_xact_replay_timestamp() AS delay;

-- 4. Логические подписки
SELECT subname, subenabled, pid, relid, received_lsn, latest_end_lsn
FROM pg_stat_subscription;

-- 5. Конфликты логической репликации (PG15+)
SELECT * FROM pg_stat_subscription_stats;
```

## Грабли и мифы

1. **«Реплика = бэкап»** — нет: `DROP TABLE` мгновенно приедет на реплику. Нужен PITR.
2. **`synchronous_commit=on` без sync-реплики** — это просто локальный fsync, не синхронность.
3. **Забытый слот** съедает диск primary. Смотри `pg_replication_slots` и `max_slot_wal_keep_size`.
4. **`hot_standby_feedback=on`** спасает запросы на реплике, но раздувает таблицы на primary (vacuum не убирает версии).
5. **Асинхронная реплика теряет данные при failover** — ровно те транзакции, что не доехали.
6. **Логическая репликация не реплицирует DDL и sequence** — миграции применять на обеих сторонах.
7. **Реплика не масштабирует запись** — только чтение; и то не всегда (конфликты, лаг).
8. **Каскадная репликация увеличивает лаг** — каждый hop добавляет задержку.

## Эксперимент

В лаборатории на Docker:

```bash
docker compose --profile replica up -d
```

```sql
-- primary
CREATE TABLE repl_demo (id int primary key, v text);
INSERT INTO repl_demo VALUES (1, 'a');

-- реплика (read-only)
SELECT * FROM repl_demo;                 -- видит
INSERT INTO repl_demo VALUES (2, 'b');   -- ERROR: cannot execute INSERT in a read-only transaction

-- primary: смотрим лаг
SELECT application_name, replay_lag FROM pg_stat_replication;

-- primary: имитируем ошибку «человека»
DROP TABLE repl_demo;

-- реплика
SELECT * FROM repl_demo;                 -- ERROR: relation does not exist
-- вывод: реплика не защищает от ошибок, нужен PITR
```
