# Каталог и статистика

## Зачем это нужно

Системный каталог — это «база данных о базе данных»: таблицы, колонки, индексы, права, статистика планировщика. Почти любая диагностика в PostgreSQL — это запрос к `pg_*`. Эта заметка — справочник, к которому возвращаются.

## Как устроено

### Каталог = обычные таблицы

`pg_class`, `pg_attribute`, `pg_index`, `pg_type` — такие же heap-таблицы в `pg_catalog`, их можно читать обычным SQL. Есть удобные представления:

| Объект | Представление |
|---|---|
| Таблицы/индексы/sequences | `pg_class`, `pg_tables`, `pg_indexes` |
| Колонки | `pg_attribute`, `information_schema.columns` |
| Индексы | `pg_index`, `pg_indexes`, `pg_stat_user_indexes` |
| Ограничения | `pg_constraint` |
| Функции | `pg_proc` |
| Расширения | `pg_extension`, `pg_available_extensions` |
| Роли/права | `pg_roles`, `pg_authid`, `pg_class.relacl` |
| Настройки | `pg_settings` (runtime), `pg_file_settings` |
| Активность | `pg_stat_activity` |
| Статистика планировщика | `pg_statistic` → `pg_stats` |

Основные поля `pg_class`: `relname`, `relnamespace`, `relkind` (`r` таблица, `i` индекс, `v` view, `m` matview, `p` partitioned, `t` toast), `relfilenode`, `reltuples`, `relpages`, `relfrozenxid`, `reloptions` (fillfactor и пр.).

`pg_attribute`: `attrelid`, `attname`, `atttypid`, `attnum`, `attnotnull`, `attstorage` (PLAIN/EXTENDED/EXTERNAL/MAIN), `attstattarget`.

### Статистика планировщика

`ANALYZE` собирает статистику в `pg_statistic` (внутренний формат) → читаем через `pg_stats`:

| Колонка `pg_stats` | Что означает |
|---|---|
| `null_frac` | доля NULL |
| `n_distinct` | число уникальных значений (`>0` — абсолютное, `<0` — доля от строк) |
| `most_common_vals` / `most_common_freqs` | MCV-список и их частоты |
| `histogram_bounds` | границы гистограммы (по `default_statistics_target` корзин) |
| `correlation` | физическая корреляция с порядком страниц (`1` — идеально отсортировано, `0` — случайно) |
| `avg_width` | средняя ширина значения |

```sql
SELECT * FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';
-- n_distinct = 3, most_common_vals = {paid,new,shipped}, correlation = 0.01
```

**Correlation** напрямую влияет на выбор: при `correlation ≈ 1` планировщик считает index scan дешевле (страницы читаются последовательно), при `≈ 0` — дороже (random I/O).

**`default_statistics_target`** (100, максимум 10 000) — число корзин гистограммы и размер MCV-списка. Поднимают точечно:

```sql
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;
```

### Расширенная статистика (PG10+)

Обычная статистика считает колонки **независимыми**. Если `city` и `region` коррелируют, оценка `WHERE city='Москва' AND region='Москва'` будет занижена в разы.

```sql
CREATE STATISTICS st_orders_city_region (dependencies, ndistinct, mcv)
ON city, region FROM orders;

ANALYZE orders;
SELECT * FROM pg_statistic_ext_data;
-- dependencies → функциональная зависимость
-- ndistinct   → число комбинаций
-- mcv         → частые комбинации (PG12+)
```

### `pg_stat_*`: накопительная статистика

| Представление | Что показывает |
|---|---|
| `pg_stat_database` | `blks_hit/read`, `xact_commit/rollback`, `deadlocks`, `temp_files/bytes`, `tup_*` |
| `pg_stat_user_tables` | `seq_scan`, `idx_scan`, `n_live_tup`, `n_dead_tup`, `n_tup_ins/upd/del/hot_upd`, `last_vacuum/analyze` |
| `pg_stat_user_indexes` | `idx_scan`, `idx_tup_read/fetch` |
| `pg_statio_user_tables` | `heap_blks_read/hit`, `idx_blks_read/hit` |
| `pg_stat_user_functions` | время выполнения функций (если `track_functions=pl`) |
| `pg_stat_statements` | нормализованные запросы: время, вызовы, строки, буферы |
| `pg_stat_activity` | текущие сессии: `state`, `wait_event`, `xact_start`, `backend_xmin` |
| `pg_stat_bgwriter` / `pg_stat_checkpointer` | checkpoint'ы, буферы (PG17+ разделил) |
| `pg_stat_wal` (PG14+) | объём и частота WAL |
| `pg_stat_io` (PG16+) | I/O по типам объектов и контекстам |
| `pg_stat_progress_*` | прогресс vacuum, create index, analyze, copy… |
| `pg_stat_replication` | лаг реплик |
| `pg_stat_ssl`, `pg_stat_archiver`, `pg_stat_subscription` | по назначению |

Счётчики накопительные с момента старта (или `pg_stat_reset()`), поэтому смотреть надо **дельты**, а не абсолютные значения.

## Что видно в psql

```sql
-- Размеры всех таблиц
SELECT relname,
       pg_size_pretty(pg_total_relation_size(oid)) AS total,
       pg_size_pretty(pg_relation_size(oid))       AS heap,
       pg_size_pretty(pg_indexes_size(oid))        AS idx
FROM pg_class
WHERE relkind = 'r' AND relnamespace = 'public'::regnamespace
ORDER BY pg_total_relation_size(oid) DESC;

-- Топ по мусору
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 10;

-- Неиспользуемые индексы
SELECT relname, indexrelname, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;

-- Cache hit ratio по базе
SELECT datname,
       round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS hit_ratio
FROM pg_stat_database
WHERE datname = current_database();

-- Текущие настройки
SELECT name, setting, unit, source
FROM pg_settings
WHERE name IN ('shared_buffers','work_mem','random_page_cost','max_connections');

-- Кто держит долгие транзакции
SELECT pid, state, now() - xact_start AS age, left(query, 60)
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY age DESC
LIMIT 10;
```

Полезные `psql`-команды:

```
\d+ orders          структура + размеры + storage
\di+                индексы с размерами
\dn+                схемы
\df+                функции
\dp                 права
\x auto             вертикальный вывод для широких таблиц
\timing on          время выполнения
```

## Грабли и мифы

1. **`n_live_tup`/`n_dead_tup` — оценки**, а не точные числа. Для точности — `pgstattuple` или `count(*)`.
2. **`reltuples = -1`** означает «таблицу ещё не анализировали» (часто у новых секций/партиций) → плохой план.
3. **`pg_stat_*` сбрасываются при рестарте** (кроме персистентной части в PG15+). `idx_scan = 0` после рестарта ничего не значит.
4. **`pg_statistic` не читают напрямую** — формат `anyarray` внутренний, используй `pg_stats`.
5. **`correlation` — про физический порядок**, а не про уникальность. Кластеризация (`CLUSTER`) повышает её и ускоряет index scan.
6. **Расширенная статистика не создаётся автоматически**, её надо явно объявить и проанализировать.

## Эксперимент

```sql
-- 1. Как выглядит статистика колонки
CREATE TABLE stats_demo AS
SELECT (g % 10) AS grp, (g % 2) AS parity, md5(g::text) AS v
FROM generate_series(1, 100000) g;
ANALYZE stats_demo;

SELECT attname, n_distinct, correlation, most_common_vals
FROM pg_stats WHERE tablename = 'stats_demo';

-- 2. Ошибка оценки на коррелированных колонках
EXPLAIN ANALYZE SELECT * FROM stats_demo WHERE grp = 5 AND parity = 1;
-- rows (оценка) сильно меньше actual

CREATE STATISTICS st_demo (dependencies, mcv) ON grp, parity FROM stats_demo;
ANALYZE stats_demo;
EXPLAIN ANALYZE SELECT * FROM stats_demo WHERE grp = 5 AND parity = 1;
-- оценка приблизилась к реальности
```
