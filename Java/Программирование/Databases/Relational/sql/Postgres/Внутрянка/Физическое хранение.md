# Физическое хранение

## Зачем это нужно

Пока таблица — «строчки в psql», непонятно, почему `UPDATE` в два раза дороже `INSERT`, откуда берётся bloat, зачем `fillfactor` и почему индекс на `text` иногда не создаётся. Всё это — следствия устройства страницы и кортежа.

## Как устроено

### Таблица = массив страниц по 8 КБ

Файл таблицы разбит на блоки (`BLCKSZ = 8192`). Внутри файла — сегменты по 1 ГБ (`orders`, `orders.1`, `orders.2`…), чтобы не упираться в лимиты ФС.

Номер страницы + смещение внутри неё = **`ctid`** (физический адрес версии строки). Пример: `(0,1)` — страница 0, первый item pointer.

```
Страница 8 КБ:
┌──────────────┬──────────────────────────────────────────────┐
│ PageHeader   │ pd_lsn, pd_checksum, pd_flags,               │
│ 24 байта     │ pd_lower, pd_upper, pd_special               │
├──────────────┼──────────────────────────────────────────────┤
│ ItemId[]     │ массив указателей на кортежи (4 байта каждый)│
│ (растёт →)   │ offset | length | flags                      │
├──────────────┼──────────────────────────────────────────────┤
│              │          свободное место                     │
│              │        (pd_upper - pd_lower)                 │
├──────────────┼──────────────────────────────────────────────┤
│   кортежи    │ версии строк, растут навстречу указателям    │
│  (← растут)  │                                              │
└──────────────┴──────────────────────────────────────────────┘
```

### Кортеж (tuple header)

Заголовок ~23 байта + bitmap NULL-колонок + данные:

| Поле | Смысл |
|---|---|
| `xmin` | XID транзакции, создавшей версию строки |
| `xmax` | XID транзакции, удалившей/обновившей версию (0 — живая) |
| `cid` | Command id внутри транзакции |
| `ctid` | Адрес *предыдущей/следующей* версии в HOT-цепочке |
| `infomask` | Флаги: `HEAP_HASNULL`, `HEAP_UPDATED`, hint-биты (`HEAP_XMIN_COMMITTED`…) |

Hint-биты — кэш статуса транзакции прямо в кортеже, чтобы не ходить в `pg_xact` каждый раз. Выставляются «на лету» при чтении и не пишутся в WAL (потеря безопасна — просто пересчитаются).

### TOAST: как влезает строка больше 8 КБ

Строка физически не может занимать больше страницы. Если после сжатия она больше ~2 КБ (`TOAST_TUPLE_THRESHOLD = 2032`), «широкие» атрибуты уезжают в отдельную таблицу `pg_toast.pg_toast_<oid>` кусками по ~2 КБ.

Стратегии (`ALTER TABLE … ALTER COLUMN … SET STORAGE`):

| Стратегия | Сжимать | Выносить | Когда |
|---|---|---|---|
| `PLAIN` | нет | нет | фиксированные типы (`int`, `bool`) |
| `EXTENDED` (default) | да | да | текст, `jsonb`, `bytea` |
| `EXTERNAL` | нет | да | уже сжатые данные (gzip, изображения) |
| `MAIN` | да | в последнюю очередь | когда нужен быстрый доступ к части колонок |

Сжатие: `pglz` (медленнее) или `lz4` (быстрее, PG14+), `default_toast_compression`. Сжатие экономит I/O, но тратит CPU; для уже сжатых данных — `EXTERNAL`.

### FSM и VM

Два вспомогательных файла рядом с данными:

- **FSM** (`_fsm`) — Free Space Map: сколько свободного места на каждой странице. По ней `INSERT`/`UPDATE` находит страницу, куда влезет кортеж. Без FSM — sequential-поиск.
- **VM** (`_vm`) — Visibility Map: 2 бита на страницу:
  - *all-visible* — все кортежи видимы всем транзакциям (нужно для **index-only scan**);
  - *all-frozen* — все кортежи заморожены (нужно для быстрого `VACUUM`).

`VACUUM` обновляет оба файла. Если VM «пустая», index-only scan деградирует в обычный index scan с походом в heap.

### fillfactor

Сколько процентов страницы заполнять при вставке. Остаток — запас под будущие версии строки:

- heap: по умолчанию `100` (нет запаса → любая правка уводит кортеж на другую страницу);
- btree: по умолчанию `90` (запас под split).

Для таблиц с частыми `UPDATE` ставят `fillfactor = 80..90`, чтобы работал HOT (см. [[Внутрянка/MVCC и версии строк]]).

## Что видно в psql

```sql
CREATE EXTENSION IF NOT EXISTS pageinspect;

SELECT pg_relation_size('orders')  AS heap,
       pg_indexes_size('orders')   AS indexes,
       pg_total_relation_size('orders') AS total;

-- Заголовок страницы 0
SELECT * FROM page_header(get_raw_page('orders', 0));

-- Кортежи на странице 0: lp, lp_off, lp_len, t_xmin, t_xmax, t_ctid
SELECT lp, lp_off, lp_len, t_xmin, t_xmax, t_ctid,
       t_infomask2, t_infomask, t_data
FROM heap_page_items(get_raw_page('orders', 0));

-- Размер одной строки и вклад TOAST
SELECT pg_column_size(t.*) FROM orders t LIMIT 1;
```

Размеры:

```sql
SELECT pg_size_pretty(pg_relation_size('orders'));        -- только heap
SELECT pg_size_pretty(pg_total_relation_size('orders'));  -- heap + индексы + toast
```

## Грабли и мифы

1. **`DELETE` не уменьшает файл.** Место помечается как переиспользуемое; файл уменьшается только при `VACUUM FULL`/`pg_repack` или при отсечении «хвостовых» пустых страниц обычным `VACUUM`.
2. **`fillfactor=100` на heap — норма для OLTP-вставок, но вредна для «горячих» строк.** Постоянные `UPDATE` без запаса → новые страницы → bloat и рост индексов.
3. **Индексная запись тоже ограничена размером.** B-tree не проиндексирует значение длиннее ~2704 байт (`1/3` страницы). Для длинных `text` — хэш/`md5()`, `pg_trgm` или GIN.
4. **TOAST не участвует в основном heap.** `SELECT *` по таблице с большими колонками читает TOAST только для выбранных колонок; `SELECT *` тянет всё.
5. **`pg_relation_size` ≠ размер на диске после `DELETE`.** Он показывает размер файлов, а не количество живых данных.
6. **`ctid` меняется после `UPDATE`/`VACUUM FULL`.** Использовать `ctid` как идентификатор строки нельзя.

## Эксперимент

```sql
CREATE TABLE t_demo (id int, payload text);
INSERT INTO t_demo
SELECT g, repeat('x', 3000) FROM generate_series(1, 1000) g;

SELECT pg_size_pretty(pg_relation_size('t_demo'));       -- ~3.5 MB (TOAST + сжатие)
SELECT pg_size_pretty(pg_total_relation_size('t_demo')); -- больше, из-за toast

-- Посмотреть, что уехало в TOAST
SELECT relname, pg_size_pretty(pg_relation_size(oid))
FROM pg_class WHERE relnamespace = 'pg_toast'::regnamespace;

-- Удалить половину и сравнить
DELETE FROM t_demo WHERE id % 2 = 0;
SELECT pg_size_pretty(pg_relation_size('t_demo'));       -- размер не изменился!
VACUUM t_demo;
SELECT pg_size_pretty(pg_relation_size('t_demo'));       -- может не измениться
VACUUM FULL t_demo;                                      -- а вот тут уменьшится
```
