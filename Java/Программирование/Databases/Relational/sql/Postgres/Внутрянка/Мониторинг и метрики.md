# Мониторинг и метрики

## Зачем это нужно

Оптимизация без мониторинга — это реакция на жалобы. Мониторинг нужен, чтобы: находить деградацию до пользователей, понимать, куда уходит время, и не гадать при инциденте. Здесь — минимум метрик, которые надо собирать, и готовые запросы.

## Как устроено

### Уровни мониторинга

| Уровень | Что смотрим | Инструмент |
|---|---|---|
| **ОС** | CPU, память, диск (IOPS/latency), сеть | node_exporter, iostat, vmstat |
| **PostgreSQL** | соединения, запросы, кэш, локи, WAL, репликация | `pg_stat_*`, `pg_stat_statements` |
| **Запросы** | топ по времени/частоте, планы | `pg_stat_statements`, `auto_explain`, логи |
| **Бизнес** | latency API, ошибки, очереди | APM, приложение |

### Что обязательно собирать

| Метрика | Запрос | Тревога |
|---|---|---|
| Cache hit ratio | `blks_hit / (blks_hit + blks_read)` | < 99% на OLTP |
| Connections | `count(*) FROM pg_stat_activity` | > 80% `max_connections` |
| Долгие транзакции | `now() - xact_start` | > 5 мин |
| `idle in transaction` | `state LIKE 'idle in transaction%'` | > 1 мин |
| Deadlocks | `pg_stat_database.deadlocks` | рост > 0 |
| Temp files | `temp_files`, `temp_bytes` | резкий рост |
| WAL | `pg_stat_wal.wal_records`, `wal_bytes` | аномалии |
| Checkpoints | `pg_stat_bgwriter` / `pg_stat_checkpointer` | слишком частые |
| Autovacuum | `last_autovacuum`, `n_dead_tup` | мусор растёт |
| XID age | `age(datfrozenxid)` | > 1.5 млрд |
| Replication lag | `pg_stat_replication.replay_lag` | > N сек |
| Slots WAL | `pg_replication_slots` retained | > N ГБ |
| Bloat | `pgstattuple_approx` | dead > 20–30% |
| Размер БД/таблиц | `pg_database_size`, `pg_total_relation_size` | резкий рост |
| Ошибки | лог | `ERROR`, `FATAL`, `PANIC` |

### `pg_stat_activity`: главный экран

```sql
SELECT pid,
       usename,
       datname,
       state,
       wait_event_type,
       wait_event,
       now() - xact_start   AS xact_age,
       now() - query_start  AS query_age,
       now() - state_change AS state_age,
       left(query, 80)      AS query
FROM pg_stat_activity
WHERE backend_type = 'client backend'
ORDER BY xact_age DESC NULLS LAST;
```

Что означает:

- `state = idle in transaction` + большой `state_age` — забытая транзакция;
- `wait_event_type = Lock` — блокировка ([[Внутрянка/Конкурентность на практике]]);
- `wait_event_type = IO` — диск;
- `query_age` большой, а `state = active` — запрос реально работает долго.

### `pg_stat_statements`: топ запросов

```sql
SELECT queryid, calls,
       round(total_exec_time::numeric, 1)  AS total_ms,
       round(mean_exec_time::numeric, 2)   AS mean_ms,
       round(stddev_exec_time::numeric, 2) AS stddev_ms,
       rows,
       shared_blks_hit, shared_blks_read,
       temp_blks_written,
       wal_bytes,
       left(query, 120)
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

Смотреть не только `total_exec_time`:

- `mean_exec_time` — дорогие единичные запросы;
- `calls` — много мелких (N+1);
- `temp_blks_written` — сортировки/хэши на диск;
- `shared_blks_read` — реальный I/O;
- `wal_bytes` — нагрузка на запись.

`pg_stat_statements` сбрасывается `pg_stat_statements_reset()`; статистика копится с момента старта.

### `pg_stat_io` (PG16+)

Детальная статистика I/O по типам объектов и контекстам:

```sql
SELECT backend_type, object, context,
       reads, read_bytes, writes, write_bytes,
       extends, hits, evictions, fsyncs
FROM pg_stat_io
ORDER BY reads DESC;
```

Позволяет увидеть, кто именно читает с диска: `client backend`, `autovacuum worker`, `checkpointer`, `walwriter`, `background writer`.

### Логи

```conf
log_min_duration_statement = '500ms'
log_checkpoints = on
log_lock_waits = on
log_temp_files = 0
log_autovacuum_min_duration = '1s'
log_line_prefix = '%m [%p] %q%u@%d '
log_error_verbosity = default
```

Анализ:

- **pgBadger** — HTML-отчёт по логам;
- **pgCluu**;
- grep по `ERROR`, `FATAL`, `deadlock`, `temporary file`.

### Инструменты

| Инструмент | Назначение |
|---|---|
| **pg_stat_statements** | обязательное расширение |
| **auto_explain** | планы медленных запросов в лог |
| **pg_stat_kcache** | CPU и реальный I/O по запросам |
| **pg_wait_sampling** | сэмплирование wait events |
| **pg_qualstats** | какие предикаты чаще всего выполняются |
| **pg_store_plans** | планы запросов |
| **postgres_exporter + Prometheus + Grafana** | стандартный стек |
| **pgBadger** | разбор логов |
| **pg_activity / pg_top** | live-мониторинг |
| **check_postgres** | Nagios-совместимые проверки |

### Алерты: минимальный набор

1. Диск < 15% свободного.
2. `pg_wal` растёт аномально / слот держит WAL.
3. Репликационный лаг > 30 сек.
4. `age(datfrozenxid)` > 1.5 млрд.
5. Соединения > 80% лимита.
6. Deadlocks растут.
7. Cache hit ratio падает ниже 99%.
8. Долгие транзакции/`idle in transaction` > 5 мин.
9. Checkpoint'ы чаще, чем раз в минуту.
10. Temp-файлы растут (нехватка `work_mem`).
11. Ошибки в логе (`FATAL`, `PANIC`, `deadlock detected`).

## Что видно в psql

```sql
-- 1. Обзор базы
SELECT datname,
       numbackends,
       xact_commit, xact_rollback,
       blks_read, blks_hit,
       round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS hit_pct,
       temp_files, pg_size_pretty(temp_bytes) AS temp,
       deadlocks,
       pg_size_pretty(pg_database_size(datname)) AS size
FROM pg_stat_database
WHERE datname IS NOT NULL;

-- 2. Таблицы: активность и мусор
SELECT relname, seq_scan, idx_scan, n_live_tup, n_dead_tup,
       n_tup_ins, n_tup_upd, n_tup_hot_upd,
       last_vacuum, last_autovacuum, last_analyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 15;

-- 3. Индексы: не используются?
SELECT relname, indexrelname, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
ORDER BY idx_scan, pg_relation_size(indexrelid) DESC
LIMIT 20;

-- 4. Возраст XID
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;

-- 5. WAL
SELECT wal_records, wal_fpi, pg_size_pretty(wal_bytes), wal_buffers_full
FROM pg_stat_wal;

-- 6. Checkpoints (PG17+)
SELECT num_timed, num_requested, write_time, sync_time, buffers_written
FROM pg_stat_checkpointer;
```

## Грабли и мифы

1. **Счётчики накопительные** — абсолютные значения бесполезны, нужны **дельты** (rate). `idx_scan = 0` после рестарта ничего не значит.
2. **Средние скрывают хвост.** Запрос с `mean=10ms` может иметь p99=5s. Нужны гистограммы/логи медленных запросов.
3. **`pg_stat_statements` не видит планы** — только текст и агрегаты. Для планов — `auto_explain`.
4. **Cache hit ratio 99% может быть плохо** при огромном объёме чтений: 1% от миллиарда страниц — это много.
5. **`pg_stat_activity` — мгновенный снимок.** Проблема длиной 200 мс может не попасть; нужен сэмплинг (`pg_wait_sampling`) или логи.
6. **Мониторинг без алертов** — просто красивые графики. Настрой пороги.
7. **Сбор статистики сам создаёт нагрузку**: `track_io_timing`, `pg_stat_statements` с большим `max`, частые опросы — держи в разумных пределах.

## Эксперимент

```sql
-- 1. Снять дельту за интервал
SELECT now() AS t, xact_commit, blks_read, blks_hit, temp_files
FROM pg_stat_database WHERE datname = current_database() \gset before_

SELECT pg_sleep(60);

SELECT xact_commit - :before_xact_commit AS commits_per_min,
       blks_read   - :before_blks_read   AS reads_per_min,
       temp_files  - :before_temp_files  AS temp_files_per_min
FROM pg_stat_database WHERE datname = current_database();

-- 2. Включить auto_explain в сессии (если расширение загружено)
LOAD 'auto_explain';
SET auto_explain.log_min_duration = 0;
SET auto_explain.log_analyze = on;

-- 3. Посмотреть прогресс длительной операции
SELECT * FROM pg_stat_progress_create_index;
```
