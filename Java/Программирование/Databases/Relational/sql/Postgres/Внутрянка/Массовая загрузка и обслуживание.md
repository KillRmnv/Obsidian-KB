# Массовая загрузка и обслуживание

## Зачем это нужно

Загрузить 100 млн строк через `INSERT` в цикле — часы. Через `COPY` — минуты. Но массовая загрузка меняет поведение системы: WAL, autovacuum, индексы, репликация. Здесь — как грузить быстро и не развалить кластер.

## Как устроено

### COPY — самый быстрый путь

```sql
-- Серверный COPY (файл на сервере, нужны права)
COPY orders FROM '/data/orders.csv' WITH (FORMAT csv, HEADER true);

-- Клиентский \copy (файл на клиенте)
\copy orders FROM 'orders.csv' WITH (FORMAT csv, HEADER true)

-- Из программы (JDBC: CopyManager, Npgsql: BeginTextImport)
COPY orders (id, user_id, total) FROM STDIN WITH (FORMAT csv);
```

Почему быстрее `INSERT`:

- одна команда на весь батч, без parse/plan на каждую строку;
- меньше round-trip;
- меньше WAL-записей на строку (группировка);
- нет триггеров на каждую строку, если их отключить.

`COPY` с `FREEZE` (PG9.4+):

```sql
COPY big_table FROM STDIN WITH (FREEZE true);
-- все загруженные строки сразу «заморожены», vacuum не нужен
-- работает, только если таблица создана в этой же транзакции или пуста
```

### Порядок операций при большой загрузке

1. **Убрать индексы** (кроме PK, если нужен для FK) — вставка без индексов в разы быстрее.
2. **Отключить триггеры/проверки FK** (суперпользователь):

```sql
ALTER TABLE orders DISABLE TRIGGER ALL;
-- или (шире):
SET session_replication_role = replica;  -- отключает FK/триггеры
```

3. **Загрузить `COPY`** батчами по 10–50 тыс. строк в отдельных транзакциях (не одна гигантская — иначе WAL и bloat).
4. **Включить обратно** триггеры, `session_replication_role = origin`.
5. **Создать индексы** (`maintenance_work_mem` побольше, `max_parallel_maintenance_workers`).
6. **`ANALYZE`** — обязательно, иначе план будет строиться на `reltuples = -1`.
7. **`VACUUM`** — если были `UPDATE`/`DELETE`.

### Настройки на время загрузки

| Параметр | Значение | Зачем |
|---|---|---|
| `synchronous_commit` | `off` (в сессии) | не ждать fsync на каждый батч |
| `maintenance_work_mem` | `1–2GB` | быстрее `CREATE INDEX`/`VACUUM` |
| `max_wal_size` | `8GB+` | реже checkpoint'ы |
| `wal_level` | `minimal` + `COPY` в той же транзакции, что `CREATE TABLE` | без WAL для новой таблицы (несовместимо с репликацией) |
| `autovacuum` | можно отключить на таблице на время | не мешает |
| `max_parallel_maintenance_workers` | 2–4 | параллельное построение индексов |

```sql
BEGIN;
SET LOCAL synchronous_commit = off;
CREATE TABLE new_orders (LIKE orders INCLUDING ALL);
COPY new_orders FROM STDIN;
COMMIT;
```

`wal_level=minimal` требует: таблица создана в той же транзакции, нет реплик, `max_wal_senders=0`. На практике чаще используют `replica` и просто батчи.

### UNLOGGED-таблицы

```sql
CREATE UNLOGGED TABLE staging.orders_raw (LIKE orders);
```

- не пишут WAL → быстрее в разы;
- **не переживают краш** (при рестарте очищаются);
- **не реплицируются** на standby;
- хороши как промежуточный слой: `COPY` → `UNLOGGED` → `INSERT … SELECT` в основную таблицу.

### Партиции: загрузка и attach

```sql
-- 1. Создать отдельную таблицу с той же структурой
CREATE TABLE orders_2026_03 (LIKE orders INCLUDING ALL);

-- 2. Загрузить в неё (быстро, без партиционного overhead)
COPY orders_2026_03 FROM …;

-- 3. Добавить CHECK, чтобы ATTACH не сканировал
ALTER TABLE orders_2026_03 ADD CONSTRAINT chk_range
  CHECK (created_at >= '2026-03-01' AND created_at < '2026-04-01');

-- 4. Присоединить
ALTER TABLE orders ATTACH PARTITION orders_2026_03
  FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');
```

`ATTACH PARTITION` берёт `SHARE UPDATE EXCLUSIVE` на родителя (не блокирует чтение/запись), но при отсутствии `CHECK` — сканирует таблицу.

### Обслуживание больших таблиц

| Задача | Инструмент | Блокировка |
|---|---|---|
| Вернуть место ОС | `VACUUM FULL` | `ACCESS EXCLUSIVE` |
| Вернуть место онлайн | `pg_repack` | короткая в конце |
| Перестроить индекс | `REINDEX INDEX CONCURRENTLY` (PG12+) | без блокировки записи |
| Создать индекс онлайн | `CREATE INDEX CONCURRENTLY` | `SHARE UPDATE EXCLUSIVE` |
| Пересортировать физически | `CLUSTER` | `ACCESS EXCLUSIVE` |
| Обновить статистику | `ANALYZE` | `SHARE UPDATE EXCLUSIVE` |
| Заморозить | `VACUUM (FREEZE)` | как обычный vacuum |

`pg_repack` требует расширения и свободного места ≈ размер таблицы; работает через триггеры и логическую репликацию изменений.

### Очистка старых данных

```sql
-- Плохо: миллионы DELETE → bloat + WAL + autovacuum
DELETE FROM logs WHERE created_at < now() - interval '90 days';

-- Хорошо: партиции
DROP TABLE logs_2025_01;          -- мгновенно
-- или отсоединить и удалить
ALTER TABLE logs DETACH PARTITION logs_2025_01 CONCURRENTLY;  -- PG14+
DROP TABLE logs_2025_01;
```

### TRUNCATE vs DELETE

| | `DELETE` | `TRUNCATE` |
|---|---|---|
| WAL | на каждую строку | почти нет |
| Блокировка | `ROW EXCLUSIVE` | `ACCESS EXCLUSIVE` |
| Триггеры | срабатывают | нет (кроме `ON TRUNCATE`) |
| Возврат места | нет | да |
| Условие | `WHERE` | только вся таблица/партиция |

## Что видно в psql

```sql
-- Прогресс COPY / CREATE INDEX / VACUUM
SELECT * FROM pg_stat_progress_copy;
SELECT * FROM pg_stat_progress_create_index;
SELECT * FROM pg_stat_progress_vacuum;

-- Оценка объёма WAL для загрузки
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0'));

-- Не залипли ли индексы в INVALID
SELECT indexrelid::regclass, indisvalid FROM pg_index WHERE NOT indisvalid;

-- Статистика после загрузки
ANALYZE orders;
SELECT reltuples, relpages FROM pg_class WHERE relname = 'orders';
```

## Грабли и мифы

1. **Одна гигантская транзакция** на 100 млн строк → огромный WAL, долгий rollback, bloat, блокировки. Лучше батчи.
2. **`INSERT` в цикле** — худший вариант: parse/plan на каждую строку. `COPY` или `INSERT … SELECT`.
3. **Забыть `ANALYZE`** после загрузки → `reltuples = -1`, planner строит катастрофические планы.
4. **`wal_level=minimal`** несовместим с репликацией и требует особых условий; не включай «на всякий случай».
5. **`UNLOGGED`** теряет данные при краше и не реплицируется — только staging.
6. **`CREATE INDEX` после загрузки** быстрее, чем инкрементальное обновление индекса на каждой вставке.
7. **`VACUUM FULL` в рабочие часы** = простой; используй `pg_repack`.
8. **`DELETE` без vacuum** не возвращает место, а `DROP PARTITION` — мгновенный и без WAL.

## Эксперимент

```sql
-- 1. COPY vs INSERT (1 млн строк, одна колонка)
CREATE TABLE load_copy (id int);
\timing on
INSERT INTO load_copy SELECT generate_series(1, 1000000);
TRUNCATE load_copy;
COPY load_copy FROM PROGRAM 'seq 1 1000000';   -- нужен суперпользователь

-- 2. Загрузка без индексов
CREATE TABLE load_no_idx (id int, v text);
COPY load_no_idx FROM STDIN;
-- … данные …
CREATE INDEX ON load_no_idx (id);

-- 3. Партиция через ATTACH
CREATE TABLE part_demo (id int, created_at date) PARTITION BY RANGE (created_at);
CREATE TABLE part_new (LIKE part_demo INCLUDING ALL);
ALTER TABLE part_new ADD CONSTRAINT chk CHECK (created_at >= '2026-01-01' AND created_at < '2026-02-01');
INSERT INTO part_new SELECT g, '2026-01-15' FROM generate_series(1, 100000) g;
ALTER TABLE part_demo ATTACH PARTITION part_new FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
```
