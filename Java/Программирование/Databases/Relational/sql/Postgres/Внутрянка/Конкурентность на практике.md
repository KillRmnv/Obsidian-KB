# Конкурентность на практике

## Зачем это нужно

Теория локов объясняет, *что* блокируется. Практика — *почему прод встал*: миграция взяла `ACCESS EXCLUSIVE` и встала в очередь, `idle in transaction` держит vacuum, горячая строка превращает `UPDATE` в сериализованную очередь. Здесь — рабочие приёмы и готовые паттерны.

## Как устроено

### Как читать ожидания

`pg_stat_activity.wait_event_type` / `wait_event` — главный индикатор:

| `wait_event_type` | Что означает | Типичная причина |
|---|---|---|
| `Lock` | ждёт блокировку объекта | DDL, `UPDATE` той же строки, FK |
| `LWLock` | лёгкая внутренняя блокировка | конкуренция за буферы/WAL (`WALWrite`, `BufferContent`) |
| `IO` | ждёт диск | медленный диск, холодный кэш |
| `Client` | ждёт клиента | сеть, приложение не читает результат |
| `IPC` | ждёт другой процесс | параллельные воркеры, `pg_sleep`, replication |
| `Timeout` | таймер | `pg_sleep`, `statement_timeout` |
| `BufferPin` | ждёт страницу | редкая внутренняя ситуация |

`state`:

- `active` — выполняет запрос;
- `idle` — ждёт следующего запроса (нормально);
- `idle in transaction` — **опасно**: открыта транзакция, держит снапшот и локи;
- `idle in transaction (aborted)` — то же, но с ошибкой.

### Кто кого блокирует

```sql
-- Прямые блокировщики
SELECT pid, pg_blocking_pids(pid) AS blockers, wait_event_type, left(query, 60)
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- Корень цепочки: найти бэкенд, который никого не ждёт
SELECT a.pid, a.state, a.query,
       pg_blocking_pids(a.pid) AS blocked_by
FROM pg_stat_activity a
WHERE a.pid IN (
  SELECT unnest(pg_blocking_pids(pid)) FROM pg_stat_activity
  WHERE cardinality(pg_blocking_pids(pid)) > 0
)
AND cardinality(pg_blocking_pids(a.pid)) = 0;
```

Корень — обычно забытая транзакция или миграция. `pg_terminate_backend(pid)` — крайняя мера.

### DDL и очередь блокировок

`ALTER TABLE` берёт `ACCESS EXCLUSIVE`. Если перед ним в очереди стоит длинный `SELECT` (держит `ACCESS SHARE`), `ALTER` ждёт. Но за `ALTER` в очередь встают **все** новые запросы, даже `SELECT` — потому что очередь FIFO.

Итог: одна «быстрая» миграция блокирует таблицу на всё время длинного `SELECT`.

Правило для миграций:

```sql
SET lock_timeout = '3s';
SET statement_timeout = '30s';
-- если не удалось — повторить позже, а не ждать
```

Дополнительно:

- `CREATE INDEX CONCURRENTLY` — без `SHARE`;
- `ALTER TABLE … ADD COLUMN … DEFAULT` — быстро (PG11+), но лок всё равно берётся на мгновение;
- `VALIDATE CONSTRAINT` — `SHARE UPDATE EXCLUSIVE`, не блокирует запись;
- `VACUUM FULL` — `ACCESS EXCLUSIVE`, только в окно обслуживания.

### Горячие строки

```sql
UPDATE counters SET value = value + 1 WHERE id = 42;
```

Все транзакции выстраиваются в очередь на одну строку. Это не deadlock, а **сериализация**.

Решения:

- **шардирование счётчика**: `N` строк `(id, shard)`, `UPDATE … WHERE id=42 AND shard = random(0..N-1)`, чтение — `SUM`;
- **асинхронный агрегат** (Redis/очередь + периодический flush);
- **`INSERT` событий** вместо `UPDATE`, агрегация позже;
- **advisory lock** только если нужна настоящая сериализация.

### Очередь на `FOR UPDATE SKIP LOCKED`

Классический паттерн для воркеров:

```sql
BEGIN;
WITH picked AS (
  SELECT id FROM jobs
  WHERE status = 'pending'
  ORDER BY created_at
  LIMIT 10
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs SET status = 'processing'
WHERE id IN (SELECT id FROM picked)
RETURNING id;
COMMIT;
```

`SKIP LOCKED` — воркеры не ждут друг друга и не берут одну задачу дважды. Без `SKIP LOCKED` они бы сериализовались.

### Идемпотентность и upsert

```sql
INSERT INTO users (email, name) VALUES ($1, $2)
ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name
RETURNING id;
```

- `ON CONFLICT DO NOTHING` — без блокировки на конфликтующих строках (но `DO UPDATE` блокирует);
- при высокой конкуренции `ON CONFLICT` может давать deadlock'и — сортируй входные данные по ключу;
- `MERGE` (PG15+) — для сложных сценариев, но осторожно с конкурентностью.

### Optimistic locking

```sql
UPDATE accounts SET balance = balance - 100, version = version + 1
WHERE id = 42 AND version = 7;
-- 0 строк → кто-то изменил, повторить
```

Не блокирует строку на время «подумать», но требует retry в приложении.

### Пул соединений

- **PgBouncer transaction mode** — соединение возвращается в пул после `COMMIT`;
- нельзя: `SET` на сессию без сброса, `LISTEN/NOTIFY`, session advisory locks, временные таблицы, `PREPARE` (до 1.21);
- `max_client_conn` может быть большим, `default_pool_size` — небольшим (10–20 на CPU-ядро).

Правило: **активных запросов должно быть примерно столько, сколько ядер**; остальное — очередь в пуле.

### Сериализационные ошибки: retry

`REPEATABLE READ`/`SERIALIZABLE` могут вернуть:

```
ERROR: could not serialize access due to concurrent update
ERROR: could not serialize access due to read/write dependencies
```

Это **штатное** поведение. Приложение обязано повторять транзакцию (с экспоненциальной задержкой, ограниченным числом попыток). Без retry — «случайные» 500-е.

## Что видно в psql

```sql
-- 1. Кто чего ждёт и сколько
SELECT pid, state, wait_event_type, wait_event,
       now() - xact_start AS xact_age,
       now() - state_change AS state_age,
       left(query, 80)
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY xact_age DESC NULLS LAST;

-- 2. Блокировки по объектам
SELECT mode, granted, count(*)
FROM pg_locks GROUP BY 1,2 ORDER BY 3 DESC;

-- 3. Долгие idle-in-transaction
SELECT pid, now() - state_change AS idle_age, left(query, 80)
FROM pg_stat_activity
WHERE state LIKE 'idle in transaction%'
ORDER BY idle_age DESC;

-- 4. Готовый запрос «дерево ожиданий»
SELECT pid, pg_blocking_pids(pid) AS blockers, wait_event, left(query, 50)
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- 5. Таймауты на всякий случай
SET lock_timeout = '3s';
SET idle_in_transaction_session_timeout = '60s';
```

## Грабли и мифы

1. **«Блокировка» ≠ «deadlock»**. Deadlock — частный случай, который сервер сам разрешает через `deadlock_timeout`.
2. **Убийство сессии не откатывает транзакцию мгновенно** — сначала rollback, потом освобождение локов.
3. **`pg_terminate_backend` на postmaster/aux-процессе** может уронить сервер. Убивай только `client backend`.
4. **Очередь локов FIFO** — «быстрый» `ALTER` может заблокировать всё, если перед ним длинный читатель.
5. **`FOR UPDATE` без `SKIP LOCKED`** в очереди задач = сериализация воркеров.
6. **`idle in transaction`** не «просто висит» — он держит `xmin` и мешает vacuum.
7. **Retry обязателен** для `SERIALIZABLE`/`REPEATABLE READ`: ошибки сериализации — не баг, а контракт.
8. **Больше соединений ≠ больше throughput**. После насыщения CPU добавление соединений только увеличивает latency.

## Эксперимент

```sql
-- 1. Очередь на строку
CREATE TABLE hot (id int primary key, v int);
INSERT INTO hot VALUES (1, 0);
-- Сессия A: BEGIN; UPDATE hot SET v=v+1 WHERE id=1; SELECT pg_sleep(30);
-- Сессия B: UPDATE hot SET v=v+1 WHERE id=1;   -- ждёт
-- Смотрим: wait_event_type='Lock', pg_blocking_pids

-- 2. SKIP LOCKED
CREATE TABLE jobs (id serial primary key, status text default 'pending');
INSERT INTO jobs (status) SELECT 'pending' FROM generate_series(1, 100);
-- Две сессии одновременно:
BEGIN;
SELECT id FROM jobs WHERE status='pending' LIMIT 5 FOR UPDATE SKIP LOCKED;
-- обе получат РАЗНЫЕ строки, без ожидания
ROLLBACK;

-- 3. Deadlock
-- A: UPDATE hot SET v=1 WHERE id=1; затем id=2
-- B: UPDATE hot SET v=2 WHERE id=2; затем id=1
-- через ~1s: ERROR: deadlock detected

-- 4. DDL и lock_timeout
SET lock_timeout = '500ms';
-- при долгом SELECT в другой сессии:
ALTER TABLE hot ADD COLUMN x int;  -- ERROR: canceling statement due to lock timeout
```
