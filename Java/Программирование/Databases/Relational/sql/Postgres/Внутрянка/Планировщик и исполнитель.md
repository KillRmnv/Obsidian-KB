# Планировщик и исполнитель

## Зачем это нужно

`EXPLAIN` — это отчёт планировщика о том, **почему** он выбрал такой план. Без понимания cost model и путей доступа чтение планов превращается в гадание. Здесь — как запрос превращается в план и как план исполняется.

## Как устроено

### Конвейер

```
SQL
 │  parser            синтаксис → дерево разбора
 ▼
parse tree
 │  analyzer/rewrite  имена, типы, права; правила и views
 ▼
query tree
 │  planner           перебор путей (paths), оценка стоимости
 ▼
plan tree (Plan nodes)
 │  executor          выполняет узлы, тянет кортежи вверх
 ▼
результат
```

Планировщик **не ищет оптимальный план**, а выбирает самый дешёвый из рассмотренных. Отсюда ошибки: плохая статистика → неверная оценка `rows` → неверный выбор join/scan.

### Cost model

Стоимость — в условных единицах, где `1.0` ≈ чтение одной страницы с диска последовательно.

| Параметр | Default | Смысл |
|---|---|---|
| `seq_page_cost` | `1.0` | последовательное чтение страницы |
| `random_page_cost` | `4.0` | случайное чтение страницы (SSD → `1.1`) |
| `cpu_tuple_cost` | `0.01` | обработка одной строки |
| `cpu_index_tuple_cost` | `0.005` | обработка записи индекса |
| `cpu_operator_cost` | `0.0025` | одна операция/функция |
| `parallel_setup_cost` | `1000` | запуск параллельных воркеров |
| `parallel_tuple_cost` | `0.1` | передача строки от воркера |

Формулы (упрощённо):

```
Seq Scan:      pages * seq_page_cost + rows * cpu_tuple_cost
Index Scan:    index_pages * random_page_cost + rows * cpu_index_tuple_cost
               + heap_pages * random_page_cost + rows * cpu_tuple_cost
```

Планировщик сравнивает **полные стоимости** — включая стоимость доставки результата наверх (иногда «дешёвый» путь проигрывает из-за `LIMIT`/сортировки).

### Узлы сканирования

| Узел | Когда выбирается |
|---|---|
| `Seq Scan` | нужно прочитать большую долю таблицы (>~5–10%), таблица маленькая |
| `Index Scan` | высокая селективность, нужен порядок по индексу, `LIMIT` |
| `Index Only Scan` | все нужные колонки в индексе + страница all-visible |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | средняя селективность, много страниц; битмап сортирует `ctid` → меньше random I/O |
| `TID Scan` | `WHERE ctid = …` |
| `Function Scan`, `Values Scan`, `CTE Scan`, `Subquery Scan` | соответствующие конструкции |

Bitmap heap scan бывает **lossy**: если битмапа не влезла в `work_mem`, страницы помечаются «возможно, есть совпадения» и перепроверяются (`Rows Removed by Filter`, `Heap Blocks: exact/lossy`).

### Соединения

| Метод | Как работает | Когда хорош | Когда плох |
|---|---|---|---|
| **Nested Loop** | для каждой внешней строки ищет внутренние | мало внешних строк + индекс на внутренней | внешних много → миллионы index lookup |
| **Hash Join** | строит хэш по меньшей таблице, сканирует большую | большие таблицы без индексов, `=` | не хватило `work_mem` → батчи на диск |
| **Merge Join** | сортирует обе стороны и сливает | обе стороны уже отсортированы (индексы) | нужна дорогая сортировка |

В плане `Hash Join` всегда показывает `Hash` (build side) — обычно это **меньшая** сторона. `Batches > 1` означает, что хэш не влез в память и пишется во временные файлы.

### Агрегация, сортировка, параллелизм

- `HashAggregate` — хэш-таблица групп, требует `work_mem`; `GroupAggregate` — по отсортированным данным.
- `Sort` — quicksort в памяти; при нехватке — external merge sort с temp-файлами (`Sort Method: external merge Disk: …kB`).
- `Gather` / `Gather Merge` — сбор результатов параллельных воркеров; `Parallel Seq Scan`, `Parallel Hash Join`.
- `JIT` (LLVM) — компиляция выражений, включается при `jit_above_cost` (100 000). На коротких запросах только вредит.

### Параллельные запросы: ограничители

```sql
SET max_parallel_workers_per_gather = 4;   -- default 2
SET min_parallel_table_scan_size = '8MB';
SET parallel_setup_cost = 1000;
-- отключить для отладки:
SET max_parallel_workers_per_gather = 0;
```

Планировщик включает параллелизм, если таблица большая и стоимость окупает запуск воркеров.

### `enable_*` — только для отладки

`enable_seqscan`, `enable_indexscan`, `enable_hashjoin`… не отключают метод, а **сильно завышают его стоимость**. Использовать только чтобы проверить гипотезу «а если без seq scan», и никогда — в проде.

## Что видно в psql

```sql
EXPLAIN (ANALYZE, BUFFERS, SETTINGS)
SELECT …;
```

Читаем план **изнутри наружу**: самые глубокие узлы выполняются первыми, результат поднимается вверх.

```
Hash Join  (cost=… rows=… width=…) (actual time=… rows=… loops=1)
  Hash Cond: (o.user_id = u.id)
  Buffers: shared hit=1234 read=56
  ->  Seq Scan on orders o  (cost=… rows=100000) (actual time=0.02..45.1 rows=100000 loops=1)
        Filter: (status = 'paid')
        Rows Removed by Filter: 900000
  ->  Hash  (cost=… rows=10000) (actual time=… loops=1)
        Buckets: 16384  Batches: 1  Memory Usage: 1024kB
        ->  Seq Scan on users u  ...
```

Что искать:

- **`rows` (оценка) vs `actual rows`** — расхождение >10× = проблема статистики;
- **`loops`** — `actual time` указан *на один цикл*; умножать на loops;
- **`Rows Removed by Filter`** — индекс/фильтр работает вхолостую;
- **`Buffers: read`** — сколько реально читалось с диска;
- **`Sort Method: external merge`** — не хватило `work_mem`;
- **`Heap Fetches`** у Index Only Scan — VM не обновлена;
- **`Batches > 1`** у Hash — хэш не влез в память.

## Грабли и мифы

1. **`cost` — не время.** Это условные единицы. Сравнивать cost между разными запросами бессмысленно.
2. **Планировщик ошибается не «из вредности»** — обычно из-за устаревшей статистики, коррелированных колонок или функций в `WHERE`.
3. **`EXPLAIN` без `ANALYZE` не выполняет запрос** — и не показывает реальные строки. Для диагностики почти всегда нужен `ANALYZE, BUFFERS`.
4. **`EXPLAIN ANALYZE` выполняет запрос**, включая `DELETE`/`UPDATE`. Оборачивай в `BEGIN … ROLLBACK`.
5. **План зависит от значений в `WHERE`** (custom plan) и от `plan_cache_mode` для prepared statements. Generic plan может быть хуже.
6. **`work_mem` действует на каждый узел**, а не на запрос: 3 сортировки × 64 МБ = 192 МБ на один запрос.
7. **Параллелизм не всегда ускоряет**: на маленьких таблицах `Gather` дороже выигрыша.

## Эксперимент

```sql
CREATE TABLE plan_demo AS
SELECT g AS id, (g % 100) AS grp, md5(g::text) AS payload
FROM generate_series(1, 1_000_000) g;
ANALYZE plan_demo;

-- 1. Маленькая выборка → Index Scan; большая → Seq Scan
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM plan_demo WHERE id = 500;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM plan_demo WHERE id > 100;

-- 2. Оценка vs реальность
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM plan_demo WHERE grp = 42;

-- 3. Проверить гипотезу «мешает seq scan»
SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM plan_demo WHERE grp = 42;
RESET enable_seqscan;

-- 4. Стоимость сортировки и work_mem
SET work_mem = '64kB';
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM plan_demo ORDER BY payload;
RESET work_mem;
```
