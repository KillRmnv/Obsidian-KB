# Индексы изнутри

## Зачем это нужно

«Добавь индекс» — самый популярный совет и самая частая ошибка. Индекс ускоряет чтение, но замедляет запись, занимает место и требует WAL. Чтобы выбирать осознанно, нужно знать, как устроен B-tree, почему index-only scan не всегда работает и чем GIN отличается от BRIN.

## Как устроено

### B-tree: страницы, ключи, split

B-tree — сбалансированное дерево, где листья связаны в двусвязный список:

```
                [ metapage: root, level ]
                            │
                 ┌──────────▼──────────┐
                 │  internal page      │  ключи-разделители + указатели
                 └──────┬───────┬──────┘
            ┌───────────▼─┐   ┌─▼───────────┐
            │  leaf page  │◄─►│  leaf page  │◄─► ...
            │ key → TID   │   │ key → TID   │
            └─────────────┘   └─────────────┘
```

- **fillfactor = 90** по умолчанию: 10% страницы оставлено, чтобы вставки не вызывали split сразу.
- **Split**: при переполнении страница делится, в родителя добавляется разделитель. Это дорого (WAL + случайная запись).
- **High key** — максимальный ключ страницы, помогает при поиске и split.
- **Deduplication** (PG13+): одинаковые ключи в leaf хранятся один раз + список TID (posting list). Сильно уменьшает размер индексов с низкой кардинальностью.
- **Index tuple limit**: одна запись не может быть больше ~2704 байт (`1/3` страницы). Длинный `text` проиндексировать не получится.

Поиск: `O(log n)` по страницам + последовательный проход по листьям (важно для диапазонов и `ORDER BY`).

### Index-only scan и visibility map

Обычный `Index Scan` идёт: индекс → `ctid` → heap (проверить видимость и достать колонки). **Index Only Scan** берёт данные прямо из индекса, но только если страница помечена **all-visible** в VM.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM orders WHERE id = 42;
-- Index Only Scan ... Heap Fetches: 0   ← идеально
-- Index Only Scan ... Heap Fetches: 100 ← VM не обновлена, нужен VACUUM
```

`INCLUDE (col)` добавляет «полезную нагрузку» в листья индекса, не участвующую в сравнении:

```sql
CREATE INDEX idx_orders_user_created
  ON orders (user_id, created_at) INCLUDE (status, total);
```

### Другие методы доступа

| Тип | Для чего | Особенности |
|---|---|---|
| **B-tree** | `=`, `<`, `>`, `BETWEEN`, `ORDER BY`, префикс `LIKE 'abc%'` | default, самый универсальный |
| **Hash** | только `=` | компактнее B-tree, но не умеет диапазоны; WAL-logged с PG10 |
| **GIN** | `jsonb`, массивы, `tsvector`, `pg_trgm` | «перевёрнутый»: ключ → список TID; pending list (`fastupdate`), дорогая запись |
| **GiST** | геометрия, диапазоны, `tsvector`, exclusion constraints | сбалансированное дерево с потерями (lossy), поддерживает KNN (`<->`) |
| **SP-GiST** | точечные/радиусные/quadtree структуры | для несбалансированных данных (телефоны, IP, геометрия) |
| **BRIN** | огромные таблицы с корреляцией (логи, телеметрия по времени) | хранит min/max на диапазон страниц; крошечный размер, но работает только при физической упорядоченности |

BRIN особенно полезен: индекс на 1 ТБ таблицу может занимать мегабайты. Условие — колонка должна коррелировать с физическим порядком (`pg_stats.correlation` близко к 1).

### HOT и индексы

Если `UPDATE` не меняет индексируемые колонки — новые index-записи не создаются ([[Внутрянка/MVCC и версии строк]]). Но для этого нужно свободное место **на той же странице** → `fillfactor` таблицы.

### Цена индексов

Каждый индекс:

- замедляет `INSERT`/`UPDATE`/`DELETE` (нужно обновить все индексы);
- генерирует WAL;
- занимает место и кэш (`shared_buffers`);
- добавляет работу autovacuum.

`pg_stat_user_indexes.idx_scan = 0` — кандидат на удаление (но проверь `pg_stat_user_indexes` после сброса статистики и учитывай редкие отчёты).

```sql
-- Бесполезные и дублирующиеся индексы
SELECT relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
ORDER BY idx_scan, pg_relation_size(indexrelid) DESC;

-- Индексы, которые не используются и не являются unique
SELECT i.indexrelid::regclass
FROM pg_index i
JOIN pg_stat_user_indexes s ON s.indexrelid = i.indexrelid
WHERE NOT i.indisunique AND s.idx_scan = 0;
```

## Что видно в psql

```sql
CREATE EXTENSION IF NOT EXISTS pageinspect;
CREATE EXTENSION IF NOT EXISTS pgstattuple;

-- Структура B-tree
SELECT * FROM bt_metap('orders_pkey');
SELECT * FROM bt_page_stats('orders_pkey', 1);
SELECT * FROM bt_page_items('orders_pkey', 1) LIMIT 10;

-- Плотность/фрагментация индекса
SELECT * FROM pgstatindex('orders_pkey');
-- avg_leaf_density, leaf_fragmentation

-- Размеры
SELECT indexrelname, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes WHERE relname = 'orders';
```

## Грабли и мифы

1. **«Индекс есть → он используется».** Нет: функция над колонкой, неявный каст, `LIKE '%…%'`, `OR` по разным колонкам, низкая селективность — и планировщик выберет seq scan.
2. **Индекс по `boolean`/`status` почти бесполезен** (кроме partial index по редкому значению).
3. **`CREATE INDEX` блокирует запись.** На проде — `CREATE INDEX CONCURRENTLY` (нельзя в транзакции, может оставить `INVALID`).
4. **Индекс раздувается** так же, как таблица. `REINDEX CONCURRENTLY` (PG12+) лечит.
5. **`index-only scan` требует `VACUUM`.** Без обновлённой VM он ходит в heap (`Heap Fetches`).
6. **Порядок колонок в составном индексе важен.** `(a, b)` покрывает `a` и `(a,b)`, но не `b`. Правило: сначала equality-колонки, потом диапазон/сортировка.
7. **Индекс на `text` с длинными значениями может не создаться** (limit 2704 байта). Используй `md5(col)`, `left(col, n)` или `pg_trgm`.

## Эксперимент

```sql
CREATE TABLE idx_demo (id serial, user_id int, status text, created_at timestamptz, payload text);
INSERT INTO idx_demo (user_id, status, created_at, payload)
SELECT (random()*10000)::int,
       (ARRAY['new','paid','shipped'])[1 + (random()*2)::int],
       now() - (random() * interval '365 days'),
       repeat('x', 100)
FROM generate_series(1, 1_000_000);

ANALYZE idx_demo;

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM idx_demo WHERE user_id = 500;
-- Seq Scan (нет индекса) → 1M строк

CREATE INDEX idx_user ON idx_demo (user_id);
ANALYZE idx_demo;

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM idx_demo WHERE user_id = 500;
-- Index Scan

-- Покрывающий индекс
CREATE INDEX idx_user_cover ON idx_demo (user_id) INCLUDE (status);
VACUUM idx_demo;
EXPLAIN (ANALYZE, BUFFERS) SELECT user_id, status FROM idx_demo WHERE user_id = 500;
-- Index Only Scan, Heap Fetches: 0

-- Частичный индекс вместо индекса по статусу
CREATE INDEX idx_paid ON idx_demo (created_at) WHERE status = 'paid';
EXPLAIN SELECT * FROM idx_demo WHERE status = 'paid' AND created_at > now() - interval '30 days';
```
