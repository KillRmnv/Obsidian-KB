# Лабораторки

Сценарии к лаборатории: [[Практикум/Лаборатория на Docker]]. Каждая — один файл в `labs/`, 10–20 минут. Цель — не «выполнить», а **объяснить, что видно в плане**.

Запуск:

```bash
cd "…/sql/Postgres/Практикум"
psql -h localhost -p 5433 -U postgres -d lab -f labs/01-explain.sql
```

## 01. EXPLAIN: оценка vs реальность

**Файл:** `labs/01-explain.sql`
**Тема:** [[Оптимизация/EXPLAIN и EXPLAIN ANALYZE]], [[Внутрянка/Планировщик и исполнитель]]

Что сделать:

1. Сравнить `EXPLAIN` и `EXPLAIN (ANALYZE, BUFFERS)` на одном запросе.
2. Найти запрос, где `rows` (оценка) расходится с `actual rows` в 10+ раз.
3. Увидеть `loops` и пересчитать реальное время узла.
4. Посмотреть `Rows Removed by Filter` на seq scan.
5. Убедиться, что `cost` — не время.

Вопросы:

- Почему `EXPLAIN` без `ANALYZE` может «врать»?
- Какой узел самый дорогой и почему `actual time` надо умножать на `loops`?
- Что означает `Buffers: shared hit=… read=…`?

## 02. Индексы: когда работают, когда нет

**Файл:** `labs/02-indexes.sql`
**Тема:** [[Оптимизация/Индексы на практике]], [[Внутрянка/Индексы изнутри]]

Что сделать:

1. `Seq Scan` → `Index Scan` после создания индекса на `user_id`.
2. Показать, что индекс по `status` не используется (80% строк).
3. Заменить его на **partial index** `WHERE status = 'new'`.
4. Покрывающий индекс + `VACUUM` → `Index Only Scan`, `Heap Fetches: 0`.
5. Expression index для `lower(email)`.
6. GIN по `jsonb` (`@>`) vs `->>` (без индекса).

Вопросы:

- Почему index-only scan не работает без `VACUUM`?
- Почему `INCLUDE` не помогает искать по колонке?
- Что будет с `INSERT` при 8 индексах на таблице?

## 03. Кардинальность и расширенная статистика

**Файл:** `labs/03-cardinality.sql`
**Тема:** [[Оптимизация/Оценка кардинальности]]

Что сделать:

1. `country` и `locale` в `lab.users` коррелируют (RU → ru-RU).
2. Запрос `WHERE country='RU' AND locale='ru-RU'`: оценка ≈ `0.2 × 0.2 = 4%`, реально 20%.
3. `CREATE STATISTICS … (dependencies, mcv)` + `ANALYZE` → оценка исправляется.
4. Поднять `default_statistics_target` для колонки с перекосом.

Вопросы:

- Почему планировщик предполагает независимость?
- Когда `ANALYZE` не помогает и нужна расширенная статистика?
- Как `n_distinct < 0` читать?

## 04. JOIN и `work_mem`

**Файл:** `labs/04-joins.sql`
**Тема:** [[Оптимизация/JOIN-оптимизация]]

Что сделать:

1. `users JOIN orders` без индекса на `orders.user_id` → hash join.
2. С индексом → сравнить план (nested loop/hash).
3. `SET work_mem='64kB'` → `Batches > 1`, `Sort Method: external merge`.
4. `SET work_mem='64MB'` → всё в памяти.
5. Top-3 заказа на пользователя через `LATERAL` + индекс `(user_id, created_at DESC)`.
6. `SET enable_nestloop=off` — только чтобы проверить гипотезу.

Вопросы:

- Почему nested loop с `loops=100000` — плохо?
- Что означает `Batches: 4` у Hash Join?
- Почему `work_mem` — «на узел», а не на запрос?

## 05. Блокировки и deadlock

**Файл:** `labs/05-locking.sql`
**Тема:** [[Внутрянка/Транзакции и блокировки]], [[Внутрянка/Конкурентность на практике]]

Что сделать:

1. Воспроизвести ожидание на строке (через `dblink` или две сессии).
2. `lock_timeout` → ошибка вместо бесконечного ожидания.
3. Найти блокировщика: `pg_blocking_pids`.

5. `FOR UPDATE SKIP LOCKED` на очереди задач.

## 07. Bloat, VACUUM и `pgstattuple`

**Файл:** `labs/07-bloat.sql`
**Тема:** [[Внутрянка/VACUUM и autovacuum]], [[Внутрянка/MVCC и версии строк]]

Что сделать:

1. Создать таблицу 200k строк, обновить все строки.
2. Посмотреть `n_dead_tup` и размер до/после.
3. `VACUUM` → мусор исчез, файл почти не уменьшился.
4. `pgstattuple_approx` → доля мёртвых/свободного места.
5. `VACUUM FULL` → файл уменьшился, но была блокировка.
6. `fillfactor=80` + повторный апдейт → больше `n_tup_hot_upd`.

Вопросы:

- Почему `VACUUM` не возвращает место ОС?
- Почему долгая транзакция мешает vacuum?
- Когда `pg_repack` лучше `VACUUM FULL`?
