# Тюнинг параметров сервера

## Зачем это нужно

Конфиг по умолчанию рассчитан на «запустится на ноутбуке». На реальном сервере он оставляет производительность на столе. Но и копировать чужие `postgresql.conf` опасно: параметры зависят от железа, нагрузки и версии. Здесь — что реально влияет и как проверять.

## Как устроено

### Принцип

> Меняй один параметр за раз, измеряй до/после, фиксируй результат.

Источники «правильных» значений:

1. документация PostgreSQL (описание каждого GUC);
2. **pgtune** / PGTune online — стартовая конфигурация по объёму RAM и типу нагрузки;
3. собственные метрики (`pg_stat_*`, `EXPLAIN (ANALYZE, BUFFERS)`).

### Память

| Параметр | Ориентир | Влияние |
|---|---|---|
| `shared_buffers` | 25% RAM (до 8–16 ГБ) | кэш страниц; больше — не всегда лучше, дублирует page cache |
| `effective_cache_size` | 50–75% RAM | **только подсказка планировщику**, память не выделяет |
| `work_mem` | 4–16 МБ глобально | на **каждый** узел сортировки/хэша, умножается на соединения |
| `maintenance_work_mem` | 5–10% RAM (до 1–2 ГБ) | `VACUUM`, `CREATE INDEX`, `ALTER TABLE` |
| `autovacuum_work_mem` | = `maintenance_work_mem` или `-1` | память autovacuum-воркеров |
| `temp_buffers` | 8–32 МБ | временные таблицы |
| `wal_buffers` | `-1` (авто, до 16 МБ) | буфер WAL |

**Формула риска `work_mem`:**

```
worst_case ≈ max_connections × (число узлов сортировки/хэша в запросе) × work_mem
```

10 сортировок × 64 МБ × 200 соединений = 128 ГБ. Поэтому:

```sql
-- точечно, для конкретного запроса
SET LOCAL work_mem = '256MB';
```

### Стоимость и планировщик

| Параметр | Default | Для SSD |
|---|---|---|
| `random_page_cost` | `4.0` | `1.1` |
| `seq_page_cost` | `1.0` | `1.0` |
| `effective_io_concurrency` | `1` | `100–200` |
| `cpu_tuple_cost` | `0.01` | обычно не трогать |
| `parallel_setup_cost` | `1000` | |
| `max_parallel_workers_per_gather` | `2` | 4 при многих ядрах |

`random_page_cost=4` на SSD — причина, по которой планировщик выбирает seq scan там, где индекс был бы лучше.

### Соединения

```conf
max_connections = 200              # не 1000
```

- Каждое соединение — процесс ([[Внутрянка/Архитектура PostgreSQL]]).
- Для веб-приложений — **PgBouncer** в `transaction` режиме.
- `superuser_reserved_connections = 3` — оставить запас для админа.
- `idle_in_transaction_session_timeout` — убивать «зависшие» транзакции.

Особенности transaction pooling: нельзя рассчитывать на session-level состояние (`SET`, advisory locks, `LISTEN/NOTIFY`, временные таблицы, `PREPARE` до PgBouncer 1.21+).

### WAL и checkpoint

| Параметр | Ориентир |
|---|---|
| `wal_level` | `replica` (или `logical` при логической репликации) |
| `max_wal_size` | `4–8GB` (больше — реже checkpoint'ы) |
| `min_wal_size` | `1–2GB` |
| `checkpoint_timeout` | `15min` (при стабильной нагрузке) |
| `checkpoint_completion_target` | `0.9` |
| `wal_compression` | `lz4` или `zstd` (PG15+) |
| `synchronous_commit` | `on` (для денег), `off` для аналитики |
| `full_page_writes` | `on` (не выключать) |

Частые checkpoint'ы → пики записи и раздувание WAL (FPI). Редкие → долгий recovery и риск переполнения `pg_wal`.

### Autovacuum

```conf
autovacuum = on
autovacuum_max_workers = 3        # больше при многих таблицах
autovacuum_naptime = '30s'
autovacuum_vacuum_cost_delay = '2ms'
autovacuum_vacuum_cost_limit = 1000
```

Для больших таблиц — per-table scale factor:

```sql
ALTER TABLE big_table SET (autovacuum_vacuum_scale_factor = 0.02);
```

### Логирование и диагностика

```conf
log_min_duration_statement = '500ms'
log_checkpoints = on
log_lock_waits = on
log_temp_files = 0
log_autovacuum_min_duration = '1s'
track_io_timing = on
track_activity_query_size = 2048
shared_preload_libraries = 'pg_stat_statements,auto_explain'
```

`track_io_timing` добавляет накладные расходы, но без него `Buffers` не покажет время I/O.

### JIT

```conf
jit = on
jit_above_cost = 100000
jit_inline_above_cost = 500000
jit_optimize_above_cost = 500000
```

Для OLTP с короткими запросами JIT чаще **вредит** (компиляция дороже выигрыша). Признак: `JIT` в `EXPLAIN` с большими `Timing`/`Deform`.

### PG18: async I/O

```conf
io_method = 'worker'   # или 'io_uring' на Linux с поддержкой
io_workers = 3
```

Влияет на чтение с диска; смотреть `pg_stat_io`. На логику запросов не влияет.

## Что видно в psql

```sql
-- Что реально применено и откуда
SELECT name, setting, unit, source, sourcefile
FROM pg_settings
WHERE name IN ('shared_buffers','work_mem','effective_cache_size',
               'random_page_cost','max_connections','wal_level');

-- Сколько памяти занято
SELECT * FROM pg_shmem_allocations ORDER BY size DESC LIMIT 10;

-- Проверить, что параметр сессионный
SHOW work_mem;
SET work_mem = '128MB';
SHOW work_mem;

-- Перечитать конфиг без рестарта (для параметров с context=user/sighup)
SELECT pg_reload_conf();
```

Профиль нагрузки:

```sql
SELECT datname,
       xact_commit, xact_rollback,
       blks_read, blks_hit,
       temp_files, pg_size_pretty(temp_bytes) AS temp,
       deadlocks
FROM pg_stat_database
WHERE datname = current_database();
```

## Грабли и мифы

1. **`shared_buffers` = 80% RAM** — плохой совет: ОС тоже кэширует файлы, а PostgreSQL не умеет отдавать память.
2. **`work_mem` глобально в гигабайтах** — верный способ получить OOM под нагрузкой.
3. **`random_page_cost=4` на SSD** — планировщик недооценивает индексы.
4. **`max_connections=1000` без пулера** — память и контекст-свитчи.
5. **`fsync=off`** — не тюнинг, а отключение Durability ([[Внутрянка/WAL и durability]]).
6. **`autovacuum=off`** — отложенный wraparound.
7. **Конфиг с интернета без понимания** — чужие `effective_cache_size` и `work_mem` почти наверняка не про ваш сервер.
8. **`pg_reload_conf()` не применяет всё** — часть параметров требует рестарта (`shared_buffers`, `max_connections`, `wal_level`).

## Эксперимент

В лаборатории:

```sql
-- 1. Как random_page_cost меняет план
SET random_page_cost = 4;
EXPLAIN SELECT * FROM idx_practice WHERE user_id = 500;
SET random_page_cost = 1.1;
EXPLAIN SELECT * FROM idx_practice WHERE user_id = 500;

-- 2. work_mem и внешняя сортировка
SET work_mem = '64kB';
EXPLAIN (ANALYZE) SELECT * FROM idx_practice ORDER BY payload;
SET work_mem = '64MB';
EXPLAIN (ANALYZE) SELECT * FROM idx_practice ORDER BY payload;

-- 3. Что занимает shared memory
SELECT * FROM pg_shmem_allocations ORDER BY size DESC LIMIT 5;
```
