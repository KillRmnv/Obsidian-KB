# Схема и модель данных

## Зачем это нужно

Половина проблем производительности решается не запросами и индексами, а схемой: типы, ограничения, порядок колонок, способ хранения. Кроме того, схема влияет на размер БД, скорость `ALTER TABLE` и корректность данных.

## Как устроено

### Типы: что выбрать

| Задача | Правильно | Почему |
|---|---|---|
| Деньги | `numeric(12,2)` | точная арифметика; `float` даёт ошибки округления |
| ID | `bigint GENERATED ALWAYS AS IDENTITY` | 8 байт, монотонный, без bloat в индексе |
| Универсальный ID | `uuid` + `uuidv7()` (PG18+) | v4 случайный → вставки в середину B-tree; v7 — почти монотонный |
| Строки | `text` | `varchar(n)` — тот же тип + проверка длины, выигрыша нет |
| Фиксированная длина | `char(n)` — только если реально нужен padding | дополняет пробелами, сравнения сюрпризят |
| Время | `timestamptz` | хранит UTC, конвертирует при выводе; `timestamp` — источник багов с поясами |
| Дата | `date` | 4 байта вместо 8 |
| Флаги | `boolean` | не `char(1)` и не `int` |
| Справочник | отдельная таблица или `enum` | enum дёшев, но `ALTER TYPE … ADD VALUE` ограничен |
| Полуструктурированное | `jsonb` | бинарный, индексируется GIN; `json` — только для сохранения исходного текста |
| Списки | `array` + GIN | для «тегов»; для связей «многие-ко-многим» — таблица |
| Диапазоны | `int4range`, `tstzrange` | exclusion constraints, `<@`, `&&` |

### Порядок колонок и выравнивание

PostgreSQL выравнивает данные по границам:

| Тип | Размер | Выравнивание |
|---|---|---|
| `smallint` | 2 | 2 |
| `int` | 4 | 4 |
| `bigint`, `double`, `timestamptz` | 8 | 8 |
| `text`, `numeric`, `jsonb` | переменный | 4 (по указателю) |
| `boolean` | 1 | 1 |

Кортеж может содержать «дыры» из-за выравнивания. Правило: **сначала 8-байтовые, потом 4, потом 2, потом 1**. Экономия — единицы процентов, но на сотнях миллионов строк заметна.

```sql
-- Плохо: 7 байт padding
CREATE TABLE bad (b boolean, i bigint, s smallint);
-- Лучше
CREATE TABLE good (i bigint, s smallint, b boolean);
```

### Ограничения (constraints)

- **PK** — уникальность + `NOT NULL`, создаёт индекс.
- **FK** — ссылочная целостность. **Индекс на ссылающуюся колонку не создаётся автоматически**, а без него `DELETE`/`UPDATE` родителя делает seq scan дочерней таблицы.
- **UNIQUE** — индекс; для длинных строк/выражений — unique expression index.
- **CHECK** — дешёвая валидация; на больших таблицах добавляется через `NOT VALID` + `VALIDATE CONSTRAINT`.
- **EXCLUDE** — «диапазоны не пересекаются» (нужен GiST или SP-GiST).

```sql
-- Безопасное добавление CHECK на большую таблицу
ALTER TABLE orders ADD CONSTRAINT chk_total CHECK (total >= 0) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT chk_total;  -- без ACCESS EXCLUSIVE
```

`PG18+`: `ALTER TABLE … ALTER COLUMN … SET NOT NULL NOT VALID` + `VALIDATE CONSTRAINT` — добавление `NOT NULL` без полного сканирования под блокировкой.

### Добавление колонок

| Операция | Что происходит |
|---|---|
| `ADD COLUMN nullable` | мгновенно (только каталог) |
| `ADD COLUMN DEFAULT const` (PG11+) | мгновенно (значение хранится в каталоге) |
| `ADD COLUMN DEFAULT volatile` | перезапись таблицы |
| `ALTER TYPE` (например, `int` → `bigint`) | перезапись таблицы |
| `SET NOT NULL` (до PG18) | полный скан под `ACCESS EXCLUSIVE` |
| `DROP COLUMN` | мгновенно (место не возвращается) |

### Нормализация vs денормализация

- **OLTP** — нормализация (3НФ), меньше аномалий, но больше join'ов.
- **OLAP/отчёты** — денормализация, materialized views, wide tables.
- **Смешанная нагрузка** — нормализованная схема + materialized view/read-model для отчётов.

Денормализация оправдана, когда:

- join слишком дорог и данные меняются редко;
- агрегаты нужны постоянно (счётчики, суммы);
- есть требование к задержке чтения.

Цена: нужно поддерживать согласованность (триггеры, приложение, CDC).

### Партиционирование и наследование

Декларативное партиционирование (PG10+) — [[Партиции]]. Кратко:

```sql
CREATE TABLE events (id bigint, created_at date, payload jsonb)
PARTITION BY RANGE (created_at);
CREATE TABLE events_2026_01 PARTITION OF events
FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
```

- ключ партиционирования должен быть в запросах, иначе скан всех партиций;
- уникальные индексы обязаны включать ключ;
- загрузка в отдельную таблицу + `ATTACH PARTITION` быстрее, чем INSERT в партиционированную;
- слишком много партиций (сотни) замедляет планирование.

### Именование и служебные поля

Разумный стандарт:

```sql
CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     bigint NOT NULL REFERENCES users(id),
  status      text NOT NULL DEFAULT 'new',
  total       numeric(12,2) NOT NULL CHECK (total >= 0),
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON orders (user_id, created_at DESC);
CREATE INDEX ON orders (status) WHERE status <> 'done';
```

- `created_at`/`updated_at` — почти всегда нужны;
- `updated_at` — триггер или `DEFAULT` + приложение;
- `deleted_at` (soft delete) — не забыть partial-индексы `WHERE deleted_at IS NULL`;
- не использовать `id` типа `serial` в новых таблицах — `identity` стандартнее и не даёт «случайных» прав на sequence.

### Multi-tenancy

- `tenant_id` в каждой таблице и **первым** в составных индексах;
- RLS (`ROW LEVEL SECURITY`) для изоляции;
- партиционирование по `tenant_id` (hash) при большом числе тенантов;
- отдельные схемы/базы — максимальная изоляция, но дороже в обслуживании.

## Что видно в psql

```sql
-- Размер строки и потери на выравнивание
SELECT attname, atttypid::regtype, attlen, attalign, attnum
FROM pg_attribute
WHERE attrelid = 'orders'::regclass AND attnum > 0 AND NOT attisdropped;

SELECT pg_column_size(o.*) AS row_bytes FROM orders o LIMIT 1;

-- Ограничения
SELECT conname, contype, conrelid::regclass, pg_get_constraintdef(oid)
FROM pg_constraint WHERE conrelid = 'orders'::regclass;

-- Внешние ключи без индекса на ссылающейся стороне
SELECT c.conrelid::regclass AS child, c.conname
FROM pg_constraint c
WHERE c.contype = 'f'
  AND NOT EXISTS (
    SELECT 1 FROM pg_index i
    WHERE i.indrelid = c.conrelid
      AND (i.indkey::int2[])[0:array_length(c.conkey,1)-1] = c.conkey
  );

-- Размеры типов
SELECT typname, typlen, typalign FROM pg_type
WHERE typname IN ('int4','int8','numeric','text','timestamptz','uuid','bool');
```

## Грабли и мифы

1. **`varchar(n)` не быстрее `text`** и не экономит место — это тот же varlena с проверкой.
2. **`char(n)` дополняет пробелами** → `'a'::char(5) = 'a'` работает, но `length()` вернёт 5.
3. **`timestamp` без пояса** — данные «плывут» при смене таймзоны сервера/клиента. Только `timestamptz`.
4. **`float` для денег** — накопление ошибок; `numeric` или целые копейки.
5. **UUID v4 как PK** — случайные вставки, раздувание индекса, плохой кэш. `bigint identity` или `uuidv7()` (PG18+).
6. **FK без индекса** — скрытый seq scan при удалении родителя.
7. **`ALTER TYPE`** перезаписывает таблицу и берёт `ACCESS EXCLUSIVE`.
8. **Денормализация без механизма синхронизации** — источник расхождений, а не оптимизация.
9. **`SELECT *` в ORM** ломает покрывающие индексы.

## Эксперимент

```sql
-- 1. Выравнивание
CREATE TABLE align_bad (b boolean, i bigint, s smallint, t text);
CREATE TABLE align_good (i bigint, t text, s smallint, b boolean);
INSERT INTO align_bad  SELECT true, g, 1, 'x' FROM generate_series(1,100000) g;
INSERT INTO align_good SELECT g, 'x', 1, true FROM generate_series(1,100000) g;
SELECT pg_size_pretty(pg_relation_size('align_bad'))  AS bad,
       pg_size_pretty(pg_relation_size('align_good')) AS good;

-- 2. FK без индекса
CREATE TABLE parent (id bigint PRIMARY KEY);
CREATE TABLE child (id bigint PRIMARY KEY, parent_id bigint REFERENCES parent(id));
INSERT INTO parent SELECT generate_series(1, 100000);
INSERT INTO child  SELECT g, g FROM generate_series(1, 100000) g;
EXPLAIN (ANALYZE, BUFFERS) DELETE FROM parent WHERE id = 1;
CREATE INDEX ON child (parent_id);
EXPLAIN (ANALYZE, BUFFERS) DELETE FROM parent WHERE id = 2;

-- 3. NOT NULL без долгой блокировки (PG18+)
-- ALTER TABLE child ALTER COLUMN parent_id SET NOT NULL NOT VALID;
-- ALTER TABLE child VALIDATE CONSTRAINT child_parent_id_not_null;
```
