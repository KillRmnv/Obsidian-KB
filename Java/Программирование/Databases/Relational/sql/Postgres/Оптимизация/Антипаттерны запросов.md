# Антипаттерны запросов

## Зачем это нужно

Большинство «медленных запросов» — не экзотика, а повторяющиеся паттерны. Если знать их список, половину проблем можно находить по тексту SQL, ещё до `EXPLAIN`.

## Как устроено

### 1. OFFSET-пагинация

```sql
-- Плохо: на OFFSET 100000 PostgreSQL читает и выбрасывает 100000 строк
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 100000;

-- Хорошо: keyset (seek) pagination
SELECT * FROM orders
WHERE created_at < $last_seen_created_at
ORDER BY created_at DESC
LIMIT 20;
```

Keyset требует индекса `(created_at DESC)` и уникального tie-breaker:

```sql
WHERE (created_at, id) < ($last_created_at, $last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Для админок с произвольным переходом на страницу — `OFFSET`, но с ограничением глубины или через materialized view/кэш.

### 2. `SELECT *`

- тянет TOAST-колонки и лишние байты;
- ломает index-only scan;
- увеличивает сетевой трафик и память.

```sql
-- Плохо
SELECT * FROM users WHERE id = 1;
-- Хорошо
SELECT id, email, created_at FROM users WHERE id = 1;
```

### 3. Точный `count(*)` для UI

```sql
-- Плохо на большой таблице: читает всё
SELECT count(*) FROM orders WHERE status = 'paid';
```

Варианты:

- оценка: `SELECT reltuples::bigint FROM pg_class WHERE relname = 'orders'` (после `ANALYZE`);
- `EXPLAIN (FORMAT JSON)` и достать `Plan Rows` (быстро, приблизительно);
- отдельная таблица-счётчик с триггерами/инкрементами;
- «показать ещё» без общего числа.

### 4. `NOT IN` с NULL

```sql
-- Вернёт пусто, если в подзапросе есть NULL
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders);
-- Правильно
SELECT * FROM users u WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

### 5. Функции и касты над колонкой

```sql
-- Плохо: индекс по created_at не используется
WHERE date_trunc('day', created_at) = '2026-01-01';
WHERE created_at::date = '2026-01-01';
WHERE upper(email) = 'A@B.C';

-- Хорошо: sargable-условия
WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02';
WHERE email = lower('A@B.C');            -- или expression index
```

### 6. `LIKE '%…%'`

```sql
-- Плохо: полный скан
WHERE name LIKE '%иван%';
-- Хорошо: trigram-индекс
CREATE EXTENSION pg_trgm;
CREATE INDEX ON users USING gin (name gin_trgm_ops);
```

`LIKE 'иван%'` может использовать B-tree, но только при collation `C` или индексе с `text_pattern_ops`.

### 7. `OR` по разным колонкам

```sql
-- Плохо: один индекс не покрывает оба условия
WHERE email = $1 OR phone = $2;

-- Хорошо: UNION ALL (если нужны все совпадения) или два индекса + BitmapOr
SELECT * FROM users WHERE email = $1
UNION ALL
SELECT * FROM users WHERE phone = $2 AND email <> $1;
```

PostgreSQL умеет `BitmapOr` для двух индексов, но при разных типах/селективности это часто seq scan.

### 8. Раздутые `IN`-списки

```sql
-- Плохо: 10 000 литералов — долгий parse/plan, огромный план
WHERE id IN (1,2,3, …, 10000);

-- Лучше: один параметр-массив
WHERE id = ANY($1::int[]);
-- или JOIN с VALUES / временной таблицей
```

### 9. `ORDER BY random()`

```sql
-- Плохо: сортировка всей таблицы
SELECT * FROM quotes ORDER BY random() LIMIT 1;
-- Лучше: случайный id + индекс, или TABLESAMPLE
SELECT * FROM quotes TABLESAMPLE SYSTEM (1) LIMIT 1;
```

### 10. `DISTINCT` как «пластырь» от размножения строк

```sql
-- Плохо: join размножил строки, DISTINCT их убирает (сортировка/хэш)
SELECT DISTINCT u.* FROM users u JOIN orders o ON o.user_id = u.id;

-- Хорошо: EXISTS, если нужны только пользователи с заказами
SELECT * FROM users u WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

### 11. N+1 запросов из ORM

Симптом в `pg_stat_statements`: одинаковый запрос с `calls` в тысячах и `rows=1`. Лечение — `JOIN FETCH` / batch-загрузка / `IN`.

### 12. Запросы в цикле на PL/pgSQL

```sql
-- Плохо: 10 000 отдельных INSERT
FOR i IN 1..10000 LOOP
  INSERT INTO t VALUES (i);
END LOOP;

-- Хорошо: один INSERT … SELECT
INSERT INTO t SELECT generate_series(1, 10000);
```

### 13. JSONB без GIN

```sql
-- Плохо: seq scan + разбор каждого документа
WHERE data->>'status' = 'paid';
-- Хорошо: GIN + оператор @>
CREATE INDEX ON events USING gin (data jsonb_path_ops);
WHERE data @> '{"status":"paid"}';
```

`->>` не использует GIN; `@>` использует.

### 14. Долгие транзакции и `SELECT FOR UPDATE`

Держат `xmin` и локи, мешают vacuum, создают очереди. Правило: транзакция — минимально короткая, без сетевых вызовов внутри.

### 15. `DELETE` вместо партиций

```sql
-- Плохо: миллионы строк + bloat + WAL
DELETE FROM logs WHERE created_at < now() - interval '90 days';

-- Хорошо (при партиционировании): мгновенно
DROP TABLE logs_2025_01;
```

### 16. Типы, которые ломают индексы

- `varchar(n)` не даёт выигрыша по сравнению с `text`, но добавляет проверку длины;
- `char(n)` дополняет пробелами — сравнения сюрпризят;
- `timestamp` без `timezone` — ошибки при смене пояса;
- `float` для денег — округления;
- `uuid v4` как PK — случайные вставки в B-tree (лучше `uuidv7()` в PG18+ или `bigint identity`).

## Что видно в psql

```sql
-- Найти повторяющиеся запросы (N+1)
SELECT calls, rows, mean_exec_time, left(query, 100)
FROM pg_stat_statements
WHERE calls > 1000 AND rows <= 1
ORDER BY calls DESC LIMIT 20;

-- Запросы, которые пишут во временные файлы (сортировки/хэши)
SELECT calls, temp_blks_written, left(query, 100)
FROM pg_stat_statements
ORDER BY temp_blks_written DESC LIMIT 20;

-- Долгие транзакции
SELECT pid, state, now() - xact_start AS age
FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY age DESC;
```

## Грабли и мифы

1. **`LIMIT` не всегда спасает**: с `OFFSET`, окном или сортировкой работа всё равно делается.
2. **`EXISTS` не «всегда быстрее `IN`»** — планировщик часто приводит их к одному semi join. Важнее корректность с NULL.
3. **`DISTINCT` — не оптимизация, а признак проблемы** с join'ом.
4. **Индекс не поможет `LIKE '%…%'`, `ORDER BY random()`, `count(*)`** — нужны другие приёмы.
5. **`SELECT *` может быть быстрее** в узких местах (меньше round-trip), но почти всегда хуже по I/O и кэшу.
6. **`OFFSET 0` безвреден**, а `OFFSET 100000` — нет. Глубина пагинации важна.

## Эксперимент

```sql
CREATE TABLE ap_demo AS
SELECT g AS id, (g % 100000) AS user_id, now() - (g || ' seconds')::interval AS created_at,
       md5(g::text) AS payload, (g % 3) AS status
FROM generate_series(1, 1_000_000) g;
ANALYZE ap_demo;
CREATE INDEX ON ap_demo (created_at DESC);

-- OFFSET vs keyset
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM ap_demo ORDER BY created_at DESC LIMIT 20 OFFSET 500000;

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM ap_demo
WHERE created_at < (SELECT created_at FROM ap_demo ORDER BY created_at DESC OFFSET 500000 LIMIT 1)
ORDER BY created_at DESC LIMIT 20;

-- count(*) vs оценка
EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM ap_demo WHERE status = 1;
SELECT reltuples::bigint FROM pg_class WHERE relname = 'ap_demo';

-- Функция над колонкой
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM ap_demo WHERE created_at::date = current_date;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM ap_demo WHERE created_at >= current_date;
```
