# Индексы на практике

## Зачем это нужно

Знать, что такое B-tree, недостаточно: индекс может быть создан, но не использоваться, использоваться неоптимально или вредить записи. Здесь — практические правила: какой индекс под какой запрос, почему планировщик его игнорирует и как это проверить.

## Как устроено

### Главное правило: индекс работает, если условие «sargable»

**Sargable** (Search ARGument able) — условие, по которому можно искать в индексе напрямую.

| Плохо (не sargable) | Хорошо (sargable) |
|---|---|
| `WHERE date_trunc('day', created_at) = '2026-01-01'` | `WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'` |
| `WHERE upper(email) = 'A@B.C'` | `WHERE email = 'a@b.c'` (или expression index) |
| `WHERE price * 1.2 > 100` | `WHERE price > 100 / 1.2` |
| `WHERE substring(phone, 1, 3) = '916'` | `WHERE phone LIKE '916%'` |
| `WHERE id::text = '42'` | `WHERE id = 42` |
| `WHERE col = $1 OR other = $1` | `UNION ALL` двух запросов |

### Порядок колонок в составном индексе

Индекс `(a, b, c)` — это сортировка сначала по `a`, потом по `b`, потом по `c`.

```
Используется для:  a, (a,b), (a,b,c), (a,b,c) — диапазоны в конце
НЕ используется:  b, c, (b,c)
```

Правило:

1. **Равенства** (`=`, `IN`) — сначала, самые селективные;
2. **Диапазон/сортировка** (`>`, `BETWEEN`, `ORDER BY`) — в конце;
3. Колонки для покрытия — в `INCLUDE`, не в ключ.

```sql
-- Запрос:
SELECT status, total FROM orders
WHERE user_id = 42 AND created_at > now() - interval '30 days'
ORDER BY created_at DESC;

CREATE INDEX idx_orders ON orders (user_id, created_at DESC) INCLUDE (status, total);
```

`PG18+`: появился **skip scan** для B-tree — планировщик может использовать индекс `(a, b)` даже без условия на `a`, если `a` имеет мало уникальных значений. Раньше это было невозможно.

### Какой тип индекса под задачу

| Запрос | Индекс |
|---|---|
| `=` по PK/FK, диапазоны, `ORDER BY` | B-tree |
| только `=` по длинному ключу | hash (реже, чем B-tree) |
| `jsonb @>`, `?`, `array @>`, полнотекст | GIN |
| `LIKE '%…%'`, нечёткий поиск | GIN/GiST + `pg_trgm` |
| геометрия, диапазоны, `KNN <->` | GiST |
| огромная таблица, колонка коррелирует с порядком | BRIN |
| «горячее» подмножество (`status='new'`) | partial index |
| регистронезависимый поиск | expression index на `lower(col)` |

### Покрывающие индексы и index-only scan

```sql
CREATE INDEX idx_cover ON orders (user_id, created_at) INCLUDE (status);
VACUUM orders;  -- обновить visibility map

EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, created_at, status FROM orders WHERE user_id = 42;
-- Index Only Scan ... Heap Fetches: 0
```

Если `Heap Fetches` большое — VM не обновлена (нужен `VACUUM`) или индекс не покрывает колонки.

### Частичные и функциональные индексы

```sql
-- Partial: только активные заказы (5% таблицы)
CREATE INDEX idx_active_orders ON orders (created_at) WHERE status = 'active';

-- Expression: поиск по email без учёта регистра
CREATE INDEX idx_lower_email ON users (lower(email));

-- Работает только при точном совпадении условия:
SELECT * FROM orders WHERE status = 'active' AND created_at > now() - interval '1 day';
```

Ограничения:

- функция в expression index должна быть **IMMUTABLE**;
- планировщик должен уметь доказать, что условие запроса покрывается предикатом индекса (`status = 'active'` подходит, `status IN ('active')` — тоже, `status <> 'closed'` — нет).

### Индексы и запись

Каждый индекс:

- добавляет работу на `INSERT`/`UPDATE`/`DELETE`;
- генерирует WAL;
- занимает место (часто больше таблицы);
- замедляет `VACUUM` (нужно чистить и индексы).

Практика: 3–5 индексов на таблицу — норма; 10+ — повод задуматься. Часть запросов лучше ускорить переписыванием, чем новым индексом.

### Создание без простоя

```sql
CREATE INDEX CONCURRENTLY idx_orders_user ON orders (user_id);
```

Особенности:

- не блокирует запись (`SHARE UPDATE EXCLUSIVE` вместо `SHARE`);
- **нельзя в транзакции**;
- работает дольше (два прохода по таблице);
- при сбое оставляет **`INVALID`** индекс:

```sql
SELECT indexrelid::regclass, indisvalid, indisready
FROM pg_index WHERE NOT indisvalid;

-- Лечение
REINDEX INDEX CONCURRENTLY idx_orders_user;  -- PG12+
-- или DROP + CREATE заново
```

После неудачного `CREATE INDEX CONCURRENTLY` индекс нужно удалить: он не используется, но замедляет запись.

### Когда индекс не используется

Полный список — в [[Шпаргалки/Индекс не работает — 12 причин]]. Кратко:

1. селективность низкая (планировщик считает seq scan дешевле);
2. функция/каст над колонкой;
3. несовпадение типов;
4. `LIKE '%…%'` без `pg_trgm`;
5. `OR` по разным колонкам;
6. индекс «не тот» по порядку колонок;
7. устаревшая статистика (`ANALYZE`);
8. `random_page_cost` слишком высокий;
9. индекс невалидный (`indisvalid = false`);
10. запрос читает большую долю таблицы.

## Что видно в psql

```sql
-- Какие индексы есть и используются ли
SELECT relname, indexrelname, idx_scan, idx_tup_read, idx_tup_fetch,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC;

-- Дубликаты (индекс является префиксом другого)
SELECT a.indexrelid::regclass AS redundant,
       b.indexrelid::regclass AS covering
FROM pg_index a
JOIN pg_index b
  ON a.indrelid = b.indrelid
 AND a.indexrelid <> b.indexrelid
 AND a.indkey::text = ANY (string_to_array(b.indkey::text, ' ')::text[])
WHERE a.indisunique = false;

-- Размер и фрагментация
SELECT * FROM pgstatindex('idx_orders_user');
-- avg_leaf_density < 50 → кандидат на REINDEX

-- Принудительно проверить, что индекс вообще применим
SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS) SELECT …;
RESET enable_seqscan;
```

## Грабли и мифы

1. **«Индекс на каждую колонку»** — антипаттерн: планировщик не умеет комбинировать индексы так же хорошо, как один составной; запись страдает.
2. **`CREATE INDEX` на проде без `CONCURRENTLY`** блокирует запись на всё время построения.
3. **Индекс по `boolean`/`status` с 3 значениями** почти бесполезен — нужен partial index по редкому значению.
4. **`LIKE 'abc%'`** использует индекс только при collation `C` или индексе с `text_pattern_ops`; `LIKE '%abc'` — никогда без `pg_trgm`.
5. **`INCLUDE` не заменяет ключевые колонки**: по `INCLUDE`-колонкам нельзя искать и нельзя сортировать.
6. **`ORDER BY` с `DESC`/`NULLS FIRST`** должен совпадать с индексом, иначе будет сортировка.
7. **Индекс не обновляется при `UPDATE` неиндексируемых колонок** — это HOT, и это хорошо.
8. **Удаление индекса может ускорить запись сильнее, чем добавление нового ускорит чтение** — проверяй обе стороны.

## Эксперимент

```sql
CREATE TABLE idx_practice AS
SELECT g AS id,
       (random()*100000)::int AS user_id,
       (ARRAY['new','paid','cancelled'])[1 + (random()*2)::int] AS status,
       now() - (random() * interval '730 days') AS created_at,
       (random()*10000)::numeric(10,2) AS total,
       md5(g::text) AS payload
FROM generate_series(1, 2_000_000) g;
ANALYZE idx_practice;

-- 1. Составной индекс под конкретный запрос
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, total FROM idx_practice
WHERE user_id = 500 AND status = 'paid'
ORDER BY created_at DESC LIMIT 20;

CREATE INDEX idx_practice_q ON idx_practice (user_id, status, created_at DESC) INCLUDE (total);
ANALYZE idx_practice;

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, total FROM idx_practice
WHERE user_id = 500 AND status = 'paid'
ORDER BY created_at DESC LIMIT 20;

-- 2. Partial index вместо «широкого»
CREATE INDEX idx_practice_new ON idx_practice (created_at) WHERE status = 'new';
EXPLAIN SELECT * FROM idx_practice WHERE status = 'new' AND created_at > now() - interval '7 days';

-- 3. Expression index
CREATE INDEX idx_practice_lower ON idx_practice (lower(payload));
EXPLAIN SELECT * FROM idx_practice WHERE lower(payload) = 'abc';

-- 4. Посмотреть, что индекс реально используется
SELECT indexrelname, idx_scan FROM pg_stat_user_indexes WHERE relname = 'idx_practice';
```
