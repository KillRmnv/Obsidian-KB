# Методика разбора медленного запроса

## Зачем это нужно

«Запрос тормозит» — это не диагноз. Методика нужна, чтобы не гадать и не добавлять индексы наугад: сначала найти, потом измерить, потом проверить гипотезу, потом закрепить результат. Без порядка легко «оптимизировать» то, что не является узким местом.

## Как устроено

### Шаг 0. Понять, что именно «тормозит»

Разные симптомы — разные инструменты:

| Симптом | Куда смотреть |
|---|---|
| Все запросы медленные | ресурсы: CPU, диск, память, `pg_stat_io`, wait events |
| Один запрос медленный | `EXPLAIN (ANALYZE, BUFFERS)`, статистика |
| Периодические всплески | checkpoint, autovacuum, блокировки, VACUUM FULL, бэкап |
| Растёт со временем | bloat, устаревшая статистика, рост данных, индексы |
| Медленно только под нагрузкой | локи, `work_mem`, пул соединений, конкуренция за CPU |

### Шаг 1. Найти запросы-кандидаты

**`pg_stat_statements`** — обязательное расширение (`shared_preload_libraries`). Нормализует запросы (литералы → `$1`) и агрегирует.

```sql
-- по суммарному времени
SELECT queryid, calls,
       round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 2) AS mean_ms,
       round((100 * total_exec_time / sum(total_exec_time) OVER ())::numeric, 1) AS pct,
       rows, left(query, 100)
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;

-- по среднему времени (дорогие единичные запросы)
SELECT … ORDER BY mean_exec_time DESC LIMIT 20;

-- по числу вызовов (много мелких — тоже проблема)
SELECT … ORDER BY calls DESC LIMIT 20;
```

Смотри не только `total_exec_time`, но и `shared_blks_read` (реальный I/O), `temp_blks_written` (сортировки/хэши на диск), `wal_bytes` (нагрузка на запись).

**`auto_explain`** — логирует планы автоматически для медленных запросов:

```conf
shared_preload_libraries = 'pg_stat_statements,auto_explain'
auto_explain.log_min_duration = '1s'
auto_explain.log_analyze = on
auto_explain.log_buffers = on
auto_explain.log_nested_statements = on
```

**Логи** — `log_min_duration_statement = 500ms`, `log_checkpoints`, `log_autovacuum_min_duration`, `log_lock_waits = on`, `log_temp_files = 0`.

### Шаг 2. Измерить

```sql
EXPLAIN (ANALYZE, BUFFERS, SETTINGS)
SELECT …;
```

Смотрим (подробно — [[Оптимизация/EXPLAIN и EXPLAIN ANALYZE]]):

1. **расхождение `rows` vs `actual rows`** — главный источник плохих планов;
2. **самый дорогой узел** по `actual time × loops`;
3. **`Rows Removed by Filter`** — работа вхолостую;
4. **`Buffers`** — сколько страниц реально прочитано;
5. **`Sort Method` / `Batches`** — нехватка `work_mem`;
6. **`Heap Fetches`** — VM/vacuum.

### Шаг 3. Сформулировать гипотезу

Примеры гипотез и что проверять:

| Гипотеза | Проверка |
|---|---|
| Нет подходящего индекса | `EXPLAIN`, `pg_stat_user_indexes` |
| Индекс есть, но не используется | sargability, касты, функции, селективность |
| Планировщик недооценил строки | `pg_stats`, `CREATE STATISTICS`, `ANALYZE` |
| Мало `work_mem` | `Sort Method: external merge`, `Batches > 1` |
| Nested Loop на больших объёмах | `loops`, `rows` у внешнего узла |
| Блокировки | `pg_stat_activity.wait_event`, `pg_blocking_pids` |
| Bloat | `pgstattuple`, `pg_stat_user_tables` |
| Медленный I/O | `track_io_timing`, `pg_stat_io`, `Buffers: read` |

### Шаг 4. Проверить

- Меняй **одну** вещь за раз.
- Для проверки гипотезы используй сессионные `SET` (`enable_seqscan=off`, `work_mem`), но не тащи их в прод.
- Сравнивай `EXPLAIN (ANALYZE, BUFFERS)` до/после на **репрезентативных данных**.
- Смотри не только время, но и `Buffers` — иначе «ускорение» может быть эффектом кэша.

### Шаг 5. Закрепить

- Индекс/статистика/переписанный запрос — в миграцию.
- Проверить, что новый индекс не дублирует существующий и не убивает запись.
- Добавить метрику/алерт (медленный запрос, лаг, bloat).
- Записать вывод в заметку — через месяц ты не вспомнишь, почему `random_page_cost=1.1`.

## Что видно в psql

```sql
-- 1. Что вообще происходит прямо сейчас
SELECT pid, state, wait_event_type, wait_event,
       now() - xact_start AS xact_age,
       now() - query_start AS query_age,
       left(query, 80)
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY xact_age DESC NULLS LAST;

-- 2. Топ по времени из pg_stat_statements
SELECT calls, total_exec_time, mean_exec_time, rows,
       shared_blks_read, temp_blks_written,
       left(query, 120)
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

-- 3. Сколько времени уходит на I/O в запросе
SET track_io_timing = on;
EXPLAIN (ANALYZE, BUFFERS) SELECT …;

-- 4. Что делал сервер в среднем
SELECT * FROM pg_stat_database WHERE datname = current_database();
```

## Грабли и мифы

1. **«Оптимизируй самый частый запрос»** — не всегда. Запрос с 1 вызовом в час и 10 секундами может быть важнее 10 000 вызовов по 1 мс. Смотри и `total`, и `mean`, и `calls`.
2. **`EXPLAIN ANALYZE` на прогретом кэше врёт** про I/O. Смотри `Buffers: read` и при необходимости сбрасывай кэш (`pg_prewarm`, рестарт в лаборатории).
3. **Средние значения обманывают.** Один запрос с плохим планом на «неудачных» данных (generic plan) может давать 99-й перцентиль, невидимый в среднем.
4. **План зависит от параметров.** `PREPARE` + generic plan может выбрать seq scan там, где custom plan был хорош (`plan_cache_mode`).
5. **Не оптимизируй по слухам.** «Добавь `random_page_cost=1.1`» — правда только на SSD и только для случайного чтения.
6. **`pg_stat_statements` не видит запросы без `shared_preload_libraries`** и не хранит планы (для планов — `auto_explain` / `pg_store_plans`).

## Эксперимент

В лаборатории:

```sql
-- 1. Включить сбор
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
SELECT pg_stat_statements_reset();

-- 2. Нагрузить
SELECT count(*) FROM orders WHERE status = 'paid';  -- несколько раз

-- 3. Найти
SELECT calls, mean_exec_time, left(query, 60)
FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 5;

-- 4. Разобрать
EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM orders WHERE status = 'paid';
```
