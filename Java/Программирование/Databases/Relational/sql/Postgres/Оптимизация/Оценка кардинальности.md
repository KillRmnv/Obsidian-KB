# Оценка кардинальности

## Зачем это нужно

Планировщик выбирает план по **оценке** числа строк. Если оценка врёт, весь план строится на песке: nested loop вместо hash join, seq scan вместо index scan, маленький `work_mem`. Умение находить и лечить ошибки оценки — главный навык оптимизации, который отличает «добавлятора индексов» от инженера.

## Как устроено

### Откуда берутся оценки

Для каждого узла планировщик считает **селективность** (долю проходящих строк):

```
rows_estimate = rows_input × selectivity
```

Селективность берётся из статистики:

- **`=`** → по MCV-списку (`most_common_vals/freqs`), иначе `1 / n_distinct`;
- **диапазон** → по гистограмме (`histogram_bounds`) с равномерным распределением внутри корзины;
- **`IS NULL`** → `null_frac`;
- **`AND`** → произведение селективностей (**предполагается независимость!**);
- **`OR`** → `s1 + s2 − s1×s2` (тоже независимость);
- **join** → `1 / max(n_distinct_left, n_distinct_right)` для равенства.

Именно допущение о независимости — источник большинства ошибок.

### Где смотреть

```sql
-- Статистика по колонке
SELECT attname, n_distinct, null_frac, correlation,
       array_length(most_common_vals::text::text[], 1) AS mcv_count,
       array_length(histogram_bounds::text::text[], 1) AS hist_buckets
FROM pg_stats
WHERE schemaname = 'public' AND tablename = 'orders';

-- Настройка детализации
SHOW default_statistics_target;  -- 100
```

`default_statistics_target` = число корзин гистограммы и максимальный размер MCV. Для неравномерных колонок (статусы, регионы, категории) 100 может быть мало.

```sql
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;
```

### Типичные причины ошибок

| Причина | Признак | Лечение |
|---|---|---|
| Статистика устарела | `reltuples = -1`, данные только что залиты | `ANALYZE` |
| Мало корзин гистограммы | оценка на «хвосте» распределения | поднять `STATISTICS` |
| Коррелированные колонки | `AND` двух условий → занижение в разы | `CREATE STATISTICS` |
| Функция над колонкой | оценка 0.5% «по умолчанию» | expression index / переписать |
| `LIKE '%…%'`, `OR`, `NOT IN` | грубая эвристика | переписать / pg_trgm |
| Данные изменились после `ANALYZE` | план «съехал» | autovacuum/ANALYZE чаще |
| Generic plan prepared statement | план не зависит от параметра | `plan_cache_mode`, `EXECUTE` |
| `WHERE` на partition key без pruning | скан всех партиций | проверить план |

### Расширенная статистика

```sql
-- Функциональная зависимость: city → region
CREATE STATISTICS st_addr (dependencies) ON city, region FROM addresses;

-- Число комбинаций (для GROUP BY)
CREATE STATISTICS st_addr_nd (ndistinct) ON city, region FROM addresses;

-- Частые комбинации (PG12+)
CREATE STATISTICS st_addr_mcv (mcv) ON city, region FROM addresses;

ANALYZE addresses;

SELECT e.stxname, e.stxkind,
       d.stxdndistinct    IS NOT NULL AS has_ndistinct,
       d.stxddependencies IS NOT NULL AS has_dependencies,
       d.stxdmcv          IS NOT NULL AS has_mcv
FROM pg_statistic_ext e
JOIN pg_statistic_ext_data d ON d.stxoid = e.oid;
```

Проверка эффекта:

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM addresses WHERE city = 'Москва' AND region = 'Москва';
-- до: rows=12 (оценка), actual=200000
-- после CREATE STATISTICS: rows≈200000
```

### Оценка join'ов

Для `a JOIN b ON a.x = b.y` планировщик считает:

```
rows ≈ rows_a × rows_b × selectivity
selectivity ≈ 1 / max(n_distinct(a.x), n_distinct(b.y))
```

Проблемы:

- **перекос значений** (80% заказов у одного клиента) — оценка средняя, реальность другая;
- **коррелированные условия на обеих сторонах**;
- **`JOIN` по выражению/касту** — статистика не применяется.

Лечение: `ANALYZE`, extended statistics на фильтруемые колонки, иногда — переписывание запроса или `MATERIALIZED` CTE (осторожно, PG12+ инлайнит CTE).

### Prepared statements и generic plan

После 5 выполнений PostgreSQL может переключиться на **generic plan**, не зависящий от параметров. Если данные перекошены — план станет плохим.

```sql
SET plan_cache_mode = force_custom_plan;   -- или auto (default)
-- Посмотреть, какой план используется:
PREPARE q(int) AS SELECT * FROM orders WHERE user_id = $1;
EXPLAIN EXECUTE q(1);
EXPLAIN EXECUTE q(999);   -- generic plan будет одинаковым
```

`force_custom_plan` — лечение, но каждый вызов тратит время на планирование. Часто лучше поправить статистику.

### Когда оценка не важна

- Запрос на 100 строк: любой план быстрый.
- Чистый `INSERT`/`UPDATE` по PK.
- `count(*)` без фильтра: seq scan всё равно.

Ошибки оценки критичны на **больших** таблицах и **сложных** запросах с несколькими join'ами.

## Что видно в psql

```sql
-- 1. Где оценка врёт: сравнить rows и actual rows
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'paid' AND region = 'EU';

-- 2. Что знает статистика
SELECT attname, n_distinct, most_common_vals, most_common_freqs
FROM pg_stats
WHERE tablename = 'orders' AND attname IN ('status', 'region');

-- 3. Селективность вручную
SELECT count(*) FILTER (WHERE status = 'paid')::numeric / count(*) AS sel_status,
       count(*) FILTER (WHERE region = 'EU')::numeric / count(*) AS sel_region
FROM orders;

-- 4. Сколько строк на самом деле проходит оба условия
SELECT count(*) FROM orders WHERE status = 'paid' AND region = 'EU';
```

Сравни `rows × sel_status × sel_region` с реальным числом — это и есть ошибка независимости.

## Грабли и мифы

1. **«`ANALYZE` всё исправит»** — не всегда: при коррелированных колонках независимая статистика принципиально не может дать точную оценку. Нужен `CREATE STATISTICS`.
2. **`n_distinct < 0`** — это доля, а не количество (`-0.5` = половина строк уникальна). Читай внимательно.
3. **`correlation` влияет на стоимость, а не на количество строк.** При `correlation≈1` index scan дешевле, при `≈0` — дороже.
4. **`EXPLAIN` без `ANALYZE` показывает только оценку**, поэтому «план хороший» без выполнения — самообман.
5. **Generic plan может быть лучше custom** — не отключай кэш планов «на всякий случай», проверяй.
6. **`SELECT * FROM t WHERE id = $1`** с `id` — PK: оценка всегда 1, тут ошибок не бывает. Ошибки — на неключевых и составных условиях.
7. **JIT и параллелизм тоже зависят от оценки**: при завышенных строках включается JIT (`jit_above_cost`), который на деле вредит.

## Эксперимент

```sql
CREATE TABLE card_demo AS
SELECT g AS id,
       (g % 2) AS parity,
       CASE WHEN g % 100 < 80 THEN 'A' ELSE 'B' END AS grp,  -- перекос 80/20
       (g % 1000) AS bucket
FROM generate_series(1, 1_000_000) g;
ANALYZE card_demo;

-- Оценка на перекошенной колонке
EXPLAIN ANALYZE SELECT * FROM card_demo WHERE grp = 'A';
EXPLAIN ANALYZE SELECT * FROM card_demo WHERE grp = 'B';

-- Ошибка независимости: parity и grp сильно коррелируют
EXPLAIN ANALYZE SELECT * FROM card_demo WHERE grp = 'A' AND parity = 1;
-- оценка ≈ 40% от 50% = 20% (200k), реально 40% (400k)

CREATE STATISTICS st_card (dependencies, mcv) ON grp, parity FROM card_demo;
ANALYZE card_demo;
EXPLAIN ANALYZE SELECT * FROM card_demo WHERE grp = 'A' AND parity = 1;

-- Поднять детализацию
ALTER TABLE card_demo ALTER COLUMN bucket SET STATISTICS 1000;
ANALYZE card_demo;
SELECT attname, array_length(histogram_bounds::text::text[], 1)
FROM pg_stats WHERE tablename = 'card_demo' AND attname = 'bucket';
```
