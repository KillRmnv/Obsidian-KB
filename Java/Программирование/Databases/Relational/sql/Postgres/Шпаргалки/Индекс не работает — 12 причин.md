# Индекс не работает — 12 причин

Проверяй по порядку. Подробности — [[Оптимизация/Индексы на практике]].

---

## 1. Условие не sargable

```sql
-- индекс по created_at не применится
WHERE date_trunc('day', created_at) = '2026-01-01'
WHERE created_at::date = '2026-01-01'
WHERE created_at + interval '1 day' > now()

-- применится
WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'
```

## 2. Функция над колонкой

```sql
WHERE upper(email) = 'A@B.C';        -- нет
WHERE email = lower('A@B.C');       -- да
-- или expression index:
CREATE INDEX ON users (lower(email));
```

## 3. Несовпадение типов / неявный каст

```sql
WHERE bigint_id = '123'::text       -- каст колонки → индекс не тот
WHERE numeric_col = 1.0             -- сравни типы через pg_typeof
```

Проверка: `EXPLAIN` не показывает `Index Scan`, хотя индекс есть → посмотри тип выражения.

## 4. Порядок колонок в составном индексе

Индекс `(a, b)` не работает для `WHERE b = ...`.

Правило: equality первыми, диапазон/сортировка последними.

```sql
CREATE INDEX ON orders (user_id, created_at DESC);  -- под WHERE user_id=? ORDER BY created_at
```

`PG18+`: skip scan частично снимает это ограничение для колонок с малым числом значений.

## 5. Низкая селективность

Если условие возвращает 30% таблицы, seq scan дешевле. Индекс по `status` с 3 значениями бесполезен — нужен **partial index**.

```sql
CREATE INDEX ON orders (created_at) WHERE status = 'new';
```

## 6. `LIKE '%…%'`

```sql
WHERE name LIKE '%иван%';   -- seq scan
CREATE EXTENSION pg_trgm;
CREATE INDEX ON users USING gin (name gin_trgm_ops);
```

`LIKE 'иван%'` работает только при collation `C` или индексе с `text_pattern_ops`.

## 7. `OR` по разным колонкам

```sql
WHERE email = $1 OR phone = $2;
```

Планировщик может сделать `BitmapOr`, но часто — seq scan. Перепиши через `UNION ALL`.

## 8. Устаревшая статистика

```sql
ANALYZE orders;   -- особенно после массовой загрузки
```

Признак: `reltuples = -1`, `rows` в плане сильно отличается от реальности.

## 9. Слишком высокий `random_page_cost`

```sql
SHOW random_page_cost;   -- 4.0 на SSD → планировщик боится индексов
SET random_page_cost = 1.1;
```

## 10. Индекс невалидный или неготовый

```sql
SELECT indexrelid::regclass, indisvalid, indisready
FROM pg_index WHERE NOT indisvalid;
```

Неудачный `CREATE INDEX CONCURRENTLY` оставляет мусор — удали и создай заново.

## 11. Запрос читает слишком много

`SELECT *` по большой таблице: даже с индексом нужен поход в heap за каждой строкой. Покрывающий индекс + `VACUUM` → index-only scan.

```sql
CREATE INDEX ON orders (user_id) INCLUDE (status, total);
VACUUM orders;
```

## 12. План закэширован (prepared statement)

Generic plan может игнорировать параметр.

```sql
SET plan_cache_mode = force_custom_plan;
-- или EXECUTE с конкретным значением
```

---

## Универсальная проверка

```sql
-- 1. Индекс вообще может быть использован?
SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS) <запрос>;
RESET enable_seqscan;
```

Если с `enable_seqscan=off` индекс **не** используется — проблема в самом условии (каст, функция, порядок колонок), а не в стоимости.

```sql
-- 2. Что видит планировщик
EXPLAIN (ANALYZE, BUFFERS, VERBOSE) <запрос>;
SELECT * FROM pg_stats WHERE tablename = '<таблица>' AND attname = '<колонка>';
```
