# Изоляция и блокировки

## Зачем это нужно

«MVCC» не означает «без блокировок». Разница между СУБД — в том, **что именно блокируется**, **когда** и какие аномалии это оставляет. От этого зависят deadlock'и, «зависшие» сессии и корректность приложения.

## Уровни изоляции: кто что гарантирует

| Уровень | PostgreSQL | MySQL/InnoDB | SQL Server | Oracle |
|---|---|---|---|---|
| `READ UNCOMMITTED` | = RC (грязного чтения нет) | грязное чтение | грязное чтение (NOLOCK) | нет (есть только в воспоминаниях) |
| `READ COMMITTED` (default) | снапшот на **оператор** | снапшот на **оператор**, gap locks почти отключены | блокировки строк; RCSI → версии в tempdb | снапшот на **оператор** |
| `REPEATABLE READ` | снапшот на транзакцию; конфликт `UPDATE` → ошибка | **default**; снапшот + gap locks | блокировки до конца транзакции | = `SERIALIZABLE` (snapshot) |
| `SERIALIZABLE` | **SSI** (откат по зависимостям) | как RR + gap locks (не полная сериализуемость) | range locks | snapshot + `ORA-08177` |

**Важно:** названия уровней **не означают одно и то же**. `REPEATABLE READ` в MySQL и в PG — разные вещи; `SERIALIZABLE` в Oracle — это snapshot isolation.

## Где хранятся блокировки

| | PostgreSQL | MySQL/InnoDB | SQL Server | Oracle |
|---|---|---|---|---|
| Строки | в кортеже (`xmax`) + lock table | в блоке (ITL) | в структурах памяти | в блоке (ITL) |
| Таблицы | общая таблица локов | intention locks | объектные локи | intention locks |
| Эскалация | **нет** | нет (но есть `LOCK TABLES`) | **есть** (~5000 → таблица) | нет |
| Диагностика | `pg_locks` | `performance_schema.data_locks` | `sys.dm_tran_locks` | `V$LOCK` |

## Gap locks и phantom

**PostgreSQL**: в `READ COMMITTED`/`REPEATABLE READ` фантомы возможны (в RR — нет, потому что снапшот), а `SERIALIZABLE` ловит их через **SSI** — отслеживание конфликтов чтения/записи и откат одной транзакции. Никаких gap locks.

**MySQL/InnoDB**: в `REPEATABLE READ` берутся **gap locks** — блокировки промежутков в индексе, чтобы другая транзакция не вставила строку в диапазон. Это защищает от фантомов, но:
- больше блокировок и deadlock'ов;
- `SELECT ... FOR UPDATE` по диапазону блокирует вставки;
- в `READ COMMITTED` gap locks почти отключены.

**SQL Server**: `SERIALIZABLE` — **range locks** (аналог gap locks); по умолчанию — блокировки строк/страниц с эскалацией.

**Oracle**: snapshot isolation; фантомы «не видны» в рамках снапшота, но `SERIALIZABLE` не ловит write skew — приложение должно само.

## Deadlock

| | PostgreSQL | MySQL | SQL Server | Oracle |
|---|---|---|---|---|
| Detection | через `deadlock_timeout` (1 с) | `innodb_deadlock_detect` (мгновенно) | monitor (5 с по умолчанию) | мгновенно |
| Жертва | одна транзакция | одна транзакция | одна (по `DEADLOCK_PRIORITY`) | одна |
| Ошибка | `deadlock detected` (40P01) | `Deadlock found` (1213) | 1205 | `ORA-00060` |
| Что делать | retry | retry | retry | retry |

Правило: **deadlock — не баг, а контракт**; приложение обязано повторять транзакцию.

## Конкурентность без блокировок

| Механизм | Где |
|---|---|
| `SELECT ... FOR UPDATE SKIP LOCKED` | PG 9.5+, MySQL 8.0+, Oracle, SQL Server (READPAST) |
| Advisory locks | PG |
| `ON CONFLICT` / `ON DUPLICATE KEY` / `MERGE` | PG / MySQL / SQL Server, Oracle |
| Optimistic locking (version column) | везде, на уровне приложения |
| Snapshot isolation | PG (RR), Oracle, SQL Server (RCSI/SNAPSHOT) |

### Очередь задач

```sql
-- PostgreSQL / MySQL 8.0+ / Oracle
BEGIN;
SELECT id FROM jobs
WHERE status = 'pending'
ORDER BY created_at
LIMIT 10
FOR UPDATE SKIP LOCKED;
-- ...
COMMIT;
```

SQL Server: `WITH (UPDLOCK, READPAST)`.

## DDL и блокировки

| | PostgreSQL | MySQL | SQL Server | Oracle |
|---|---|---|---|---|
| `ALTER TABLE` | `ACCESS EXCLUSIVE` | metadata lock (MDL) | schema modification lock | DDL lock (online в 12c+) |
| `CREATE INDEX` | `SHARE` (блокирует запись) | `ALGORITHM=INPLACE` | блокирует по умолчанию | `ONLINE` |
| Онлайн-индекс | `CONCURRENTLY` | `ALGORITHM=INPLACE, LOCK=NONE` | `WITH (ONLINE=ON)` | `ONLINE` |
| DDL в транзакции | да (транзакционный) | нет (autocommit) | да | **нет** (автокоммит) |
| `lock_timeout` | есть | `lock_wait_timeout` | `LOCK_TIMEOUT` | `DDL_LOCK_TIMEOUT` |

**Ловушка PG**: очередь локов FIFO — «быстрый» `ALTER` может заблокировать таблицу, если перед ним длинный `SELECT`. См. [[Внутрянка/Конкурентность на практике]].

## Диагностика: перевод

```sql
-- PostgreSQL
SELECT pid, pg_blocking_pids(pid), wait_event_type, wait_event, query
FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- MySQL
SELECT * FROM sys.innodb_lock_waits;
SELECT * FROM performance_schema.data_lock_waits;

-- SQL Server
SELECT session_id, blocking_session_id, wait_type, wait_time
FROM sys.dm_exec_requests WHERE blocking_session_id <> 0;

-- Oracle
SELECT sid, blocking_session, event, seconds_in_wait FROM v$session
WHERE blocking_session IS NOT NULL;
```

## Грабли и мифы

1. **`REPEATABLE READ` ≠ `REPEATABLE READ`**: в MySQL — с gap locks, в PG — снапшот без них.
2. **`SERIALIZABLE` в Oracle — не SSI**: write skew возможен.
3. **PG не делает грязного чтения даже в `READ UNCOMMITTED`** — уровень принимается, но ведёт себя как RC.
4. **Эскалация блокировок есть только в SQL Server** — в PG миллион строк = миллион записей в lock table.
5. **`idle in transaction`** опасен везде, но по-разному: PG — `xmin`/vacuum, MySQL — undo/purge, Oracle — undo retention.
6. **DDL автокоммитит в Oracle/MySQL**, но не в PG — миграции переносятся по-разному.
7. **`NOLOCK` в SQL Server** — не «быстрое чтение», а грязное чтение с пропусками/дублями.
8. **Retry обязателен** для SSI (PG), `ORA-08177`, MySQL deadlock, SQL Server 1205.
9. **`FOR UPDATE` по диапазону** в MySQL RR блокирует вставки (gap locks), в PG — только строки.
10. **Отсутствие deadlock'а не значит «всё хорошо»**: сериализация на горячей строке — это очередь, а не deadlock.
