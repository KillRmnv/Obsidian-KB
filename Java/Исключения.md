# Java SE — Шпаргалка: Исключения (теория + подводные камни собесов)

***

## 1. Иерархия исключений

Вся иерархия исключений строится на одном корне — классе `Throwable`, который является прямым наследником `Object`.[1][2][3][4]

```
Throwable
├── Error                          (unchecked, неисправимые системные сбои)
│   ├── OutOfMemoryError
│   ├── StackOverflowError
│   ├── AssertionError
│   └── ExceptionInInitializerError
└── Exception                      (потенциально обрабатываемые)
    ├── RuntimeException           (unchecked)
    │   ├── NullPointerException
    │   ├── ArrayIndexOutOfBoundsException
    │   ├── ClassCastException
    │   ├── ArithmeticException
    │   ├── IllegalArgumentException
    │   ├── IllegalStateException
    │   └── UnsupportedOperationException
    └── (все остальные) → checked
        ├── IOException
        ├── SQLException
        ├── FileNotFoundException
        └── CloneNotSupportedException
```

### Error vs Exception

**Error** — критические системные проблемы, которые программа **не должна пытаться обрабатывать**: нехватка памяти, переполнение стека, ошибки JVM. Возникают вне контроля приложения, восстановление от них, как правило, невозможно.[5][1]

**Exception** — события, от которых программа **потенциально может восстановиться**. Делятся на checked и unchecked в зависимости от отношения к `RuntimeException`.[1][5]

## 2. Checked vs Unchecked исключения

### Checked исключения[6][7][8][1]

Все подклассы `Exception`, кроме `RuntimeException` и его потомков. Проверяются компилятором — если метод может бросить checked исключение, оно обязано быть либо поймано в `try-catch`, либо объявлено в сигнатуре через `throws`. Не обработанное checked исключение — **ошибка компиляции**.

**Философия:** checked исключение — предсказуемая внешняя проблема, которую разработчик должен учесть. Файл может отсутствовать, сеть может не ответить — это ожидаемые сценарии.

### Unchecked исключения[7][8][6][1]

`RuntimeException` и его потомки, а также `Error`. Компилятор **не требует** их обработки. Возникают в runtime — как правило, из-за ошибок программирования (null-обращение, выход за границу массива, неверный каст).

**Философия:** unchecked исключение — программная ошибка, которую нужно исправлять в коде, а не "обрабатывать". Нет смысла заставлять каждый метод объявлять `throws NullPointerException`.[9][10][11]

### Критерий выбора (по Oracle и Effective Java)[10][11][12][9]

> Если клиент **может разумно ожидать восстановления** от исключения — делай его **checked**. Если восстановление невозможно или нецелесообразно — делай **unchecked**.

| Характеристика | Checked | Unchecked |
|---|---|---|
| Базовый класс | `Exception` (не `RuntimeException`) | `RuntimeException` или `Error` |
| Проверяется компилятором | ✅ | ❌ |
| Требует `try-catch` или `throws` | ✅ | ❌ |
| Причина возникновения | Внешние факторы (I/O, сеть, БД) | Ошибки программирования |
| Восстановление возможно | Как правило да | Как правило нет |
| Примеры | `IOException`, `SQLException` | `NPE`, `ClassCastException` |

### ⚠️ Подводные камни

**Можно ли catch `Error`?** Синтаксически — да, компилятор не запрещает. Но делать это почти всегда неправильно. Единственный редкий случай — graceful shutdown с логированием перед завершением.[1]

**`throws` в сигнатуре для unchecked — допустимо**, но необязательно и вводит в заблуждение. Конвенция: в `throws` объявляют только checked.

**Споры о checked exceptions:** многие современные фреймворки (Spring, Hibernate) переводят checked в unchecked (обёртывают в `RuntimeException`) — из-за "exception leakage" через слои архитектуры и загрязнения сигнатур.[11][9]

## 3. try-catch-finally

### Механизм работы[13][14][15]

**`try`** — блок, в котором может возникнуть исключение.

**`catch`** — перехватывает конкретные типы исключений. Можно указать несколько `catch`. С Java 7 — **multi-catch**: `catch (IOException | SQLException e)`. Порядок `catch` важен: более конкретные типы должны стоять **выше** общих — иначе ошибка компиляции ("exception already caught").

**`finally`** — выполняется **всегда**, независимо от того, было ли исключение, и был ли он поймано. Исключения: `System.exit()`, фатальные `Error`, принудительное завершение JVM.

### Когда finally НЕ выполняется

В трёх случаях: `System.exit()` вызван явно, поток убит принудительно (kill -9), фатальный `Error` на уровне JVM. Во всех остальных случаях — выполняется.[13]

### ⚠️ Подводные камни try-catch-finally

**`return` в `finally` поглощает `return` из `try`/`catch`.** Если `try` вернул `"catch"`, а `finally` вернул `"finally"` — метод вернёт `"finally"`. Исходный return подавлен.

**Исключение в `finally` поглощает исходное исключение.** Это главная ловушка! Если в `try` брошено исключение X, а в `finally` брошено исключение Y — Y "побеждает" и распространяется дальше. X теряется безвозвратно. Именно для этого создан try-with-resources с механизмом suppressed exceptions.[16][17]

**`catch` не обязателен при наличии `finally`.** Конструкция `try { } finally { }` без `catch` — абсолютно легитимна. Используется для гарантированной очистки ресурсов.

## 4. try-with-resources (Java 7+)

### Механизм[14][15][18][13]

Любой объект, реализующий `AutoCloseable` (или `Closeable`), можно объявить в скобках после `try`. JVM гарантирует вызов `close()` по завершении блока — в обычном и исключительном случаях.

Ресурсы закрываются в **обратном порядке** объявления (последний открытый — первый закрытый). С Java 9 ресурс может быть объявлен вне `try` как effectively final переменная.

### Suppressed Exceptions — ключевое отличие от finally[15][19][17][20][16]

Это важный механизм, который часто спрашивают на собесах.

**Ситуация:** в `try`-блоке возникло исключение A. При закрытии ресурса `close()` брошено исключение B. Что происходит?

- **В try-catch-finally:** исключение B **замещает** A — A теряется, B распространяется. Исходная причина ошибки утрачена.
- **В try-with-resources:** исключение A распространяется (оно первичное), а B **присоединяется к A как suppressed**. Получить его можно через `a.getSuppressed()`. Ничего не теряется.[19][17][15]

`Throwable.addSuppressed()` и `getSuppressed()` — методы для ручного управления suppressed-исключениями (Java 7+).[17]

### ⚠️ Подводные камни try-with-resources

**`AutoCloseable.close()` может бросать `Exception`**, тогда как `Closeable.close()` — только `IOException`. Если ресурс реализует `AutoCloseable`, нужно обрабатывать потенциальный `Exception` из `close()`.

**Порядок закрытия — обратный порядку открытия.** Если открыто три ресурса — закрывается последний, потом средний, потом первый.

**`close()` вызывается даже при `return` из `try`-блока** — это гарантия ресурсоочистки.

## 5. Создание собственных исключений

### Теория[21][10][11]

Собственное исключение создаётся расширением:
- `Exception` — если хочешь **checked** исключение
- `RuntimeException` — если хочешь **unchecked** исключение

**Минимальный правильный набор конструкторов** для кастомного исключения (следуй контракту `Throwable`):
1. `CustomException()` — без аргументов
2. `CustomException(String message)` — с сообщением
3. `CustomException(String message, Throwable cause)` — с сообщением и причиной
4. `CustomException(Throwable cause)` — только причина

Наиболее важен конструктор с `cause` — он поддерживает **exception chaining**.

### Exception Chaining (цепочка исключений)[22][23][24][25][21]

Механизм сохранения исходного исключения при оборачивании в новое. Без chaining нижний уровень "проглатывает" исходную причину — дебаггинг становится невозможным.

`getCause()` — возвращает исходное исключение. `initCause()` — устанавливает причину постфактум (можно вызвать **только один раз**, повторный вызов — `IllegalStateException`). При печати стектрейса JVM автоматически выводит всю цепочку "Caused by:".[25][22]

### ⚠️ Подводные камни

**Антипаттерн — "swallowing" (проглатывание) исключения.** `catch(Exception e) { }` или `catch(Exception e) { log(e); }` с последующим бросанием нового исключения **без** передачи `cause` — полная потеря контекста ошибки. Всегда передавай исходное исключение как `cause`.[21]

**Не злоупотребляй checked exceptions в своём API.** Если каждый метод сервисного слоя объявляет `throws MyCheckedException`, это загрязняет сигнатуры и вынуждает верхние слои либо пробрасывать, либо скрывать. В Spring/JEE принято оборачивать в `RuntimeException`.[9][11]

**`catch(Exception e)` — слишком широко.** Ловит и `RuntimeException`, и все checked — скрывает реальные проблемы. Всегда ловить максимально конкретный тип.

**Не используй исключения для управления потоком.** `try-catch` для логики (например, парсинг через `NumberFormatException`) — антипаттерн: дорого (создание объекта исключения + стектрейс), нечитаемо, скрывает реальные ошибки.

**`finally` не должен бросать исключения.** Это основное правило safe cleanup — исключение в `finally` поглощает исходное. Если в `finally` необходима операция, которая может бросить — оберни её в свой `try-catch` внутри `finally`.[16][17]
