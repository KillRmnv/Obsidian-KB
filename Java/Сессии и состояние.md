Сессии в сервлетах как раз про то, чтобы поверх **stateless**‑HTTP сделать per‑user состояние.

## Почему нужен session tracking

HTTP протокол по своей природе **без сохранения состояния**: каждый запрос независим, сервер по умолчанию не знает, что два запроса пришли от одного пользователя.otus+1

Для логина, корзины, настроек пользователя и любого состояния между запросами нужен механизм **session tracking** — способ связать серию запросов с одной логической сессией пользователя и держать для неё данные на сервере.javarush+1

Фраза:

> HTTP stateless, поэтому без дополнительного механизма сервер не различает пользователей и не помнит их состояние. Session tracking позволяет связать несколько запросов одного клиента в сессию и хранить для неё данные на сервере.javarush+1

## HttpSession: получение, атрибуты, жизнь, invalidation, fixation

`HttpSession` представляет серверную сессию пользователя: объект с уникальным ID и набором атрибутов.otus+1

Основные моменты:

- **Получение/создание**:[javarush](https://javarush.com/quests/lectures/questservlets.level12.lecture03)
    
    - `request.getSession()` — вернёт существующую сессию для этого клиента или создаст новую, если её ещё нет.
        
    - `request.getSession(false)` — вернёт существующую или `null`, если сессии нет (не создаёт новую).
        
- **Работа с данными (атрибуты)**:[javarush](https://javarush.com/quests/lectures/questservlets.level12.lecture03)
    
    - `session.setAttribute("user", userObj)` — положить объект в сессию.
        
    - `session.getAttribute("user")` — получить.
        
    - Это **данные на весь срок жизни сессии одного пользователя**, доступны во всех его запросах, пока сессия жива.
        
- **Время жизни**:otus+1
    
    - У каждой сессии есть **таймаут бездействия** (max inactive interval) — интервал, после которого при отсутствии запросов она истекает.
        
    - Можно настроить:
        
        - глобально в `web.xml` (`<session-config><session-timeout>30</session-timeout></session-config>`),
            
        - или программно: `session.setMaxInactiveInterval(seconds)`.[otus](https://otus.ru/nest/post/372/)
            
    - По истечении таймаута сессия становится недействительной, данные теряются.
        
- **Явное уничтожение**:javarush+1
    
    - `session.invalidate()` — завершает сессию сразу, очищает все атрибуты (обычно при logout).
        
- **Session fixation (сессия‑фиксация)**:[otus](https://otus.ru/nest/post/372/)
    
    - Атака, когда злоумышленник навязывает жертве известный ему Session ID.
        
    - Типичная защита: при успешной аутентификации **регенерировать ID** (создать новую сессию или сменить ID), чтобы украденный/навязанный ID перестал быть валидным.
        
    - В современных фреймворках (Spring Security) это обычно делается автоматически, но понимать идею нужно.
        

Фраза:

> `HttpSession` создаётся при первом запросе (или вручную через `getSession()`), имеет уникальный ID и хранит атрибуты между запросами. Сессия живёт до таймаута бездействия или явного `invalidate()`. Для защиты от session fixation при логине часто регенерируют Session ID.javarush+1

## Способы трекинга сессий

Сессия живёт **на сервере**, а клиенту нужно как‑то передать её идентификатор (Session ID), чтобы сервер мог «узнать» пользователя в следующих запросах.otus+1

Основные способы:

1. **Cookies (по умолчанию)**javarush+1
    
    - При создании сессии контейнер отправляет клиенту cookie с именем `JSESSIONID` и уникальным идентификатором.
        
    - В следующих запросах браузер автоматически посылает cookie обратно, сервер по `JSESSIONID` находит нужную `HttpSession`.
        
    - Это основной и самый удобный механизм.
        
2. **URL rewriting**:javarush+1
    
    - Если cookies отключены, можно «пришивать» Session ID к URL: `http://host/app/page;jsessionid=ABC123...`.
        
    - Для этого используют `response.encodeURL(url)` / `encodeRedirectURL(url)`, которые при необходимости добавят `jsessionid` в ссылку.[javarush](https://javarush.com/quests/lectures/questservlets.level12.lecture02)
        
    - Минус — ID виден в адресной строке и логах.
        
3. **Hidden fields**:otus+1
    
    - Можно передавать идентификатор сессии в скрытых полях HTML‑форм (`<input type="hidden" ...>`), особенно в чистом HTML‑форм‑флоу.
        
    - Сейчас используется редко и обычно как дополнительный механизм.
        

Фраза:

> Session ID обычно передаётся через cookie `JSESSIONID`. Если cookies недоступны, контейнер может использовать URL rewriting (`encodeURL`) или скрытые поля форм, чтобы ассоциировать запросы с серверной сессией.javarush+2

## Где реально хранятся данные сессии и как работает JSESSIONID

- Все данные, которые ты кладёшь в `HttpSession` (`setAttribute`), хранятся **на стороне сервера**: в памяти контейнера, иногда с сохранением в репозиторий/кластер в enterprise‑окружении.javarush+1
    
- На клиенте хранится только **идентификатор сессии** — `JSESSIONID` в cookie или в URL.[otus](https://otus.ru/nest/post/372/)
    
- Алгоритм:
    
    1. Клиент делает первый запрос → контейнер создаёт новую `HttpSession`, генерирует уникальный ID.
        
    2. Контейнер отправляет ответ с cookie `JSESSIONID=<id>`.
        
    3. Браузер сохраняет cookie и отправляет её с каждым следующим запросом к этому домену.
        
    4. Контейнер по `JSESSIONID` находит соответствующий объект `HttpSession` на сервере и отдаёт его в `request.getSession()`.javarush+1
        
- При истечении сессии или `invalidate()` объект `HttpSession` удаляется с сервера, а `JSESSIONID` становится невалидным; при новом запросе создаётся новая сессия с новым ID.otus+1
    

Фраза:

> Данные сессии хранятся на сервере, в `HttpSession`. Клиент обычно хранит только идентификатор сессии, `JSESSIONID`, в cookie или URL. При каждом запросе сервер по этому ID находит нужную сессию и её атрибуты.javarush+1
